# 1 Language Models
- language models encode statistical info about languages → tell us how likely a word is to appear in a given context
    - statistical nature of language discovered decades ago → 1951 landmark paper by Claude Shannon - _Prediction & Entropy of Printed English_
    - this paper introduced many concepts still used today e.g. entropy
- <mark style="background: #FFB8EBA6;">token</mark> = basic unit of language model
    - can be word, character, sub word e.g. `transition` = `tran` `si` `tion`
    - GPT-4 average token length is approx. 3/4 of a word so 100 tokens = 75 words
    - <mark style="background: #FFB8EBA6;">vocabulary</mark> = set of all tokens a model can work with, small number of tokens can be used to construct many different words
        - Mistral 8x7b vocab = 32k
        - OpenAI tiktoken = 100,256
        - choosing optimal vocab size is a tricky task → larger not always better
- 2 main types of language models
    - <mark style="background: #FFB8EBA6;">autoregressive language model</mark> = trained to predict next word in sentence, using only preceding words e.g. GPT (decoder only)
    - <mark style="background: #FFB8EBA6;">masked language model</mark> = predict missing words in a sentence e.g. BERT (encoder only)
    - the first kind is most common, can generate open ended text of any length (hence name = Generative AI)

# 2 Self-Supervision
- <mark style="background: #FFB8EBA6;">self supervision</mark> = core technique enabling language models to scale, helped overcome data labelling bottleneck
    - most models before were supervised i.e. needed expensive + time consuming labelling
        - e.g. 5 cents per image in ImageNet = $50,000, getting multiple people for consistency would cost more
    - labelling can be done pretty easily in most cases by humans, but not all tasks are simple
        - e.g. Latin translations or CT scan detection labels would be very expensive
- self-supervision use labels that occur naturally → for a given sentence, you just try to predict next word (which is the label)
    - much more unlabelled data in the world → language models can scale from this
    - larger models have more capacity to learn, therefore, need more training data to maximise performance

# 3 Foundation Models
- language models can do incredible things, but are limited to text
    - humans perceive not just language but vision, audio, touch etc → AI needs this to progress to AGI levels
- models have become **multimodal** e.g. understand text, image and audio
    - OpenAI’s Clip, 2021 used self-supervision to find naturally occurring pairs of images + their text (caption) to use as training data for text to image model
    - able to generate 400 million pairs (400x size of ImageNet) without labelling cost
- prior to LLMs, you had to fine-tune general models for task-specific purposes but this would not generalise outside of the tasks
    - foundation models now work relatively well for many tasks out of the box, often need to be tweaked e.g.
        - prompt engineering e.g. few shot learning
        - RAG - connecting model to database
        - or further fine-tuning your model
- 3 factors that lead to growth of AI engineering using large general foundation models
    1. **emerging AI capabilities** - can generate open-ended responses, unlocking many tasks e.g. anything requiring communication like writing emails, responding to customers, summarising contracts
    2. **increased AI investments** - more use-cases + estimated cost rapidly decreasing
    3. **low barrier to entry** - model-as-a-service approach via APIs, also ability to help with coding helps this further
- Sam Altman in Sept 2022, 2 months before ChatGPT release said only small number of teams can build foundation models e.g. big corporates (Google, Meta, Microsoft), governments and well funded startups (OpenAI, Mistral)
    - this has become very true but AI engineering discipline has grown from this
    - tools for AI engineering growing faster by GitHub stars than any other major projects e.g. React, Bitcoin etc

## 3.2 Common Use-Cases
- **Coding** - considered most popular category since coding tools are popular + developers code a lot
    - GitHub copilot revenue crossed 100m only 2 years after launch, many other tools blown up
    - clear AI can do SWE tasks, but unsure if it can do entire SWE job
    - McKinsey found its better at some tasks in making developers more productive e.g.
        - 200% more productive for documentation
        - 25-50% more productive for code generation + refactoring
        - minimal for very complex tasks
    - specific tasks for coding related AI’s include
        - generating code to extract structured data from webpages and PDFs _e.g. AgentGPT_
        - converting english to code _e.g. DB-GPT, sqlchat, PandasAI_
        - rendering designs or screenshots into webpages _e.g. screenshot-to-code, draw-a-ui_
        - translating between programming language/frameworks _e.g. gpt-migrate, ai-code-translator_
        - writing documentation _e.g. autodoc_
        - creating tests _e.g. PentestGPT_
        - generating commit messages _e.g. aicommits_
- **Image & Video production** - great for creative tasks like this due to probabilistic nature e.g. MidJourney, Adobe FireFly, Runway
    - many marketing and ad firms use it to generate first drafts or examples to iterate on
    - can use AI to generate multiple ads and see which words best based on seasons, locations etc
- **Writing** - ideal since we write a lot, often tedious, LLMs mainly trained for writing
    - consumers can use this communicate better e.g. emails or giving bullet points and asking for paragraphs
        - e.g. Grammarly helps with writing and grammar
    - writing books or generating stories around ideas
    - also becoming common in sales, copywriting and product descriptions
    - also quite good at SEO optimised text → enabled generation of content farms just to get Google to drive traffic to them and sell ads
        - this has implications for the future since much of the internet in the future might be AI generated junk
- **Education** - schools should encourage use of AI to help them learn faster
    - e.g. personalised lecture plans, summarising text and providing feedback to questions
    - different students can use it for different learning types e.g. auditory or visualisations or equation formatting
    - can generate quizzes (open + multi-choice) and evaluate answers, debating partner
        - much better at presenting views on same topic than average human
        - one innovative example → teacher gives AI generated essay for students to find + correct mistakes
- **Conversational bots** - help find, explain and brainstorm
    - can emulate personalities and talk in different ways e.g. therapists or romantic partners
    - customer chat bots very popular since they can save costs + improve experience for customers
    - also applications for smart NPCs in games, helping with the story line + realism
- **Information aggregation** - success often depends on filtering + digesting useful info, lots of this in today’s world with info overload
    - AI helpful in aggregating and summarising this info e.g. processing documents and retrieving insights conversationally
    - e.g. talk to your docs → can help research and create reports or distill complex ideas
- **Data organisation** - data explosion continues and we need to organise this for later search and retrieval
    - AI can help generate metadata + descriptions to video, audio, images
    - extracting structured info from unstructured data so it can be organised and searched e.g. contracts, charts, reports
- **Workflow automation** - ideally AI can automate as much busy work as possible e.g. booking things, planning tasks or trips, filling forms
    - enterprises can use it for lead management, invoicing, reimbursements, data entry, responding to customers
    - can also be used to create synthetic data for humans to use and improve on for more training or uses
    - key to this is access to external tools e.g. other apps → agentic frameworks could be big

# 4 Considerations when building AI apps
- <mark style="background: #FFB86CA6;">fast pace of change</mark>
    - improved model abilities e.g. more context, better outputs, faster + cheaper inference
        - adaptation to new models e.g. buy vs build might change every couple of months based on cost-benefit analysis
        - need to keep up to date with the advances
        - hardware considerations also e.g. GPU providers and how you compute → at their behest
    - adaptation to changes
        - API convergence of many strong foundation models makes it easy to switch since the standardisation is there
        - however, needs good infra for versioning and evaluating these transitions
    - regulatory changes - AI tech is becoming heavily regulated with compute, talent and data all becoming more restrictive e.g. GDPR compliance
- <mark style="background: #FFB86CA6;">data privacy</mark>
    - model-as-service concerns e.g. sending private data through APIs and considering policy changes
    - transparency issues e.g. training data secrecy and safety issues for users
    - memorisation and leaks of training data is also a risk → especially in adversarial attacks
- <mark style="background: #FFB86CA6;">product defensibility</mark>
    - low barrier to entry is blessing and curse, harder to build moats e.g. OpenAI new features kill startups for each release
        - e.g. PDF chat plugins no longer needed
    - 3 competitive advantages in AI → technology, data, distribution (mostly with big companies)
        - big companies have more data, but specialised data collection could become a moat for certain startups

- fundamental building blocks of AI engineering has similarities to ML engineering → usually ML people are doing this at enterprises

### 4.1.1 main layers of the AI stack (first is lowest level)
1. <mark style="background: #FFB8EBA6;">infrastructure</mark> - includes **tooling, model serving, monitoring, managing data + compute**
    - setting up GPU clusters, data centre management and keeping systems online
2. <mark style="background: #FFB8EBA6;">model development</mark> - **frameworks for modelling, training, finetuning, inference optimisation, data engineering**
    - modelling + training = model architecture, training + fine tuning e.g. Tensorflow, Torch, Transformer library
        - requires specialised ML knowledge + algorithms, concepts related to training e.g. gradient descent, objective and loss functions
            - no longer must have for AI engineering but does help
        - training may include both pre-training or fine-tuning (i.e. from scratch or domain specific)
    - dataset engineering is generating, curating and labelling data needed for training + adapting
        - very dependent on volume of data you have
        - traditional ML uses almost always tabular data + lots of feature engineering while foundation models use unstructured data
            - unique challenges include deduplication, tokenisation, quality control (e.g. remove PII + toxic data)
    - inference optimisation is about making models smaller, faster + cheaper
        - e.g. quantisation, distillation, factorisation + model alteration for faster decoding
        - always been important for ML but even more important for foundational models
        - autoregressive nature of LLMs mean generating output tokens sequentially is a bottleneck
            - big focus on reducing latency in both academia + industry
3. <mark style="background: #FFB8EBA6;">application development</mark> - **most rapidly evolving + common, involves evaluation, prompt engineering, interfaces to apps**
    - model quality no longer differentiates since everyone uses the same few base models
        - instead gain differentiation through app development process
        - includes evaluation, prompt engineering + the AI interface to the app

|                          | ML Models      | Foundation Models |
| ------------------------ | -------------- | ----------------- |
| Evaluation               | important      | very important    |
| Prompt Engineering + RAG | not applicable | very important    |
| AI Interface             | less important | very important    |

- evaluation involves picking best base model + evaluating progress on your tasks
	- evals more important for foundation models due to open-ended nature
		- no explicit ground truths like traditional ML e.g. fraud detection, recommender systems etc
		- there is also many possible right answers in open-ended scenarios
	- evolving model capacity + techniques cause benchmarks to lag behind
		- many possible eval techniques, many different setups for these e.g. custom methods for performing benchmarks
		- e.g. Gemini MMLU results used CoT@32 while GPT used 5-shot → not fair comparison
- prompt engineering + RAG → getting desirable behaviour from context alone by giving right instructions
	- also getting structured outputs e.g. JSON, managing the memory and retrieved documents
	- prompt engineering has big impact on model performance e.g. Gemini MMLU went from 84% to 90% through new prompting
- AI interfaces are the main custom part since backend model is standardised
	- includes web + desktop apps, browser extension, bots, plugins
## 4.2 AI engineering vs ML engineering
- enterprise use cases still need to map business metrics to ML metrics + vice versa
    - still need systematic experimentation e.g. hyperparameters (prompts + sampling variables)
    - still need models to run faster + cheaper + setup feedback loops to improve with production data
    - overall principles largely unchanged from traditional ML engineering
- differences between the AI vs ML engineering
    - ↔️ **always using someone else’s model, enterprises do not pre-train their own models**
        - focused more on prompt engineering + fine tuning
    - ↔️ **much bigger models than traditional ML → more compute and latency**
        - focused on efficient training and inference optimisation e.g. GPU clusters
    - ↔️ **open ended outputs, less about development, more on adapting + evaluating models**
        - adaption techniques split into if it changes model weights or not e.g. prompt engineering vs fine tuning
- prompt engineering vs finetuning
    - **prompt engineering** does not require weight updates, giving it instructions + examples in context input
        - RAG is a form of this, prompt augmented with retrieved info from database
        - easier to start with this approach + can go a long way using it alone
        - might not be enough for complex apps or if you have strict performance requirements
    - **finetuning + inference optimisation** update the model weights
        - more complicated + need more data but can improve both speed and quality dramatically
        - reducing model size cannot be done without changing model weights
## 4.3 AI engineering vs Full-stack engineering
- more emphasis on app development e.g. interfaces increases demand for front-end engineering
    - rising importance led to shift for APIs rather than ML knowledge
    - bringing AI engineering closer to full-stack development
    - “AI engineering is just software engineering with AI models thrown in the stack”
- full-stack engineers benefit from ability to turn ideas into quick demos, get feedback + iterate on promising ones
    - traditional ML has lots of data gathering, curating, training etc
    - now possible to start with product first and invest in data after initial success
