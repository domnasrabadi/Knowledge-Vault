# 1 AI Engineering Architecture
- can spend so much time planning - but getting feedback from users is the most crucial data source
	- chatbot interfaces are easy for users but harder to extract feedback signals from 
- best to start simple and add components as you e.g. 
	- enhance context via RAG or tools 
	- guardrails to protect user and system 
	- model router/gateway for more complex pipelines + security 
	- caching to optimise latency and costs 
	- more complex agents and actions 
## 1.1 Step 1: Enhance Context 
- context comes from various retrieval mechanisms e.g. text, tools, tables, images, APIs etc 
	- **context construction is feature engineering for LLMs**
## 1.2 Step 2: Guardrails
- helps mitigate risks to protect the system and users 
	- should be placed wherever there is risk exposures - broadly into inputs + outputs
		- **input guardrails** - help prevent PII leaking, protect against malicious prompts 
			- can scan inputs for sensitive data via regex 
		- **output guardrails** - used to catch output failures + specify policies for handling various failure modes
			- e.g. malformed responses, hallucinated info, generally bad responses
			- e.g. toxic responses, sensitive/private info, remote code vulnerabilities etc 
	- recall, should track both useful metrics
		- attack success rate/violation rate
		- false refusal rate 
	- guardrails involve considering tradeoffs e.g. latency vs reliability 
- how to handle guardrails when triggered
	- <span style="color:rgb(255, 136, 0)">simple retry</span> - useful due to probabilistic nature of LLMs
	- <span style="color:rgb(255, 136, 0)">execute multiple versions in parallel then choose best</span> 
	- <span style="color:rgb(255, 136, 0)">fall back to humans</span> for tricky requests
		- e.g. based on picking up key terms in the query 
## 1.3 Step 3: Routers & Gateways
- both routers + gateways useful as app complexity grows and need to serve multiple different models
	- can have different models for different queries rather than one-for-all
	- e.g. route simpler queries to cheaper models 
		- routing should happen before retrieval 
- <mark style="background: #FFB8EBA6;">router</mark> = typically an **intent classifier** to predict what user is trying to do 
	- can help from users engaging in OOT conversations and detect ambiguous queries + ask clarifications 
	- routers can also be **next-action predictors**
		- e.g. agent to decide what action to do next e.g. search via API? politely decline request?
		- for models with memory systems - which part of memory hierarchy should we build context from?
	- both types can be applied on top of LLMs
		- or trained with small classifiers from scratch 
		- may have multiple router models since they are cheap + fast 
- <mark style="background: #FFB8EBA6;">gateway</mark> = intermediate layer to securely interface with various models/components 
	- e.g. self-hosted models, API calls, small specialised scoring models etc 
		- really just a unified wrapper to access control + cost management for all models 
	- model gateway classes can have additional abilities 
		- fallback policies for handing rate limits or API failures e.g. `GPTHelper` backoff and retry 
		- load balancing, logging, analytics, caching, guardrails etc

## 1.4 Step 4: Reducing Latency with Caching
- caching is very useful for queries with multiple steps of time consuming actions 
- 2 major types of caching mechanisms:
	- <mark style="background: #FFB8EBA6;">exact caching</mark> = cached items used when exact items are requested
	- <mark style="background: #FFB8EBA6;">semantic caching</mark> = cached items used when similar item is needed 
		- only works well with reliable similarity mechanisms + requires vector DB to store embeddings of cached
- caches can be implemented to use in-memory storage for fast retrieval
	- typically also use an eviction policy to manage size e.g. LRU, LFU, FIFO 
- be careful using caches 
	- can cause data leaks when not properly handled e.g. showing another users cache 
	- can provide out of date info if caches not updated to use latest data sources
	- semantic caching often more prone to failure + setting thresholds is tricky 
## 1.5 Step 5: Using Agents
- can increase ability + risk of system by allowing model outputs to lead to write actions 
	- need to be careful here - refer to chapter 6

## 1.6 Monitoring & Observability 
- more complex the application == more crucial observability is 
	- useful DevOps observability metrics include mean detection time, mean response time, change failure rate
- <mark style="background: #FFB86CA6;">goal of monitoring</mark> = similar to evaluation, **to mitigate risks + discover opportunities** 
	- evals and monitoring should work closely 
		- metrics should translate well to monitoring metrics 
		- eval performance should also be close to monitoring performance 
		- issues detected in monitoring should feed into the evaluation pipeline 
### 1.6.1 Metrics
- <mark style="background: #FFB8EBA6;">metrics</mark> = to tell you when something is wrong + identify opportunities to improve
	- first need to understand what are types of failure modes you want to catch + design metrics around these
	- **types of failures** include:
		- formatting failures
		- factual consistency + relevancy failures e.g. LLM judges 
		- safety metrics e.g. toxicity, private info etc 
		- abnormal queries + refusal rates 
- can also perform monitoring on **conversational signals** 
	- <span style="color:rgb(255, 136, 0)">how often do users stop generation halfway?</span>
	- <span style="color:rgb(255, 136, 0)">average number of turns per conversation?</span>
	- <span style="color:rgb(255, 136, 0)">average number of tokens per input?</span>
	- <span style="color:rgb(255, 136, 0)">average number of tokens per output?</span>
		- *certain queries lengthier than others?*
	- <span style="color:rgb(255, 136, 0)">model output token distribution?</span>
		- *changing over time?*
		- *becoming more or less diverse?*
- **latency + cost metrics** also useful in monitoring
	- longer context + responses usually increase cost 
	- latency metrics e.g. TTFT, TPOT, total latency 
	- cost metrics e.g. TPS, total queries, volume of tokens, Requests per Minute 
### 1.6.2 How to use Metrics
- 💡 useful to measure how correlated metrics are to each other 
	- especially to your north-star business metrics e.g. daily active users, session duration 
	- can also choose between performing spot-checks vs exhaustive checks 
	- ensure metrics are broken down into relevant axes for granular understanding of performance
		- e.g. users, releases, prompt versions, time 
- each component within a system pipeline will have it's own metrics
	- e.g. for RAG, evaluated via context relevance and precision 
	- e.g. Vector Database can measure storage, index efficiency and query efficiency 
- metrics are typically aggregated, need to look into the detail of logs to understand what happened
	- <mark style="background: #FFB8EBA6;">logs</mark> = append-only events 
	- log everything e.g. configs, APIs, model name, sampling settings, prompt template, user queries, original + final prompt
		- ...intermediate outputs, final outputs, tool use, when component starts + ends 
		- also helps to give logs tags + IDs for later filtering e.g. session ID for logs related to same user session 

> [!NOTE] Use AI to help you analyse your logs 
- <mark style="background: #FFB8EBA6;">traces</mark> = reconstructed timeline of logs to show entire process
	- i.e. detailed recording of a request's entire execution path through all components 
	- ideally you can trace each query's transformation step-by-step 
- drift detection can also be cause by multiple dynamic components at play 
	- e.g. system prompt changes, user behaviour changes, underlying model changes

# 2 User Feedback
- user feedback plays a **crucial role in evaluating the application + informing it's development** 
	- **user feedback == proprietary data == competitive advantage** == more valuable as data becoming scarce 
	- when designed well, user feedback can be the backbone of developing your data flywheel 
## 2.1 Extracting Conversational Feedback 
- feedback can be of 2 types
	- <mark style="background: #FFB8EBA6;">implicit</mark> user feedback = inferred from user actions - highly dependent on use-case 
		- feedback from here can relate to the application's performance or user's own preferences 
	- <mark style="background: #FFB8EBA6;">explicit</mark> user feedback = provided by customer directly e.g. 👍🏼 vs 👎🏼, rating scales etc 
	- explicit usually more sparse, while implicit is more abundant but noisier 
- user feedback from conversations can be used for:
	- <span style="color:rgb(255, 136, 0)">evaluation</span> = derive metrics to monitor application 
	- <span style="color:rgb(255, 136, 0)">development</span> = to train future models or guide development 
	- <span style="color:rgb(255, 136, 0)">personalisation</span> = personalise the application to each user
- feedback signals can be found in 2 ways 
	- <mark style="background: #FFB8EBA6;">signals from natural language</mark> 
		- <span style="color:rgb(255, 0, 247)">early termination</span> = if user terminates response early it's likely bad feedback 
			- e.g. telling model to stop, leaving the agent hanging 
		- <span style="color:rgb(255, 0, 247)">error correction</span> =  user tries to correct errors by rephrasing query 
			- e.g. "No" or  "I meant this.." or pointing out things model should have done differently 
			- or even when user asks model to explicitly confirm if something is true
				- indicates response lacks detail or lack of user trust rather than bad response 
			- user edits also very good source for preference data 
		- <span style="color:rgb(255, 0, 247)">complaints</span> = just complaining without trying to correct
			- can occur in many different ways:
				- clarifying demand again 
				- complaining model did not answer or answer is irrelevant 
				- pointing out specific search results to check/re-check
				- suggest model to use search 
				- states answer is not specific/accurate/grounded/detailed
				- pointing out the model is not confident
		- <span style="color:rgb(255, 0, 247)">sentiment</span> = general expressions of negative sentiment without explanations to why is usually bad 
	- <mark style="background: #FFB8EBA6;">signals from conversational patterns</mark> (i.e. user actions)
		- <span style="color:rgb(255, 0, 247)">regeneration</span> = user asks same question to get new response 
		- <span style="color:rgb(255, 0, 247)">conversation organisation</span> = using ability to delete, rename, share or bookmark 
			- deleting conversation usually strong signal it was bad 
			- renaming suggests conversation was good but poor auto-generated title 
		- <span style="color:rgb(255, 0, 247)">conversation length</span> = number of turns per conversation can be a useful signal 
			- depends on the application to tell if it is a good or bad thing 
			- however, ideally for customer support type apps, less turns is better 
		- <span style="color:rgb(255, 0, 247)">dialogue diversity</span> = measured by distinct token or topic count 
## 2.2 Feedback Design 
- when should you collect feedback? 
	- ideally throughout the user journey 
		- <span style="color:rgb(255, 136, 0)">the beginning first using it</span> - if left empty, can start neutral and calibrate to the user over time 
		- <span style="color:rgb(255, 136, 0)">when something bad happens</span> - users should be able to flag if it's hallucinating, blocked benignly or too long to respond
		- <span style="color:rgb(255, 136, 0)">when model has low confidence</span> - model can ask user to help nudge or ask for feedback
- how to collect feedback? 
	- feedback should be non-intrusive, easy to ignore and not disrupt user experience 
	- there should also be incentives for giving good feedback 
## 2.3 Feedback Limitations
- biases of user feedback
	- <span style="color:rgb(255, 136, 0)">leniency biases</span> - tendency to rate items more positively than warranted 
		- essential to look at user rating distributions to detect this 
		- rather than show just good vs bad - be smart on design of options, trying to be more specific in categories 
	- <span style="color:rgb(255, 136, 0)">randomness</span> - people often give random feedback due to being busy or lack of motivation to be thoughtful 
	- <span style="color:rgb(255, 136, 0)">position bias</span> - often picking default first option 
		- can test by randomly shuffling ordering + experimenting
	- <span style="color:rgb(255, 136, 0)">preference bias</span> - e.g. some users might prefer longer responses naturally 
- <mark style="background: #FFB8EBA6;">degenerative feedback loops</mark> = when predictions themselves influence the feedback, in turn, influencing next iteration of model, amplifying the initial biases 
	- **user feedback loops are always incomplete**! they can only give feedback on what they can see
	- degenerate loops happen in systems where the user's feedback can modify model behaviour 
		- e.g. recommendation systems 
		- well studied problem - exposure bias, popularity bias, filter bubbles
