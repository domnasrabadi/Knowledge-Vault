# 1 LLM Evaluation Challenges
- 🚸 more intelligent = harder to eval
    - e.g. assessing summarisation requires reading entire book
    - evals can be much more time consuming for sophisticated tasks
    - also need to fact check, reason + get SMEs
- 🚸 open-ended nature undermines traditional approaches using ground truths
    - so many possible correct responses, impossible to curate eval sets comprehensively enough
- 🚸 models treated as black boxes since companies don’t expose or lack of technical expertise of developers
    - model architecture, training data + process reveal strengths and weaknesses but without them → can only eval model by observing outputs
- 🚸 eval benchmarks constantly getting outdated
    - AI progresses rapidly, evals should too → benchmarks becoming faster saturated e.g. GLUE after 1 year required new set SuperGLUE
- 🚸 scope of evaluation has expanded for general-purpose models
    - task-specific applications might be easier, but so many different tasks possible
- most new research for GenAI focused on algorithmic + application developments e.g. context, scaling
    - much less focused on evaluation, but fortunately growing
- without systematic evals, hard to evaluate the applications
    - many focus on vibe checks e.g. go-to prompts they test, only good for quick ad-hoc checks

# 2 Language Modelling Metrics 
- useful to consider actual language modelling metrics since they correlate well to downstream performance 
	- 5 key metrics we consider 

![[Screenshot 2024-09-08 at 1.59.15 pm.webp| center | 800]]

- LLMs learn the distribution of their training data 
	- the better they learn, the better they can predict what comes next in training data 
- most autoregressive LMs today trained via **cross-entropy** and **perplexity**
    - both measure how well LM captures info in training data
        - also both correlate with performance on downstream applications
    - metrics have not changed much since 1948 → Claude Shannon introduced entropy to measure how well we model English
## 2.1 Entropy 
- <mark style="background: #FFB8EBA6;">entropy</mark> = how much info a token carries 
	- → higher entropy = more information = more bits needed to represent it
    - e.g. language on left has higher entropy → each token has more info but needs more bits to represent
    - lower entropy = more predictable 

![[Screenshot 2024-09-08 at 2.00.49 pm.webp| center | 600]]

- entropy also defined as measure of uncertainty
	- intuitively - how difficult it is to predict what comes next in a language

> [!info] What is a Bit?
> - Bit = short for binary digit - the most basic unit of info e.g. on/off, yes/no, true/false
> - most frameworks use natural log (**nat**) as unit for entropy/cross-entropy 
> 	- nat uses base $e$ so PPL is exponential of $e$
> 	- $PPL(P,Q) = e^{H(P,Q)}$

## 2.2 Cross-Entropy 
- **cross entropy** = measures how difficult it is for LM to predict what comes next in this dataset
    - a model’s cross entropy depends on:
        1. training data predictability → measured by training data’s entropy $H(P)$
        2. how model’s distribution diverges from true training distribution $D_{KL}$
- assume:
    - $P$ = training data true distribution
    - $Q$ = language model learned distribution
    - **goal is to get $Q$ to be same as $P$**
- $H(P, Q)$ = cross entropy of $Q$ w.r.t. $P$
    - $H(P,Q)$ = sum of entropy of $P$ and $Q$’s divergence from $P$
    - if LM perfectly learns training data ($Q = P$) ➡️ divergence of $Q$ from $P$ = 0
- LMs try to minimise cross-entropy w.r.t the training data
    - can also think of model’s cross entropy as approximation of the entropy of it’s training data

$$
\begin{gather}
\textbf{cross entropy of Q w.r.t P} \\ \\ 
\large H(P, Q) = H(P) + D_{KL}(P \mid \mid Q)
\end{gather}
$$
- where $H$ = symbol for entropy and cross entropy
    - $H(P)$ = entropy of training data
    - $H(P, Q)$ = cross entropy of model distribution to training distribution
- $D_{KL}$ = Kullback-Leibler divergence of $Q$ from $P$
    - KL Divergence measures how different one probability distribution is from another
- Both CE and KL are not symmetric 
	- i.e. $H(P, Q) \ne H(Q,P)$
## 2.3 Bits-per-Character & Bits-per-Byte

> [!example] Bits of Entropy
> - recall 1 unit of entropy = 1 bit 
> 	- 1 bit = 2 possible outcomes, equally likely 
> - 8 equally likely outcomes would have entropy of $\log_2(8)$ = $3$ bits
> 	- since 3 binary decisions required to determine outcomes 
> - if cross-entropy of LM = 6 bits, LLM needs 6 bits to represent each token

- the number of bits-per-token across models is not comparable - due to different tokenization methods 
	- so instead of cross entropy - can use BPC/BPB 
- <mark style="background: #FFB8EBA6;">Bits-per-character (BPC)</mark> = if bits per token is 6 and average token has 2 characters
	- $BPC = \frac{6}{2} = 3$ bits
- <mark style="background: #FFB8EBA6;">Bits-per-byte (BPB)</mark> = (standardised version) number of bits an LM needs to represent one byte of original training data
	- if $BPC = 3$ and each character is 7 bits (7/8 of a byte) 
	- → $BPB = \frac{3}{7/8} = 3.43$

>[!info] *Recall* $\rightarrow$ 1 byte = 8 bits

- cross entropy measures how efficient an LM is at compressing text
    - if BPB of LM = 3.43 → can represent each original byte (8 bits) using 3.43 bits
        - essentially compressing training data to less than half original size
## 2.4 Perplexity
- <mark style="background: #FFB8EBA6;">Perplexity</mark> (or PPL) = **exponential of cross entropy** 
	- also **measures amount of uncertainty when predicting next token**
    - using above example, predicting a position in square means choosing among options → $2^2$ = 4 perplexity
    - lower perplexity = LLM better captures training text statistics 

$$
\begin{gather}
\textbf{perplexity (PPL)} \\ \ \\ \large PPL(P, Q) = 2^{H(P, Q)}
\end{gather}
$$
- where $PPL(P, Q)$ = perplexity of LLM with learned distribution $Q​$
- to calculate PPL, you need access to logprobs for tokens
### 2.4.1 What is a good perplexity?
- good value of PPL depends on training data distribution, vocabulary size and context length 
	- PPL usually conditioned on approx. last 500-1000 tokens 
		- PPL of 20 = model has $\frac{1}{20}$ chance of predicting next token correct 
		- if vocab size is 100k, this is a very good model 
- generally, the following factors can give you a sense of how good the PPL is
	- more predictable text $\approx$ lower expected PPL e.g. coding languages 
	- more complex datasets $\approx$ higher PPL 
	- bigger vocabulary $\approx$ higher PPL
	- longer context $\approx$ lower PPL - since more info model gets as context better predicts next token


>[!info] PPL not very useful for SFT/RLHF models
>-  since it measures ability to complete text not human dialogue 

- PPL is lowest for text model has seen/memorised in training
	- hence can be used for detecting contamination e.g. benchmark cheating 
	- PPL highest for gibberish/unpredictable texts 

>[!tip]
> Can use PPL as a filtering mechanism for adding new data e.g. only if PPL is high (less duplicates)

# 3 Exact Evaluation 
- Sections 3, 4 and 5 cover the below coloured parts of the diagram 
	- i.e. automatic evals for open-ended tasks 
	- since close-ended evals already well defined e.g. classification problems in regular ML 

![[Screenshot 2024-09-08 at 2.27.53 pm.webp| center | 800]]

- **exact eval** = measuring model performance directly on a task
    - produces judgement without ambiguity unlike subjective eval
## 3.1 Functional Correctness
- <mark style="background: #FFB8EBA6;">functional correctness</mark> = if it performs intended functionality, considered the best metric 
	- since it measures directly the intended use of the model on the task 
- best suited for tasks w/ measurable objectives, not easy to automative 
	- e.g. code generation - **tested via unit tests + assertions** 
		- used by many of the LLM coding benchmarks e.g. OpenAI HumanEval
	- usually comes in form of problem set 
		- each problem has a set of test cases (scenarios to test w/ expect outputs)

```python
# function to be tested
def factorial(n: int) -> int:
	if n < 0: 
		raise ValueError("Cannot compute factorial of negative number.")
	if n == 0 or n == 1:
		return 1

	result = 1
	for i in range(2, n + 1):
		result *= 1
	return result
```

```python
# test cases via assert statements
assert factorial(0) == 1, "factorial(0) should be 1." 
assert factorial(1) == 1, "factorial(1) should be 1." 
assert factorial(5) == 120, "factorial(5) should be 120." 
assert factorial(10) == 3628800, "factorial(10) should be 3628800."
```
- coding benchmarks typically use <span style="color:rgb(255, 0, 247)">pass@k</span> metric = accuracy of solved problems 
	- each problem, model generates multiple ($k$) code samples (i.e. multiple tries)
	- higher $k$ gives model more chances to get it right - so *pass@10* result better than *pass@3* usually
		- common to report $k$ of 1, 3, 10
	- successful solution = if any $k$ pass all test cases 
## 3.2 Similarity to Ground-Truths 
- similarity to ground-truth = evaluating generated response to gold-standard references
	- metrics used here have been used for decades in translation + summarisation 
- reference data also called <mark style="background: #FFB8EBA6;">ground truth</mark> or <mark style="background: #FFB8EBA6;">golden answers</mark>, each input may have multiple
	- requires format `| input | ground_truth | generated_response |`
	- ground-truths = correctly labelled or annotated text - by human or AI
		- manual human = expensive + time cost, AI can draft + human review (quicker)
- approach summarised by similarity between 2 open ended texts 
	- downfall is there are many ways to express something, hence impossible for exhaustive references

4 key methods to measuring similarity 

![[Screenshot 2024-09-08 at 3.12.21 pm.webp| center | 700]]

1. asking <mark style="background: #FFB86CA6;">evaluator to judge</mark> if 2 texts are the same 
	- can use human or LLM-as-Judge
2. <mark style="background: #FFB86CA6;">exact match</mark> - if generation matches reference exactly
	- works best for short exact responses e.g. multi-choice QA
	- variations can exist to account for formatting, but method is fragile 
		- e.g. `'What's 2 + 3'` - answer = `'5'`, generation = `'2 + 3 is 5'`
	- outputs for exact match are binary (match or not)
3. <mark style="background: #FFB86CA6;">lexical similarity (n-gram)</mark> - how similar generation is to reference _visually_
	- how much 2 texts overlap, usually at n-gram level e.g. single words, pairs, triplets etc 
		- extract all n-grams from both generation + reference
		- then calculate how many reference n-grams in generation 
	- example Generation `"my cats eat mice"`, Reference `"my cats scare the mice"`
		- generation has 3/5 words in reference i.e. 60%
	- common metrics for lexical similarity, all differ slightly in overlap calculation 
		- <span style="color:rgb(255, 136, 0)">edit distance</span>
		- <span style="color:rgb(255, 136, 0)">BLEU</span> 
		- <span style="color:rgb(255, 136, 0)">ROUGE</span>
		- <span style="color:rgb(255, 136, 0)">METEOR++</span>
		- <span style="color:rgb(255, 136, 0)">TER</span>
		- <span style="color:rgb(255, 136, 0)">CIDEr</span>
	- less benchmarks today use this approach, drawbacks include:
		- ⛔️ requires curating comprehensive set of reference responses
			- and references can be low-quality or wrong
		- ⛔️ scores don't correlate well to actual correctness 
			- e.g. low score != bad response and vice versa 
			- OpenAI found BLEU scores on HumanEval can be high but still wrong
4. <mark style="background: #FFB86CA6;">semantic similarity (embedding)</mark> - how similar generation is to reference _semantically_
	- lexical similarity is hard token matching, semantic similarity is considered soft matching
	    - uses embeddings to find similar words e.g. synonyms - might still make perfect sense but slightly different word choice
	    - i.e. **measures similarity of meaning** between 2 texts → requires numerical representation (embeddings)
	- most commonly people use cosine similarity between 2 embeddings
	    - variation often includes what embeddings are chosen:
	        - <span style="color:rgb(255, 136, 0)">BERTScore</span> - BERT generated embeddings
	        - <span style="color:rgb(255, 136, 0)">MoverScore</span> - mixture of embedding algos to generate embeddings

$$
\begin{gather}
\textbf{cosine similarity} \\ \ \\ \large CS_{A, B} = \frac{A \cdot B}{|| A|| \times || B ||}
\end{gather}
$$
- output of cosine similarity is between -1 and 1, where 
	- $A \cdot B$ = dot product of A and B
	- $|| A ||$ = euclidean norm of $A$ (L2 norm) = $\sqrt{A_1^2 + A_2^2 + ...}$
- semantic is more general than lexical approach → does not require crafting as comprehensive reference set
    - ⛔ measurement only works however with high quality embeddings
    - ⛔ also can be computationally expensive to calculate via embedding models
## 3.3 Embeddings Primer
- <mark style="background: #FFB8EBA6;">embeddings</mark> = numerical representation that aims to capture meaning of the original data 
	- produced as output from embedding algos e.g. BERT, CLIP, sentence-transformers
	- <mark style="background: #FFB8EBA6;">embedding size</mark> = how many features an embedding vector has (usually 100-10,000)
		- <span style="color:rgb(255, 136, 0)">Google BERT</span>
			- BERT base: 768
			- BERT large: 1024
		- <span style="color:rgb(255, 136, 0)">OpenAI Embeddings API</span>
			- text-embedding-3-small: 1536
			- text-embedding-3-large: 3072
		- <span style="color:rgb(255, 136, 0)">Cohere Embed V3</span>
			- embed-english-v3.0: 1024
			- embed-english-light-3.0: 384
- goal of embedding algorithm = produce embeddings which capture essence or meaning of original data
    - verify how good they are by seeing if similar texts are closer than embeddings of unrelated texts e.g. cosine similarity
    - embeddings very commonly used in NLP tasks e.g. classification, topic modelling, recsys, RAG
    - <mark style="background: #FFB8EBA6;">MTEB</mark> - **Massive Text Embedding Benchmark** = measures embedding quality on variety of tasks
- any data can be represented via embeddings → multimodal + joint embeddings
    - e.g. Pinterest use embeddings for images, graphs, queries and users
    - e.g. Criteo and Coveo use embeddings for products
    - CLIP was first major modal that mapped different modalities into shared embeddings space

# 4 Subjective Evaluation 
- **subjective eval** = measures model performance depends on model, prompt, rater etc
    - e.g. for AI judge, same model and prompt can still give different results
    - or for human marker, can depend on their day, personal biases etc
## 4.1 LLM-as-Judge 
- <mark style="background: #FFB8EBA6;">LLM-as-Judge</mark> → very fast growing use case, evaluating AI using AI
    - becoming most popular in production - especially when hard to collect user feedback
    - Huyen notes all demos from startups in 2023 used AI-as-Judge in some form
        - Lang chain State of AI report also mentioned 58% of evals used this
        - lots of research arising from this too e.g. G-Eval, GPTScore
### 4.1.1 Benefits & Limitations of LLM-as-Judge
- 💡 some tips (and mitigating risks) for using LLM-Judges
	- reliability can be helped via more examples (few-shots)
		- but beware LLMs can be consistently wrong in some aspects
	- cost is still cheaper than humans, especially in long term as you can collect data + FT smaller models
	- can be used in prod for monitoring + continuous feedback
	- very useful to measure agreement to human evaluation
		- by measuring agreement to SME classification or ratings
		- GPT4 has shown to have strong correlation to human judgement e.g. 
			- Zhang, 2023 -  found GPT4/Human agreement = 85%, more than human/human at 81%
			- Dubois, 2023 - found 98% correlation to LMSYS Chat Arena 
	- don't trust any AI judge if you cannot see the model or prompt within
	- supplement AI judges with exact + human evaluation

| ✅ Advantages of LLM-as-Judge                                                   | ⛔️ Limitations of LLM-as-Judge                                                                                                              |
| ------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------- |
| fast, easy to use.  <br><br>Relatively cheaper than human evaluators           | reliability: can give varying scores given the same prompt or slightly perturbed. <br> <br>Makes it hard to reproduce or trust eval results |
| do not need reference data                                                     | criteria ambiguity: many different possible criteria, scoring systems, instructions etc                                                     |
| flexibility: can judge any attribute <br><br>e.g. toxicity, hallucinations etc | model specific biases <br><br>e.g. 1st position, self, verbosity bias etc                                                                   |
| explanation of decision making - useful for auditing <br><br>e.g. via CoT      | cost and latency: same concerns <br><br>e.g. IP, Privacy etc                                                                                |

- overall, Huyen sees lots of promise in LLM-Judges
	- and expects more standardisation + popularity going forward
### 4.1.2 How to use LLM-as-Judge
- 3 possible options for LLM-Judge approach
	1. <span style="color:rgb(255, 136, 0)">evaluate quality of response by itself</span>
		- most basic form, can use any criteria you desire
	2. <span style="color:rgb(255, 136, 0)">compare generated response to golden answer to determine they are the same</span>
		- alternative to similarity measurements 
	3. <span style="color:rgb(255, 136, 0)">compare generated response to golden answer to determine the best one</span>
		- useful for preference data in post-training alignment
		- also useful for test time compute + ranking models via comparative evals
- versatility of LLM-judges is great - can evaluate based on any criteria you want
	- e.g. AzureAI criteria includes groundedness, relevance, fluency, similarity
	- LangChain includes conciseness, relevance, correctness, harmfulness, helpfulness, etc
	- Ragas includes faithfulness, answer relevance
- be cautious - score outputs from judges depend on underlying model + prompt 
	- 💡 some tips on prompting LLM judges, explaining each clearly:
		- **task to perform** 
			- e.g. "*Evaluate the relevance between the generated answer and the question.*"
		- **criteria to follow to evaluate**, more detailed = better
			- e.g. "*Your primary focus should be on determining whether the generated answer contains sufficient info to address the given question according to the ground truth answer*"
		- **scoring system** 
			- include examples of each response for a given score 
				- if possible, also why a response receives a certain score 
			- classification e.g. relevant/irrelevant/neutral
			- discrete numerical values e.g. 1 to 5
			- continuous numerical values e.g. 0-1, not recommended
	- note: LLMs typically work better with textual classes instead of numbers 
		- if you use numbers, try to stick to discrete scoring, wider intervals typically worsens performance
	- altering the model, the prompt, or the model’s sampling parameters results in a different judge


> [!NOTE] AzureAI Relevance Prompt
> 
```markdown
Your task is to score the relevance between a generated answer and the question based on the ground truth answer in the range between 1 and 5, and please also provide the scoring reason.

Your primary focus should be on determining whether the generated answer contains sufficient information to address the given question according to the ground truth answer. …

If the generated answer contradicts the ground truth answer, it will receive a low score of 1-2.

For example, for the question "Is the sky blue?" the ground truth answer is "Yes, the sky is blue." and the generated answer is "No, the sky is not blue."

In this example, the generated answer contradicts the ground truth answer by stating that the sky is not blue, when in fact it is blue. This inconsistency would result in a low score of 1–2, and the reason for the low score would reflect the contradiction between the generated answer and the ground truth answer.
```

- what model to use as judge? 
	- often stronger judges are used - try to pick strongest available for budget 
	- can also decide to spot-check i.e. samples of output instead of exhaustive checks (all outputs)
		- can have weaker model doing continuous offline evals too
	- can use the same model to judge but beware of self bias, still good for sanity check
		- research shows asking model to eval itself (self-critique) can iteratively improve responses
	- small specialised judges also becoming an exciting direction 
		- easier to build + much faster than general purpose LLMs
- 3 types of specialised judges/models
	- <mark style="background: #FFB86CA6;">reward model</mark> = takes in a (`prompt, response`) pair, scores how good the response given the prompt
		- very successful through RLHF usage recent years
		- e.g. Google’s Cappy, 2023 - produces score from 0-1 on correctness against prompt with only 360 million params
	- <mark style="background: #FFB86CA6;">reference based judge</mark> = evaluates the generated response with respect to one or more reference responses
		- can output similarity or quality score
		- e.g. BLEURT, 2020 takes candidate response + reference response
			- then outputs similarity score
		- Prometheus, 2023 takes `prompt, generated response, reference response, scoring rubric` 
			- outputs a quality score between 1 and 5, assuming that the reference response gets a 5
	- <mark style="background: #FFB86CA6;">preference model</mark> = takes in (`prompt, response 1, response 2`) as input 
		- outputs which of the two responses is better (preferred by users) for the given prompt
			- perhaps most exciting direction for specialised judges
			- predicting human preference opens many new possibilities e.g. preference data collection
		- having good human preference predictor makes eval easier + safer
		- PandaLM, JudgeLM (both 2023) are specialised LLMs to output which response is better + why

## 4.2 Ranking with Comparative Evaluation
- comparative evaluation = ranking models against each other, via pointwise or comparative evaluation
	- <mark style="background: #FFB8EBA6;">pointwise evaluation</mark> = evaluate each model independently, ranking them by their scores
	- <mark style="background: #FFB8EBA6;">comparative evaluation</mark> = evaluate models against each other, compute ranking from comparison results
		- first used by Anthropic, 2021, now this is what powers the 🤗 LMSYS Chatbot Arena
- comparative evals easier for subjective content
	- note: not all questions should be answered by preference, especially when correctness is more important
	- preference based voting only works if voters have expertise in the subject
- model providers offer option to pick best response in the UI
    - each could be generated by different models (AB testing) or same model but different sampling params
    - this is known as a **match** → human or AI picks winner
    - **win rate** = probability model A preferred over model B
- a rating algo can then compute ranking of models from the comparative signals
    - this concept new to AI but been around for a century in other industrues 
	    - e.g. Chess → **ELO, Bradley-Terry**
        - LMSYS started with ELO then switched to BT since the found ELO more sensitive to order of evaluators + prompts
- makes model ranking a predictive problem → compute ranking from historical match outcomes to predict future match outcomes
### 4.2.1 Challenges of Comparative Evals
- ⛔ <span style="color:rgb(255, 136, 0)">scalability bottlenecks</span> 
	- data intensive process, pairs grows quadratically with number of models 
		- e.g. # pairwise comparisons = $\# models^2$
	- unclear transitivity → ranking algos usually assume transitivity 
		- i.e. if A > B and B > C, then A should also be > C
	    - unclear if this holds for AI model ranking though, even human preference is not transitive
	- have to re-eval every new model that comes online
		- more difficult when evaluating private models
- ⛔ <span style="color:rgb(255, 136, 0)">lack of standardisation + quality control</span> 
	- quality depends on human evaluators + their own biases
	    - LMSYS has lots of bad prompts in their dataset e.g. “Hi”, “Hello”, “hey”
	    - too many simple prompts likely pollute the rankings + introduce noise
	- can address via standardised prompt sets
	    - can also address using only evaluators we trust → using common criteria + training on how to prompt
	        - severely reduces volume of comparisons we get however
	    - users can also just randomly pick options and not really care
	    - can address via AI evaluator again → more reliable
- ⛔ <span style="color:rgb(255, 136, 0)">comparative performance doesn't solve for absolute performance</span>
	- i.e. it tells us which model is better, but not how good a model is or if good enough for our use-case
	- need other forms of evals to determine best model for you 
		- other factors besides preference, e.g. cost, performance boost, etc
### 4.2.2 Future of Comparative Evals 
- besides these, many people prefer/find it easier to compare 2 outputs vs giving scores
	- as models get stronger, tasks get harder, concrete scores might not even be feasible
	- leaving comparisons as a key pillar to evals
- comparisons focus on human preference i.e. the important aspect 
	- also reduces the need to keep creating benchmarks less likely to be saturated
	- give us discriminating signals that otherwise can't be obtained
- comparative evals are also hard to game, since they are democratic
- very good option to add to toolkit for offline evals
	- in addition to in house evals, and online AB testing
