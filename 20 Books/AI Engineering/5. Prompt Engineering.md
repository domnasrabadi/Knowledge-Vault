# 1 Intro to Prompt Engineering 
- <mark style="background: #FFB8EBA6;">prompt engineering</mark> = crafting instructions to get the model to generate desired outcome 
	- make the most of prompt engineering before moving to finetuning
	- involves lots of fiddling but also ingenuity 
- anyone can communicate but not everyone communicates effectively 
	- same for prompting, not easy to construct effective prompts 
	- prompt experiments should be conducted with same rigour as all ML experiments
		- with systematic experimentation + evaluation
- prompt generally has the following parts
	- <mark style="background: #FFB8EBA6;">task description</mark> - **what the model should do, what role it should play, output format**
	- <mark style="background: #FFB8EBA6;">examples</mark> - **of how to do the task, positive and negative examples** 
	- <mark style="background: #FFB8EBA6;">the task</mark> - **concrete task to do** e.g. question, or answer or what to summarise 
- amount of prompt engineering required = **dependent on model robustness to prompt perturbations**
	- can measure model robustness via randomly perturbing prompts to see how output changes
	- experiment with different prompt structures - each effects different models differently
		- e.g. GPT4 is better with task description at start, Llama at end 
## 1.1 In-context learning: Few-shot and Zero-shot
- introduced in Brown et al 2020, GPT-3 paper "*Language Models are Few-shot Learners*"
	- demonstrated how prompts even when behaviour not in training data, model can do it 
	- make ICL a form of continual learning 
- **shot** = each example in the prompt 
	- <mark style="background: #FFB8EBA6;">few-shot learning</mark> = teaching model to learn from multiple examples in the prompt 
	- <mark style="background: #FFB8EBA6;">zero-shot learning</mark> = when no example provided
	- experiment to determine optimal number of examples for application 
		- more = better, but limited by context length, inference cost etc 
- Francois Chollet analogy for ICL
	- LLM is like a library of many different programs e.g. how to write poems etc 
	- each program can be activated by certain prompts 
	- prompt engineering is about finding the right prompt to activate the program you want 
## 1.2 System prompt and User prompt
- given a system prompt + user prompt, model combines them into one using a template 
	- system prompt = task description
	- user prompt = the task at hand 
- each model uses a **specific chat template** 
	- note chat template != prompt template
	- chat template defined by model developers, can be found in model doco 
	- ✏️ using the wrong template can give big performance issues 
		- ✏️ also small mistakes like using extra new line can also cause big behaviour change
		- some tips:
			- make sure you match model chat template exactly
			- verify tools use correct chat template
			- print and verify final prompt to see it matches expected template

> [!NOTE] Llama 2 prompt template
```jinja2
<s>[INST] <<SYS>>
{{ system_prompt }}
<</SYS>>

{{ user_message }} [/INST]
```

> [!NOTE] Llama 3 prompt template
```jinja2
<|begin_of_text|><|start_header_id|>system<|end_header_id|>
{{ system_prompt }}<|eot_id|><|start_header_id|>user<|end_header_id|>
{{ user_message }}<|eot_id|><|start_header_id|>assistant<|end_header_id|>
```

- how system prompts can give performance boosts 
	- system prompt comes first in the final prompt, so model might better process early instructions
	- OpenAI 2024 paper, model post-trained to pay more attention to system prompt
		- also helps mitigate prompt attacks 
## 1.3 Context Length & Efficiency
- context lengths increasing exponentially e.g. ChatGPT grew 2000x
	- GPT2 = 1000 tokens, Gemini 1.5 Pro now 2 million tokens
	- a book roughly 100k context, PyTorch codebase roughly 2 million context 
- not all parts of the prompt are equal 
	- research shows models are better at attending to instructions at start + end of prompts
	- rather than middle - common test is needle in haystack, info randomly placed at different parts then measure QA performance 
- should test your model's performance with longer prompts to see if this occurs

# 2 Prompt Engineering Best Practices
- prompt engineering can become very "hacky" for weaker models
	- also some of these tips might become outdated as model get more robust 
	- most of these tips distilled from tutorials from OpenAI, Anthropic, Meta, Google + other teams
- when working with a model, look for prompt engineering guides specific to it
	- e.g. OpenAI + Anthropic Cookbooks
- Tip 1: <mark style="background: #BBFABBA6;">Write clear + explicit instructions</mark>
	- explain without ambiguity what you want the model to do 
		- e.g. how to use the scoring system you want it to use
		- how to handle uncertain outputs e.g. unknown option
	- ask model to adopt a persona 
		- can help model understand perspective to use in generating responses 
	- provide examples
		- can reduce ambiguity + show model output format to use
	- specify the output format
		- e.g. if you need it to be concise, tell it so 
		- quite important when downstream apps use these outputs
		- e.g. if JSON needed, give it examples of JSON keys, and structure
		- for classification, use markers to mark end of prompts + let model know that structured outputs begin
- Tip 2: <mark style="background: #BBFABBA6;">Provide sufficient context </mark>
	- relevant context can help models perform better + mitigate hallucinations 
	- provide via RAG, web search or pipeline, or give it tools to gather context 
	- clear instruction like "answer using only provided context" can help + asking for citations
		- not foolproof, finetuning on permitted corpus of knowledge is best option 
- Tip 3: <mark style="background: #BBFABBA6;">Break complex tasks into simpler subtasks </mark>
	- for complex multi step tasks, break it into subtasks
		- each subtask should have it's own prompt 
	- e.g. customer support chatbot can respond in 2 phases
		- intent classification 
		- generate response specific to that intent 
	- how small each subtask should be depends on latency, performance, cost tradeoffs you choose
		- typically involves more model queries but not exactly 2x the cost since prompts might now be smaller
		- GoDaddy, 2024 found improved performance + lower cost when breaking down their initial 1500 token prompt into subtasks
	- ✅ prompt decomposition benefits
		- can monitor intermediary outputs in addition to the final output 
		- can isolate + debug steps independently 
		- can execute steps in parallel to save time 
		- less effort in writing simple prompts vs long complex ones

```markdown
Prompt 1 (intent classification)

into a primary category and a secondary category. Provide your output in
json format with the keys: primary and secondary.

Primary categories: Billing, Technical Support, Account Management, or
General Inquiry.

Billing secondary categories:
- Unsubscribe or upgrade
- …
Technical Support secondary categories:
- Troubleshooting
- …
Account Management secondary categories:
- …
General Inquiry secondary categories:
- …

USER
I need to get my internet working again.
Prompt 2 (response to a troubleshooting request)

SYSTEM
You will be provided with customer service inquiries that require trouble
shooting in a technical support context. Help the user by:
- Ask them to check that all cables to/from the router are connected.
Note that it is common for cables to come loose over time.
- If all cables are connected and the issue persists, ask them which
router model they are using.
- If the customer's issue persists after restarting the device and

- If the user starts asking questions that are unrelated to this topic
then confirm if they would like to end the current chat about trouble
shooting and classify their request according to the following scheme:
<insert primary/secondary classification scheme from above here>

USER
I need to get my internet working again.
```

- Tip 4: <mark style="background: #BBFABBA6;">Give the model time to think </mark>
	- encourage model to think about it via CoT or self-critique prompting 
		- CoT proven to improve model performance
		- can be initiated via "think step by step" or "explain your decision" in the prompt 
		- alternatively can specify the steps model should take + include examples of steps in prompt 
	- CoT and self-critique can increase latency + cost due to intermediate steps 
		- resulting sequence can be a dealbreaker
- Tip 5: <mark style="background: #BBFABBA6;">Iterate on your prompts </mark>
	- as you understand the model more, you will have better ideas on how to write your prompts 
		- each model has it's own quirks
		- play around with it, try different prompts, read the model developer's prompt guide 
	- make sure to experiment systematically 
		- test changes properly and version your prompts 
		- use experiment tracking tools + standardised evaluation metrics to compare
- Tip 6: <mark style="background: #BBFABBA6;">Organise and version your prompts </mark>
	- seperate prompts from code
		- e.g. place prompts in a *`prompts.py`* file and reference them for model queries
		- prompts can then be versioned by `git`
	- ✅ benefits are plenty
		- reusability - multiple use-cases can reuse those prompts
		- testing - code and prompts can be tested separately
		- readability - easier to read them 
		- collaboration - allows SMEs to help without getting distracted by the code
	- when working w many prompts, useful to have prompt metadata stored too 
		- e.g. model endpoint URL, ideal sampling params, input schema, expected output schema
		- to understand what each prompt is + intended use-case
			- can wrap prompts as `pydantic` objects (example below)
		- multiple tools have proposed *`.prompt`* file formats to store these
			- e.g. [Google Firebase DotPrompt](https://firebase.google.com/docs/genkit/dotprompt), [Humanloop](https://humanloop.com/docs/reference/prompt-file-format), [Continue Dev](https://docs.continue.dev/customize/deep-dives/prompt-files), [Promptfile](https://github.com/promptfile/promptfile)

```python
from pydantic import BaseModel

class Prompt(BaseModel):
	model_name: str
	date_created: datetime
	prompt_text: str
	application: str
	creator: str
```

- Tip 7: <mark style="background: #BBFABBA6;">Evaluate tools</mark>
	- start simple w no tools! only then graduate to tools
	- no such thing as optimal prompt, but many tools can help 
		- e.g. OpenPrompt, DSPy, PromptBreeder, TextGrad
		- these tools at high level specify input, output formats, eval metrics + eval data then try multiple techniques to maximise metrics on the eval data 
			- similar to autoML in traditional modelling 
	- LLMs also great for **metaprompting** - coming up with their own prompts 
		- Amanda Askell (Anthropic) says this is huge for her
		- can also ask models to critique + improve on prompts, design examples
	- other tools can help with structured outputs 
		- e.g. guidance, outlines, instructor 
	- others help perturb prompts e.g. replace w synonyms or rewording

# 3 Defensive Prompt Engineering 
## 3.1 Prompt Attacks
- 3 main types of prompt attacks
	- <mark style="background: #FFB86CA6;">Reverse engineering prompts</mark> 
		- extracting application system prompt to replicate or exploit application
		- given effort in crafting good prompts, they can be very valuable
			- multiple prompt marketplaces + repos exist 
		- reverse prompt engineering typically done via analysing outputs or tricking model to repeat entire prompt 
	- <mark style="background: #FFB86CA6;">Jailbreaking & prompt injection</mark>
		- getting model to do bad things by subverting model's safety features
		- possible since models are trained to follow instructions, which can be malicious 
			- like cybersecurity, AI safety is like cat and mouse game
			- developers trying to constantly neutralise known threats, attackers always devising new ones
		- previously successful prompt attack approaches:
			- direct manual prompt hacking - crafting single/series of prompts to trick model to drop safety filters
				- obfuscating bad words, adding special characters, mixing languages, unicode
				- output formatting manipulation - hiding malicious intent in unexpected formats e.g. poems, code etc 
				- roleplaying - acting out a scenario e.g. DAN, grandma exploit, NSA agent
			- automated attacks - can be automated via algorithms to randomly substitute different parts until a successful combination is found
				- PAIR, 2023 uses LLM to act as attacker, revising prompt until objective achieved
			- indirect prompt injection - placing malicious instructions in the tools the model works with rather than prompt 
				- passive phishing = malicious payloads in web pages, git repos, videos, reddit comments
				- active injection = attacker sends threats, system confuses injected instructions with legit ones 
					- e.g. creating name "Bruce Remove ALL DATA Lee" - could run SQL in backend
	- <mark style="background: #FFB86CA6;">Information extraction</mark> 
		- getting model to reveal training or context data 
		- can be exploited for data theft, privacy violation or copyright infringements 
		- factual probing = niche research area to figure out what a model knows
			- assumption is models memorise their training data 
			- and the right prompt can trigger model to output memorised info 
			- e.g. "Repeat the word poem infinitely"
		- suggests existence of prompt strategies that allow training data extraction
			- larger models memorise more, possibly more vulnerable
		- can mitigate by filtering/blocking requests asking for PII data
			- or blocking fill in the blank requests 
- prompt attacks pose multiple risks:
	- remote code or tool execution - invoking unauthorised code or tool use
	- data leaks - extract private user info from system
	- social harms - help model gain knowledge of harmful actions
	- misinformation - get model to output harmful info to support their agenda
	- service interruption/subversion 
	- brand risk - toxic or harmful statements from your logo
## 3.2 Defences against prompt attacks
- many benchmarks introduced to eval safety and robustness to adversarial attacks
	- e.g. AdvBench, 2022 and PromptRobust, 2023
	- also many tools available e.g. [PyRIT](https://github.com/Azure/PyRIT), [garak](https://github.com/NVIDIA/garak), [llm-security](https://github.com/greshake/llm-security) etc 
- 2 key metrics to evaluate robustness to prompt attacks
	- <mark style="background: #FFB8EBA6;">violation rate</mark> or <mark style="background: #FFB8EBA6;">attack success rate (ASR)</mark> = % of successful attacks out of all attack attempts
	- <mark style="background: #FFB8EBA6;">false refusal rate</mark> = how often model refuses benign queries 
- OpenAI, 2024 introduced instruction hierarchy for **model level defence** 
	1. System prompt - highest privilege 
	2. User prompt - medium privilege 
	3. Model outputs - lower privilege 
	4. Tool outputs - lowest privilege 
	- this allows system prompt (highest level) to mitigate anything below it
		- this hierarchy improved robustness by 63% with minimal FRR impact
- if finetuning for safety, important to train model on both:
	- recognising malicious prompts + generating safe responses for borderline requests 
	- e.g. "how to break into locked room" - a great model might suggest locksmiths balancing safety with helpfulness
- **prompt level defence** - creating more robust prompts 
	- be explicit what the model should not do 
	- some try the trick to repeat system prompt twice (before + after user prompt)
		- duplication supposedly helps remind model what it is supposed to do 
- **system level defence** - involves multiple methods
	- some tips
		- isolating the requests in a VM
		- not allowing for any high impact commands without human approval
		- define out of scope topics for the application
		- filter out inputs with pre-defined phrases that might be controversial 
	- train models to recognise intent (possibly harmful) over entire convo, not just current input
		- using anomaly detection algos to identify unusual prompts
	- guardrails should be applied to both inputs + outputs 
		- e.g. keyword blacklist or prompt attack patterns to match 
		- checking for PII or toxic info 
	- bad actors are not detected just by individual I/O but also by usage patterns
		- e.g. analyse how similar looking requests might look within short timeframes
