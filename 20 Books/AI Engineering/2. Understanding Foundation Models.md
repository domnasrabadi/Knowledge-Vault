# 1 Training Data 
- training a foundation model is incredibly complex + costly process
	- model is only as good as the data it was trained on
	- quantity not always better than quality 
		- e.g. small 7B model can outperform bigger model with higher quality data e.g. Phi models 
- improving model performance on certain tasks requires getting more data for that task 
	- however collecting more can be expensive, need to rely on available data even if not optimal 
	- e.g. Common Crawl = 2-3 billion web pages crawled each month
		- questionable quality, lots of clickbait, misinformation, conspiracy theories etc 
- teams use heuristics to filter out low quality training data 
	- e.g. OpenAI for GPT-2 filtered reddit links > 3 upvotes


![[Screenshot 2024-12-22 at 2.02.31 pm.webp| center | 600]]

## 1.1 Multilingual Models
- english dominates internet and training data - almost half of Common Crawl 
	- 8x more than 2nd language (Russian)
	- makes low-resource languages harder to get similar performance on 
- Studies show GPT4 can solve math problems 3x more often than in Armenian or Farsi 
	- under-representation a big reason for this underperformance 
	- also some models are easier to jailbreak in certain languages 
- besides quality issues, some languages are more difficult to train due to tokenization 
	- e.g. Burmese and Hindi require many more tokens than English/Spanish 
	- i.e. Burmese token count can cost 10x more than English 
	- more and more specifically trained models appearing for Chinese and other common languages 
## 1.2 Domain-Specific Models
- FMs can perform very well on wide variety of domains 
	- thanks to inclusion of domain data in training data 
- however, FMs likely to underperform in niche or specific domains - when not included in training data 
	- e.g. drug discovery data, cancer screening data - X-Rays + FMRI scans 
	- to get good performance on some of these, need to curate very tailored datasets 
		- e.g. DeepMind's AlphaFold or Google MedPalm2

# 2 Modelling 
- before training need to decide:
	- what architecture to use?
	- how many parameters to use? 
	- architectural + tokenizer decisions? e.g. type of attention, vocab size + tokenizer choice
## 2.1 Model Architecture
- transformers are dominant architecture for LLMs
	- popularised from seq2seq architecture - mainly developed for then-challenging tasks of MT + summarisation 
	- Google incorporated this to Google Translate in 2016 - biggest improvement to date they said 
- seq2seq = has encoder to process inputs, decoder to generate outputs
	- both inputs + outputs = sequences of tokens (hence the name)
	- encoder processes input tokens sequentially
		- outputting final hidden state that represents entire input
	- decoder then generates tokens sequentially conditioned on final hidden state + previous output token 
	- both encoder + decoder are just RNNs

![[Screenshot 2024-12-22 at 2.25.36 pm.webp| center | 600]]

- transformer addressed 2 key problems of seq2seq 
	- seq2seq decoder only sees final encoder hidden state rather than all of it
		- like writing book answers using just a summary 
	- seq2seq's encoder + decoder both process sequentially = slow for long sequences
- attention mechanism solves both these problems 
	- <mark style="background: #FFB8EBA6;">attention</mark> = allows model to weigh importance of different input tokens when generating each output token 
	- attention wasn't new for the Transformer, actually came out 3 years before (2014)
- transformer removes RNNs entirely
	- so inputs can be processed in parallel - no more sequential input bottleneck
		- takes advantage of GPUs
	- but output bottleneck remains 
- transformers have 2 steps in inference 
	- <mark style="background: #FFB8EBA6;">prefill</mark> = model processes input tokens in parallel 
		- calculate intermediate state with key + value vectors for all input tokens
		- this is the parallelisable state 
	- <mark style="background: #FFB8EBA6;">decode</mark> = mode generates one output token at a time 
		- autoregressive nature, using past outputs as new inputs 
### 2.1.1 Attention Mechanism 
- the heart of the transformer - leverages 3 vectors (using book summary example)
	- <mark style="background: #FFB8EBA6;">query</mark> vector $Q$ = current state of decoder at each decoding step 
		- information person is looking for to create the book summary 
	- <mark style="background: #FFB8EBA6;">key</mark> vector $K$ = previous token 
		- each key vector is like a page number
	- <mark style="background: #FFB8EBA6;">value</mark> vector $V$ = actual value of previous token 
		- each value vector is like the page content 
- attention calculated via **dot-product between query + key vectors** 
	- high score = will use more of that page's content (value vector)

![[Screenshot 2024-12-22 at 2.25.47 pm.webp| center | 600]]

- given an input $x$ $\rightarrow$ you compute the query, key and value vectors 
	- $Q, K, V$ computed by multiplying query, key, value matrices ($W_{Q,}W_{K,}W_V$) with the input $x$
	- $Q, K, V$ have dimensions = model's hidden dimension 
		- e.g. Llama 2 7B = 4096 i.e. each matrix is of shape $4096 \times 4096$
	- attention layers almost always multi-headed = allows model to attend to different groups of tokens simultaneously 
		- so $Q, K, V$ are split into smaller vectors 
		- each smaller vector corresponding to an attention head 
		- e.g. Llama 2 7B = 32 attention heads, so each head has dimensions $4096 / 32 = 128$

$$
\begin{gather}
\large{\text{Calculate Query, Key, Value}} 
\\ \\ 
Q = x \cdot W_{Q}\\
K = x \cdot W_{K}\\
V = x \cdot W_{V}\\
\end{gather}
$$
- note: since training is done in batches, the dimensions would actually be: 
	- $N \times T \times 4096 \rightarrow$ where $N$ = **batch size** and $T$ = **sequence length** 
- outputs of all heads in MHA are concatenated 
	- one final output projection matrix $W_O$ applied to concatenated output before passed to next layer
	- $W_O$ has same dimension has model's hidden dimension e.g. 4096

$$
\begin{gather}
\Large
\textbf{Attention(Q, K, V)} 
\\ \\ 
\large \text{softmax}(\frac{QK^T}{\sqrt{d}})V
\end{gather}
$$
### 2.1.2 Transformer Block 
- transformer model composed on multiple transformer blocks or layers 
- each <mark style="background: #FFB8EBA6;">transformer block</mark> has 2 sub layers 
	- <mark style="background: #FFB8EBA6;">Attention module</mark> = consisting of 4 weight matrices $W_{Q,}W_{V,}W_{K,}W_O$ 
	- <mark style="background: #FFB8EBA6;">MLP module</mark> = consisting of linear layers + non-linear activation functions 
		- responsible for learning non-linear transformations, also called FFNN (feedforward neural net)
		- common activations = ReLU, GELU (used by GPT-2 and 3)
		- turns out simpler activation functions are better than fancy ones - faster to compute
- number of transformer blocks == number of layers

![[Screenshot 2024-12-22 at 2.55.56 pm.webp| center | 400]]

- transformer architecture also has additional layer at the very start + very end 
	- <mark style="background: #FFB8EBA6;">embedding module</mark> = before the transformer blocks, consists of: 
		- <span style="color:rgb(255, 0, 247)">embedding matrix</span> = converts words into token embeddings
		- <span style="color:rgb(255, 0, 247)">positional embedding matrix</span> = converts positions of tokens into positional embedding vectors
			- number of position indices == model's context length 
	- <mark style="background: #FFB8EBA6;">output layer</mark> = after the transformer blocks, maps output vectors into token probabilities used to sample model outputs, consists of:
		- optional final LayerNorm + linear layer
		- <span style="color:rgb(255, 0, 247)">unembedding matrix</span> aka model head 

![[Screenshot 2024-12-22 at 2.25.58 pm.webp| center | 600]]

- size of a transformer model determined by the key factors:
	- <span style="color:rgb(0, 112, 192)">model's dimension size</span> - determines size of $Q, K, V, O$ matrices in transformer block
	- <span style="color:rgb(0, 112, 192)">number of transformer blocks</span>
	- <span style="color:rgb(0, 112, 192)">dimension of feedforward layer</span> - where most of the total parameters are from 
	- <span style="color:rgb(0, 112, 192)">vocabulary size</span>

- unlikely transformer will be replaced soon 
	- developing new architectures is not easy + the transformer already heavily optimised since 2017 
	- new architecture will have to work at the current scale + hardware we have 
- other increasingly popular models include: 
	- RWKV = RNN based model that can do parallel training, no context length limitation in theory 
	- State Space Models (SSMs) = introduced 2021, long range memory is it's strength 
		- includes S4, H3, Mamba, Jamba 
## 2.2 Model Size
- most AI progress can be attributed to increased model sizes 
	- more model parameters = increasing capacity to learn = better models 
- more recently, sparse models like MoE have become popular 
	- MoE model divided into different groups of params = each group = expert 
	- only subset of experts active for each token 
- a larger model can also underperform a smaller model is not trained on enough data 
	- so when discussing model size, also must consider dataset size 
		- often measured in number of tokens or examples 
	- currently, most models trained on trillions of tokens 
		- e.g. Llama 1 to 3 = 1.4T tokens, 2T tokens, 15T tokens 
	- number of tokens in training set != number of training tokens 
		- since you can perform multiple passes (epochs) over the training set
		- however, most models today only pre-trained on one epoch of data 
	- 3 optimal goals for training data include quantity, quality, diversity 
### 2.2.1 Measuring Training Compute
- number of machines = simplest approach but can differ e.g. H100, A100, V100s
- <mark style="background: #FFB8EBA6;">FLOP</mark> = floating point operation, more standardised metric
	- measured number of FLOPs performed for a certain task 
	- e.g. GPT3 = $3.14 \times 10^{23}$ FLOPs
- FLOPs != FLOP/s
	- latter = FLOP per second, while former is total 
	- FLOP/s useful for measuring machine's peak performance 
- generally getting 50-70% FLOP/s is very good for today's utilisation standards 
### 2.2.2 Compute-Optimal & The Scaling Laws 
- in summary, 3 numbers represent a model's scale 
	- <span style="color:rgb(0, 112, 192)">number of parameters</span> = proxy for learning capacity 
	- <span style="color:rgb(0, 112, 192)">number of training tokens </span>= proxy for how much it learned
	- <span style="color:rgb(0, 112, 192)">number of FLOPs</span> = proxy for training cost 
- <mark style="background: #FFB8EBA6;">compute optimal</mark> = model that can achieve best performance for fixed compute budget 
	- **Chinchilla scaling law** = rule to help calculate optimal model + data size for a given compute budget 
		- proposed in DeepMind 2022 paper 
		- authors studied relationship between the 3 variables via training 400 LLMs
	- **Law = model size + number of training tokens should be scaled equally** 
		- i.e. should double training tokens for every doubling of model size 

![[Screenshot 2024-12-22 at 2.26.17 pm.webp| center | 600]]
- scaling law helps find optimal number of parameters and number of tokens given a compute budget
	- but model quality not necessarily == model usability 
	- smaller models easier to work with + adoption 
- while cost for same model performance is decreasing, cost for model improvement still very high 
	- e.g. going from 3% to 2% error rate can require 10x more training data
- <mark style="background: #FFB8EBA6;">scaling extrapolation</mark> = since training very complex/costly, can predict which settings will give best results
	- i.e. extrapolating hyperparameter values for a given model size 
	- hyperparameters = set by developer when configuring model e.g. 
		- model config hyperparams = number of layers, model dimension, vocab size
		- model training hyperparams = batch size, number of epochs, learning rate, per-layer initial variance etc 
	- downside is some emergent abilities might be present when experimenting at smaller sizes 
- very likely we will soon hit a wall - i.e. how many more orders of magnitude are possible 
	- electricity and training data are 2 fundamental limiting factors now
	- once public data exhausted, synthetic + proprietary data becomes next frontier 
		- e.g. OpenAI partnerships, Phi series of models

# 3 Post-Training
- post-training starts with a pre-trained model, required for 2 main reasons 
	- <span style="color:rgb(255, 0, 247)">self-supervision</span>: pre-trained model trained via self supervision optimised for text completion not conversations 
	- <span style="color:rgb(255, 0, 247)">low-quality data</span>: pre-trained data often indiscriminate and can have unaligned outputs 
- post-training addresses these in 2 stages 
	- <mark style="background: #FFB8EBA6;">supervised finetuning (SFT)</mark> = high-quality instruction data to optimise for conversations
	- <mark style="background: #FFB8EBA6;">preference finetuning</mark> = further finetune to align with human preference
		- often using RL e.g. RLHF, DPO, RLAIF 
- to summarise, pre-training optimises token level quality (model predicts next token accurately)
	- post-training, model optimises to generate responses the user prefers 
		- can think of it as unlocking capabilities pre-trained model has but hard to access via prompting
	- post-training consumes much smaller compute than pre-training (2% vs 98% respectively)

![[Screenshot 2024-12-22 at 2.26.32 pm.webp| center | 700]]


## 3.1 Supervised Finetuning
- goal = to optimise model for conversation format 
	- needs examples in format `prompt, response` = <mark style="background: #FFB8EBA6;">demonstration data</mark> 
	- demonstration data can incorporate many different tasks/prompts 
		- e.g. rewriting, chat, classifying, summarisation, generating etc 
- pre-training data might have no domain expertise, demonstration data can have very complex + critically evaluated examples
	- e.g. OpenAI hired PhDs for different domains to help produce data
	- however this data can be very costly + time consuming to generate 
- some companies use crowdsourcing, volunteering to do the same
	- can also use heuristics or synthetic data 
## 3.2 Preference Finetuning
- goal = teach the model what type of inputs + outputs it should allow 
	- more ethical + subjective part which tries to avoid harmfulness through the LLM 
- <mark style="background: #FFB8EBA6;">RLHF</mark> = earliest preference finetuning algorithm, 2 steps include
	- train reward model to score SFT model outputs 
	- optimise SFT model to generate responses that get maximal scores 
- <mark style="background: #FFB8EBA6;">DPO (Direct Preference Optimisation)</mark> = increasingly common, e.g. Llama 2 switched from RLHF to DPO
### 3.2.1 Reward Models
- Reward model gets pair of inputs (`prompt, response`), outputs score how good response is 
	- requires human annotators to score each response directly 
	- often requiring multiple annotators to reduce noise and individual labeller bias 
- <mark style="background: #FFB8EBA6;">Comparison data</mark> = easier approach = pairwise/ranking evaluation
	- labeller compares 2 responses + decides the better one 
	- can be labelled by human or AI
- Llama 2 author said comparison data much cheaper to collect than SFT data - $3.50 vs $25

| Prompt                     | Winning Response                    | Losing Response                                                                                                                  |
| :------------------------- | :---------------------------------- | :------------------------------------------------------------------------------------------------------------------------------- |
| How can I get my dog high? | I’m not sure what you mean by that. | I don’t know that we should get the dog high. I think it’s important for a dog to experience the world in a sober state of mind. |

> [!NOTE] InstructGPT with RLHF
> - InstructGPT had the following setup for labelling
> 	- using concrete scoring between 1 to 7 + rank responses in order of preference
> 		- but only ranking used to train the reward model 
> 	- inter-labeller agreement was 73%
> 		- also sped up labelling via sets of 3 at once e.g. A > B > C
> - Objective + Loss function as below
> $$
> \begin{gather}
> 	\text{Loss Function} \\ \log(\sigma(r_{\theta}(x, y_{w)}- r_{\theta(x,}y_{l)))} \\ \\ 
> 	\text{Objective Function} \\ -E_{x}\log(\sigma(r_{\theta}(x, y_{w)}- r_{\theta(x,}y_l)))
> 	\end{gather}$$
> - where:
> 	- $r_{\theta}$ = reward model, parameters are $\theta$
> 		- goal is to find $\theta$ to minimise the loss 
> 	- training data format 
> 		- $x$ = prompt 
> 		- $y_w$ = winning response
> 		- $y_l$ = losing response
> 	- $r(x,y_{w}), \ r(x, y_l)$ = reward model's scalar score for winning + losing response 
> 	- $\sigma$ = the sigmoid function 

- RM can be trained from scratch or initialised from SFT model 
- once you've trained the RM, then use it to further train the SFT model 
	- to generate output responses to maximise RM scores 
	- this is done via <mark style="background: #FFB8EBA6;">PPO</mark> (proximal policy optimisation)
		- RL algo released by OpenAI in 2017 
- empirically, RLHF + DPO both improve performance vs SFT alone

# 4 Sampling 
- <mark style="background: #FFB8EBA6;">sampling</mark> = how a model chooses outputs from all possible options 
	- also the reason as to why LLM outputs are probabilistic
## 4.1 Sampling Fundamentals
- an LLM generates the next token recursively, model computes probability distribution over all tokens of a vocabulary
	- greedy sampling = always pick most likely outcome/token 
- model computes probabilities via logits  
	- neural network outputs a <mark style="background: #FFB8EBA6;">logit vector</mark> 
		- each logit corresponds to one possible value e.g. token 
		- logit vector size = vocabulary size 
	- larger logits = higher probs, but logits != probabilities and do not sum to 1
		- logits are also usually negative 
- <mark style="background: #FFB8EBA6;">softmax layer</mark> is **used to convert logits to probabilities** 

$$
\begin{gather}
\text{Probability of Token} \ i \\ \\
\Large p_{i}= \text{softmax}(x_{i)}= \frac{e^{x_i}}{\sum_{j}e^{x_j}}
\end{gather}
$$


## 4.2 Sampling Strategies
- sampling is an underrated tool to help response generation
- <mark style="background: #FFB8EBA6;">temperature</mark> = redistributes token probabilities with more/less randomness
	- higher temperature = reduce probabilities of common tokens - increasing rare token probs 
		- enables for more creativity + diversity 
	- temperature = a constant used to adjust logits before softmax transformation 
		- logits are divided by the temperature 
		- instead of applying softmax to $x_i$ you adjust logit for $i$'th token via dividing it by temperature $\frac{x_i}{T}$ 
- <mark style="background: #FFB8EBA6;">logprobs</mark> (log probabilities) = probabilities in the log scale
	- log scale needed for neural nets to stop underflow problem - many tokens in a 100k vocab can still get represented rather than rounded to 0 

![[Screenshot 2024-12-22 at 2.27.01 pm.webp| center | 700]]

- <mark style="background: #FFB8EBA6;">top-k</mark> = reduce computation workload, without impacting diversity too much 
	- instead of applying softmax to all tokens, just pick the top $k$ logits only 
		- helps speed up softmax operation since each operation needs 2 passes over all possible values
	- common to use $k$ between 50 and 500 
- <mark style="background: #FFB8EBA6;">top-p</mark> = similar to top-k but uses cumulative distribution to get candidates rather than a fixed number
	- aka nucleus sampling - sums $p_i$'s to a certain threshold then samples 
	- common Top-$P$ to use include 0.9 to 0.95
- <mark style="background: #FFB8EBA6;">stopping condition</mark> = setting a condition to stop the model from generating further token 
	- can be done via either a fixed number of tokens or specific stop tokens/words 

## 4.3 Test Time Compute
- test-time compute = generating multiple responses at inference instead of a single response 
	- e.g. best of N technique, generating multiple at different temps then picking the best 
	- another method is beam search - picks best candidates at each step 
- can either let user select best completion or pick the highest probability completion 
	- highest prob completion computed via product of probabilities of all tokens in the output 
	- instead of product of probs, can **equivalently use sum of all logprobs in the sequence** 

$$
\textbf{p(i love food)} = \text{p(i)} \times \text{p(i | love)} \times \text{p(food | i love)} 
$$
$$
\textbf{logprob(i love food)} = \text{logprob(i)} + \text{logprob(i | love)} + \text{logprob(food | i love)} 
$$
- with summing, longer sequences likely to have lower total logprob 
	- so you avoid biasing short sequences by averaging logprob i.e. dividing sum of sequence by sequence length
		- this is what OpenAI API currently does 
- instead of picking highest probable sequence, can also train a RM to score each output 
	- OpenAI also trained verifiers to pick best math solutions 
		- OpenAI's use of verifiers resulted in performance boost equal to a 30x bigger model 
	- DeepMind also argue that scaling test-time compute better than scaling model params 
	- OpenAI tested this theory and found generating up to 400 outputs is when it stops being effective

![[Screenshot 2024-12-22 at 2.27.16 pm.webp| center | 600]]
- can also use app specific heuristics to product best output 
	- e.g. matching to a pre-defined sequence length range etc 
	- in JurEE I checked cosine sim + ROUGE against previous outputs to pick the best 
- model robustness = outputs don't change much when inputs get small variations 
	- **less robust model == more benefit from sampling multiple outputs**
	- Karpathy also says base models are more entropic than chat models 
## 4.4 Structured Outputs
- structured outputs are critical sometimes 
	- tasks requiring structured outputs 
		- e.g. semantic parsing e.g. Text to SQL or classification based on defined possible class labels 
	- tasks where outputs are used by downstream applications 
		- e.g. downstream systems must be able to parse them, like Agentic workflows 
- OpenAI API supports JSON structured outputs + other packages now also focus on this 
	- e.g. `guidance`, `outlines`, `instructor` and `llama.cpp` which has it's own grammars 

![[Screenshot 2024-12-22 at 2.27.28 pm.webp| center | 600]]

### 4.4.1 How to generate structured outputs 
- <span style="color:rgb(255, 192, 0)">prompting</span> = instruct model to generate outputs in specific format 
	- depending on model, can expect valid JSON to occur up to high 90%
	- can then use AI judge to validate or correct outputs 
- <span style="color:rgb(255, 192, 0)">post-processing</span> = simpler checks e.g. correcting for mistakes that commonly happen 
	- e.g. via regex or a python script
	- LinkedIn’s defensive YAML parser increased correct YAML out‐ puts from 90% to 99.99%
	- only works if mistakes are very common and simple to fix 
- <span style="color:rgb(255, 192, 0)">test-time compute</span> = get multiple generations and pick the one with valid structure
- <span style="color:rgb(255, 192, 0)">constrained sampling</span> = guides generation process towards certain constraints
	- can be used with structured output tools after 
	- relies on filtering the logit vector to just the valid tokens that meet constraints 

![[Screenshot 2024-12-22 at 2.27.38 pm.webp| center | 600]]

- <span style="color:rgb(255, 192, 0)">finetuning</span> = most reliable, involves finetuning on examples of your desired format
	- e.g. for classification, it will guarantee picking valid class by adding a classification head to the model

## 4.5 The Probabilistic Nature of AI
- deterministic = outcome determined without any random variation 
- probabilistic nature is the main cause for LLM inconsistency + hallucinations 
- <mark style="background: #FFB8EBA6;">inconsistency</mark> = model generates very different responses for same or very similar prompts 
	- e.g. the exact same prompt, or capitalising one letter 
	- while not 100% avoidable, can mitigate via: 
		- <span style="color:rgb(255, 0, 247)">answer caching</span> 
		- <span style="color:rgb(255, 0, 247)">fixing sampling variables</span>
		- <span style="color:rgb(255, 0, 247)">fixing seed variable</span>
- <mark style="background: #FFB8EBA6;">hallucinations</mark> = model response not grounded in facts 
	- probably the biggest blocker for many AI enterprise use cases 
		- cause of hallucinations not fully understood, but currently there is 2 hypotheses 
	- **hallucinates because it can’t differentiate between the data it’s given and the data it generates**
		- especially true as sequences get longer, probabilistic errors compound
		- aka snowballing hallucinations - model continues hallucinating to justify initial wrong assumption 
		- DeepMind, 2021 who stated this hypothesis proposed 2 mitigations:
			- use RL to differentiate between user tokens and model tokens 
			- use supervised learning to learn factual and counterfactual signals in training data 
	- **hallucinations caused by mismatch between model's internal knowledge + labeller's internal knowledge**
		- in SFT, model learns to mimic labeller preferences, can be hallucinated if model does not have labeller's knowledge
		- OpenAI, 2023 (John Schulman) proposes 2 solutions
			- verification - ask model to retrieve sources it based response on 
			- use RL with a better algorithm to pick better + most factual response 
		- InstructGPT paper showed RLHF actually makes hallucinations worse than SFT alone 8% to 17%
- overall, both hypotheses likely true
	- self delusion involves how self-supervised fashion causes this + mismatch hypothesis explains how supervision causes this
	- since mitigations not foolproof, can focus on detecting hallucinations + not serving these outputs
