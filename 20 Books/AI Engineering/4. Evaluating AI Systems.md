# 1 Evaluation Criteria 
- robust + well-guided evals, those with clear eval criteria are best candidates
	- likewise, those without = biggest bottleneck to adoption
- most successful applications informed by sensible business ROI, not hype
	- need to demonstrate actual deployment value, examples include:
		- recommender systems - evaluated via engagement + purchase through rates
		- fraud detection - measured by prevented $ 
		- coding - measured by functional correctness/acceptance 
	- much easier to eval close-ended classification than open ended
		- close-ended also easier to verify + reproduce
- <mark style="background: #FFB8EBA6;">evaluation-driven development</mark>: best practice = defining evaluation criteria before building
- 4 general buckets to eval criteria
	1. <span style="color:rgb(255, 136, 0)">domain-specific capability</span> = how good the model understands your specific task/domain
	2. <span style="color:rgb(255, 136, 0)">generation capability </span> = how coherent, faithful etc it is
	3. <span style="color:rgb(255, 136, 0)">instruction-following capability</span> = whether it meets required constraints + format
	4. <span style="color:rgb(255, 136, 0)">cost and latency</span> = how much it will cost + how long it will take
## 1.1 Domain-specific Capability
- domain-specific capabilities determined by configuration + training data 
	- i.e. model architecture/size + how exposed was your domain in training
- to eval this - use domain-specific benchmarks (public or private)
	- most common to eval with exact evaluation coupled with subjective evals
	- many benchmarks use multiple choice approach 
		- e.g. 75% tasks in EleutherAI Eval Harness are MC
		- authors suggested they excluded open-ended to avoid inconsistent assessment 
### 1.1.1 Multiple-Choice Format
- multiple choice questions (MCQ) can have multiple right answers
	- <mark style="background: #FFB8EBA6;">accuracy</mark> = how many total questions answered correctly
		- can also use point system for multiple correct options e.g. 1 point for each
- classification in MCQs can be used where options are same for every question 
	- e.g. NEGATIVE or POSITIVE or NEUTRAL as the classes
	- metrics include F1 Score, Precision, Recall
$$
\begin{gather}
\text{Precision} = \frac{\mathrm{TP}}{\mathrm{TP} + \mathrm{FP}} \\ \ \\
\text{Recall} = \frac{\mathrm{TP}}{\mathrm{TP} + \mathrm{FN}} \\ \ \\
F_1 = 2 \cdot \frac{\text{Precision} \times \text{Recall}}{\text{Precision} + \text{Recall}} 
\end{gather}
$$
- drawback of MCQ = performance can vary with small changes in input formats 
	- e.g. very sensitive to the prompts for questions 
- MCQ best suited for evaluating internal model knowledge + reasoning 
	- not ideal for generation capabilities e.g. writing or summarising 
## 1.2 Generation Capability 
- metrics from long-standing field of NLG including translation, summarisation have been relied on
	- e.g. faithfulness + relevance been repurposed for use with LLMs
	- other metrics newly introduced e.g. dealing with hallucinations - factual consistency 
	- others include safety e.g. bias + toxicity
### 1.2.1 Factual Consistency 
- due to how crucial impact of hallucinations are - many have tried to detect + measure
	- most critical for RAG systems where generated responses need to be consistent to retrieved context 
- 2 types of factual consistency 
	- <mark style="background: #FFB86CA6;">local factual consistency</mark> = output evaluated against a context 
		- output = factually consistent if supported by given context 
		- very important for tasks w limited scope e.g. summarisation + customer support chatbots
		- aka Lillian Weng calls this extrinsic hallucinations
	- <mark style="background: #FFB86CA6;">global factual consistency</mark> = output evaluated against open knowledge 
		- important for tasks with broad scopes e.g. general chatbots, fact checkers, market research etc 
		- aka Lillian Weng calls this intrinsic hallucinations
- factual consistency much easier to verify against explicit facts 
	- hardest part = determining what the facts are
		- e.g. getting reliable sources, deriving the facts, then validating against them 
- most straightforward eval approach = LLM-as-Judge
	- LLM can be asked to compare 2 texts and ask if they are factually consistent 
	- e.g. TruthfulQA LLM-Judge, 2022 used below prompt to get 90-96% accuracy

>[!info] TruthfulQA LLM-Judge Prompt
> ```jinja2
> Factual Consistency: Does the summary untruthful or misleading facts that are not supported by the source text?
> 
> Source Text:
> {{Document}}
> 
> Summary:
> {{Summary}}
> 
> Does the summary contain factual inconsistency?
> Answer:
> ```

- more sophisticated LLM-Judge approaches include:
	- <mark style="background: #FFB8EBA6;">Self-Verification</mark> = SelfCheckGPT, 2023 relies on assumption that generating multiple outputs to same question will give same answers if factually consistency 
		- some call this answer consistency e.g. if multiple outputs disagree, more likely to be hallucinated
		- generates $N$ responses to 1 query and compares them to each other
	- <mark style="background: #FFB8EBA6;">Knowledge Augmented Verification</mark> = SAFE by Google DeepMind, 2024 used search engine to verify responses
		- decomposed model outputs into atomic statements + revised to ensure each is self-contained
		- then sent to Google Search + used LLM-judge to determine factuality 
- other methods include textual entailment models or specialised scorers
	- <mark style="background: #FFB8EBA6;">entailment models</mark> usually use the classes as below:
		- entailment = hypothesis inferred from premise aka factually consistent
		- contradiction = hypothesis contradicts premise aka factually inconsistent
		- neutral = premise neither entails nor contradicts the premise
	- <mark style="background: #FFB8EBA6;">specialised scorers</mark> can be trained to do similar
- important to analyse model outputs to see which types of queries most likely to hallucinate on 
	- then get internal benchmark to focus on these queries 
	- e.g. queries that involve niche knowledge or queries for things that don't exist 
### 1.2.2 Safety - Bias & Toxicity 
- multiple safety criteria to evaluate + multiple ways to categorise harms 
	- e.g. Meta, OpenAI, NVIDIA all use different categorisation methods 
	- in general: inappropriate language, harmful recommendations, hate speech (racist, sexist, homophobic, discriminatory), violence, stereotypes, biases towards minorities or certain groups 
- since such behaviours have been problematic for online platforms for last decade, specialised models are common 
	- specialised models much faster, smaller + cheaper than LLM-Judges
- common benchmarks include:
	- <span style="color:rgb(255, 136, 0)">RealToxicityPrompts</span> = 100k naturally occurring prompts likely to give toxic outputs
	- <span style="color:rgb(255, 136, 0)">BOLD</span> 
## 1.3 Instruction-Following Capability 
- essential for tasks requiring structured outputs 
	- generally, larger more powerful models better at such tasks 
	- however not easy to define or measure, can be confused with domain + generation capabilities 
- 2 important benchmarks
	- <span style="color:rgb(255, 136, 0)">IFEval</span> = from Google (Instruction-Following Evaluation) checks if model can produce outputs to follow expected formats
		- testing 25 types of instructions that can be automatically verified 
		- e.g. JSON format, keyword inclusion, length constraints
	- <span style="color:rgb(255, 136, 0)">INFOBench</span> = by Qin et al. 2024, much broader view, also evals ability to follow content constraints, linguistic guidelines + style rules
		- however, harder to automatically verify, authors constructed list of criteria using yes/no format to ease this
		- e.g. "*Is the generated text a questionnaire?*", "*Is the generated questionnaire for hotel guests?*" etc

## 1.4 Cost and Latency
- important to balance model quality with cost and latency
	- efficiency often a priority - evaluated via runtime/memory usage 
	- <mark style="background: #FFB8EBA6;">Pareto optimisation</mark> = field of study for optimising for multiple objectives
		- must be clear on which of the objectives you can or cannot comprise on 
- importantly to consider which type of latency matters for your application - multiple metrics of interest: 
	- <span style="color:rgb(255, 136, 0)">time to first token</span> 
	- <span style="color:rgb(255, 136, 0)">time per token</span> 
	- <span style="color:rgb(255, 136, 0)">time between tokens</span> 
	- <span style="color:rgb(255, 136, 0)">time per query</span> 
- latency depends on both model + prompt used + sampling variables 
	- note: API models don't change much with cost-per-token as you scale
	- but local models get much cheaper as you scale
## 1.5 Example Eval Criteria
- an example of criteria you can use for your application
	- note: some have hard requirements, and ideal i.e. nice-to-have

| Criteria                   | Metric                     | Benchmark                      | Hard requirement     | Ideal                |
| -------------------------- | -------------------------- | ------------------------------ | -------------------- | -------------------- |
| **Cost**                       | Cost per output token      | X                              | < $30.00 / 1M tokens | < $15.00 / 1M tokens |
| **Scale**                      | TPM (tokens per minute)    | X                              | > 1M TPM             | > 1M TPM             |
| **Latency**                    | Time to first token (P90)  | Internal user prompt dataset   | < 200ms              | < 100ms              |
| **Latency**                    | Time per total query (P90) | Internal user prompt dataset   | < 1m                 | < 30s                |
| **Overall model quality**      | Elo score                  | Chatbot Arena’s ranking        | > 1200               | > 1250               |
| **Code generation capability** | pass@1                     | HumanEval                      | > 90%                | > 95%                |
| **Factual consistency**        | Internal GPT metric        | Internal hallucination dataset | > 0.8                | > 0.9                |

# 2 Model Selection 
## 2.1 Model Selection Workflow 
- when considering which model is best *for your application*, selection process should begin with:
	- figure out best achievable performance
	- map models along cost-performance axes and choose best on frontier 
- importantly, differentiate between hard and soft attributes
	- <span style="color:rgb(255, 136, 0)">hard attributes</span> = model provider restrictions or internal policy restrictions
		- e.g. privacy, control, licenses, training data, model size 
	- <span style="color:rgb(255, 136, 0)">soft attributes</span> = things that can be improved
		- e.g. robustness, toxicity, accuracy etc via prompt engineering, finetuning etc 
		- e.g. ease of use with standard API, availability, community support 
- 4 step workflow to selecting a model 
	1. filter out models that don’t meet hard requirements e.g. cost, privacy etc
	2. use public benchmarks + info to narrow set of candidate models
	3. run your own evals with task-specific prompts + metrics for your use-case
	4. continually monitor in prod - detect failures, collect feedback to improve

## 2.2 Build vs Buy 
- understanding model licenses + Open vs Closed is necessary 
	- open models generally more flexible model usage including modifications to model, training etc 
	- closed models usually very restricted + limit what outputs can be gotten e.g. logprobs 
- questions to consider for evaluating the license of a model
	- allow for commercial use? 
	- restrictions for commercial use?
	- allow for model outputs to train or improve other models? e.g. synthetic data 
- 7 aspects to consider for public vs closed model
	- data privacy 
		- external APIs not feasible for companies with strict data policies e.g. sending data outside borders/cloud
		- risks that API providers trains models on your data, memorisation risk 
	- data lineage 
		- little transparency on what data a model was trained on 
		- still unclear on copyright concerns on model outputs due to training data grey area 
		- using commercial model providers can potentially protect you from these risks 
	- performance 
		- open vs closed source gap closing 
			- if you need strongest model currently, opt for closed source to start 
		- commercial models also have more support + community e.g. OpenAI API
	- functionality 
		- some functionalities you will likely need:
			- scalability - can inference support traffic + be sufficient in latency/cost 
			- function calling - model can use external tools e.g. RAG + agentic systems
			- structured outputs - asking models for JSON outputs
			- output guardrails - mitigating output response risks
		- API providers often provide these out of the box 
	- costs + control
		- APIs charge per usage - get very expensive as you scale 
			- also dependent on their SLAs, rate limits, usage terms 
			- however easier to get started with
		- flip side: hosting a model locally requires nontrivial time, talent + engineering chops 
			- easier to customise + manipulate over time 
			- able to host on-device, cannot with external APIs
		- regardless, you want models with standard API + good community support 

| **Category**                        | **Using model APIs**                                                                                                                              | **Self-hosting models**                                                                                                                                                   |
|------------------------------------|---------------------------------------------------------------------------------------------------------------------------------------------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| **Data**                            | ⛔️ *Have to send your data to model providers, which means your team can accidentally leak confidential info*                                    | ✅ Don’t have to send your data externally <br> ⛔️ *Fewer checks and balances for data lineage/training data copyright*                                                                                         |
| **Performance**                     | ✅ Best-performing model will likely be closed source                                                                                             | ⛔️ *The best open source models will likely be a bit behind commercial models*                                                                                                                                  |
| **Functionality**                   | ✅ More likely to support scaling, function calling, structured outputs <br> ⛔️ *Less likely to expose logprobs*                                  | ⛔️ *No/limited support for function calling and structured outputs* <br> ✅ Can access logprobs and intermediate outputs, which are helpful for classification tasks, evaluation, and interpretability          |
| **Cost**                            | ✅ API cost                                                                                                                                       | ✅ Talent, time, engineering effort to optimize, host, maintain (can be mitigated by using model hosting services)                                                                                               |
| **Finetuning**                      | ⛔️ *Can only finetune models that model providers let you*                                                                                        | ✅ Can finetune, quantize, and optimize models (if their licenses allow) <br> ⛔️ *but it can be hard to do so*                                                                                                    |
| **Control, access, and transparency** | ⛔️ *Rate limits* <br> ⛔️ *Risk of losing access to the model* <br> ⛔️ *Lack of transparency in model changes and versioning*                     | ✅ Easier to inspect changes in open source models <br> ✅ You can freeze a model to maintain its access <br> ⛔️ *but you’re responsible for building and maintaining model APIs*                                  |
| **Edge use cases**                 | ⛔️ *Can’t run on device without internet access*                                                                                                  | ✅ Can run on device <br> ⛔️ *but again, might be hard to do so*                                                                                                                                                 |

## 2.3 Navigating Public Benchmarks
- benchmark results can help identify promising models for your use-cases 
	- aggregating from a variety of benchmarks and ranking them can give you a candidate leaderboard too
	- consider which benchmarks you should include + how to aggregate/weigh the results 
	- **goal = select small subset of models to do more in-house rigorous testing**
- public benchmarks - lots of benchmarks being released + scored regularly 
	- **impossible to look at all, just categorise and choose most useful/closest to your use-case**
		- often have different coverage e.g. broad or narrow domains 
		- be aware of what capabilities each is trying to capture
	- e.g. EleutherAI supports 431, Google BIG-Bench supports 214
- Common benchmarks include
	- <span style="color:rgb(255, 136, 0)">ARC-C (2018)</span> → complex grade-school science questions
	- <span style="color:rgb(255, 136, 0)">MMLU (2020)</span> → knowledge + reasoning in 57 subjects e.g. math, US history, computer science, law
	- <span style="color:rgb(255, 136, 0)">HellaSwag (2019)</span> → completion of sentences in stories or videos, common sense and everyday understanding
	- <span style="color:rgb(255, 136, 0)">TruthfulQA (2021)</span> → accurate but also truthful + not misleading i.e. factual accuracy
	- <span style="color:rgb(255, 136, 0)">WinoGrande (2019)</span> → challenging pronoun resolution
	- <span style="color:rgb(255, 136, 0)">GSM-8K (2021)</span> → diverse math problems from grade-school curriculum
- public leaderboards can be very useful - aggregate multiple benchmarks + rank them
	- however be careful what they might leave out e.g. HF opted out of HumanEval due to compute needs 
		- HELM spent 80-100k on evaluating 30 models for full HEML suite
	- 🤗 updated their Open LLM Leaderboard in 2023 from 4 to 6 benchmarks
	- 🤗 again updated in June 2024, revamping entire set with more practical + difficulty 
		- replaced GSM-8K with <span style="color:rgb(255, 136, 0)">MATH lvl 5</span> - much harder
		- replaced MMLU with <span style="color:rgb(255, 136, 0)">MMLU-PRO</span>
		- added <span style="color:rgb(255, 136, 0)">GPQA</span>, <span style="color:rgb(255, 136, 0)">MuSR</span>, <span style="color:rgb(255, 136, 0)">BBH</span>, <span style="color:rgb(255, 136, 0)">IFEval</span>
	- HELM from Stanford is broader with 10 benchmarks 
	- 🤗 currently aggregate via averaging scores on all benchmarks to get final rank
		- i.e. every benchmark treated equally 
		- however HELM use mean win rate rather than average
		- mean win rate = % of times model obtains better score vs other model, averaged across scenarios
- importantly, consider <mark style="background: #FFB8EBA6;">benchmark correlation </mark>
	- when 2 benchmarks perfectly correlated, you don't want both since they can exaggerate biases
	- additionally, consider each benchmark likely has different eval metrics e.g. accuracy, F1, BLEU etc 
- <mark style="background: #FFB8EBA6;">data contamination</mark> = when model is trained on same data it is evaluated on 
	- aka <mark style="background: #FFB8EBA6;">data leakage</mark>, training on test set 
		- Schaeffer, 2023 showed small 1 Million param model can get perfect benchmark scores via memorising
		- OpenAI found GPT-3 had 40% of 13 benchmarks within their training data 
	- happens mostly unintentionally, but also intentionally since many benchmarks have good reasoning to bake into model params 
		- unintentional example = when you include math textbooks in training data but another benchmark creator uses some examples to create a new benchmark 
	- how to handle data contamination
		- <span style="color:rgb(255, 0, 247)">n-gram overlapping</span> = overlapping tokens between eval set + training data 
		- <span style="color:rgb(255, 0, 247)">perplexity</span> = unusually low on certain text indicates seen before
		- 🤗 plot standard deviations of model performance on given benchmarks to spot outliers

# 3 Evaluation Pipeline 

>[!tip]
> The success of an AI application often hinges on the ability to differentiate good out‐ comes from bad outcomes. 
> 
> To be able to do this, you need an evaluation pipeline that you can rely upon
## 3.1 Evaluate all Components in the System
- each application might have multiple components + tasks can use multiple steps
	- for this, evals can happen at multiple levels 
		- <span style="color:rgb(255, 136, 0)">per-task</span> - evals whether system completed a task
		- <span style="color:rgb(255, 136, 0)">per-turn</span> - can consist of multiple steps or messages, quality of each output
		- <span style="color:rgb(255, 136, 0)">per intermediate output </span> 
- optimally, evaluate end-to-end outputs + each component's intermediary outputs independently
	- useful indicator = how many turns taken to complete a task e.g. 2 vs 20 is a big difference
		- consider implicit indicators e.g. user asking variants or similar question again vs next stage question
	- task evals are harder since might be harder to determine boundaries between tasks 
## 3.2 Create an Evaluation Guideline 
- creating a clear evaluation guideline is the most important step of the evaluation pipeline
	- define what application SHOULD and SHOULD NOT do
### 3.2.1 Define your Eval Criteria
- most difficult part = defining what good means 
	- consider what makes a "*good*" response 
		- e.g. LinkedIn found a correct response not always a good response
		- e.g. LangChain 2023 State of AI Report found firms use on average 2.3 different metrics to eval
	- example of how to define good for a customer support bot
		- <span style="color:rgb(255, 136, 0)">relevance</span> = response is relevant to user's query
		- <span style="color:rgb(255, 136, 0)">factual consistency</span> = response is factually consistent with the context
		- <span style="color:rgb(255, 136, 0)">safety</span> = response is not toxic and within brand voice
> [!NOTE] Clear guidelines are the backbone of reliable evaluation pipelines + can be re-used for training data annotation
### 3.2.2 Create a scoring rubric + examples
- scoring system depends on your data + needs, options include:
	- binary e.g. 0 and 1
	- discrete numerical e.g. 1 to 5
- make sure to include examples i.e. what does a score of 1 actually mean
	- validate your rubric with expert humans + colleagues, try to aim for minimal ambiguity  
	- this process can be very iterative, so be patient 
### 3.2.3 Tie eval metrics to business metrics
- ideally, eval metrics should be considered in context of business problem trying to solve 
	- also consider usefulness threshold i.e. how much does it need to score to be actually useful?
	- anything below this threshold makes it unfeasible

> [!NOTE] Example of tying eval metrics to business metrics 
> - Factual Consistency of 80% = can automate 30% of customer support requests 
> - Factual Consistency of 90% = can automate 50%
> - Factual Consistency of 98% = can automate 90%
## 3.3 Define Evaluation Methods & Data 
### 3.3.1 Select Eval Methods
- likely will use different evaluation methods for different criteria
	- e.g. small specialised scorers for toxicity, LLM-Judge for groundedness
	- also can use multiple different methods for the same criteria 
		- e.g. cheap classifier for low-quality signal on all data
		- then higher quality LLM-judge for highest scoring 1% 
		- allows for some level of confidence while keeping costs manageable
	- if logprobs are available, use them! especially useful for classification tasks 
- use automated metrics as much as possible 
	- however also need good human evaluation even in prod 
	- having human experts manually eval model quality is a long-standing practice in AI 
		- e.g. each day, can get human experts to sample + eval outputs + detect any changes
- eval not just in development but also in production 
	- in prod, you have real users, consider what feedback you want from them 
	- and how their feedback correlates to other eval metrics + how to improve your app from these 
### 3.3.2 Annotate Eval Data
- curate a set of annotated examples to eval your application, ideally covers all: 
	- <span style="color:rgb(255, 136, 0)">end-to-end outputs</span>
	- <span style="color:rgb(255, 136, 0)">individual component outputs</span>
	- <span style="color:rgb(255, 136, 0)">across each criterion</span> 
	- <span style="color:rgb(255, 136, 0)">for both turned + task based evals</span> 
- also want to be able to filter/slice your data for more granular understanding of the system 
	- i.e. looking into subsets of the system's performance 
	- useful for following reasons:
		- avoiding potential biases e.g. minority user groups
		- debugging e.g. identifying cause like attributes of subset e.g. length, topic, format
		- finding areas for improvement e.g. add new techniques for subsets
		- avoiding Simpson's paradox e.g. Model A > Model B on aggregated data but worse on subsets 
- should have multiple eval sets to represent different data slices
	- main set to represent distribution of actual prod data = to estimate how well system does overall 
	- slice data based on traffic sources, usage, customer types etc 
		- another with common mistakes i.e. adversarial examples
		- another with high-value examples that are important to not get wrong
		- can also have frequent user error set (e.g. typos) and an out-of-scope eval set
	- **if you care about it, put a test set on it**
- how many examples to include?
	- "how big the test set should be is like asking how much money do you want?"
		- ideally, more the better 
		- generally, number should be large enough to give reliable result
			- but small enough to run efficiently 
	- can also test via bootstrap tests e.g. to test if 100 examples is sufficient, create multiple bootstraps of the 100 examples
		- e.g. start with 100 examples, check reliability by creating multiple bootstraps from here
		- draw 100 samples with replacement from original
		- evaluate model on bootstrapped set
		- **repeat process multiple times → if eval results vary significantly, more data is needed**
	- can also use statistical significance tests to compute sample size needed for certain level of confidence
		- useful if you know the score distribution 

> [!NOTE] Tips on Sample Size 
> - OpenAI suggested rule of thumb for calculating sample size based on result confidence needed
> 	- every 3x decrease in score difference, sample size should increase 10x
> 	- example table below from OpenAI
> - EleutherAI eval harness
> 	- median number of examples is 1000
> 	- average is 2159
> - Inverse Scaling Prize organisers suggested minimum is 300, preferable is 1000

### 3.3.3 Eval your Eval Pipeline
- some questions to consider re quality of your eval pipeline 
	- <span style="color:rgb(255, 136, 0)">is your eval pipeline giving you the right signals? </span>
		- do higher scores == better responses 
		- do higher scores == better business outcomes
	- <span style="color:rgb(255, 136, 0)">how reliable is your eval pipeline?</span>
		- should get same/very close results if pipeline run twice 
		- what is variance over runs? using consistent configuration 
		- make sure to control as much as possible e.g. judge prompt, seed, temperature
	- <span style="color:rgb(255, 136, 0)">how correlated are your metrics?</span>
		- 2 perfectly correlated metrics likely not helpful
		- 2 uncorrelated metrics likely can give you good insight or might need closer look into the eval
	- <span style="color:rgb(255, 136, 0)">how much cost + latency does eval pipeline add to the application? </span>
		- ensure you try to reduce this as much as practical, don't want eval to be hindrance for improvements
### 3.3.4 Iterate
- everything drifts! user behaviour, usage patterns, RAG data etc 
	- may need to update eval criteria, scoring rubric, add or remove examples 
- need consistency during iteration 
	- make sure to do proper experiment tracking 
	- log all variables that could change in an eval process
	- includes eval data, rubric, prompt, sampling configurations for LLM-judges


> [!NOTE] Final Tips
> - While evaluation takes time, a reliable evaluation pipeline will enable you to reduce risks, discover opportunities to improve performance, and benchmark progresses
> - It’s impossible to capture the ability of a high-dimensional system using one- or few-dimensional scores
> 	- Evaluating modern AI systems has many limitations and biases
> 	- However, this doesn’t mean we shouldn’t do it
> 	- Combining different methods and approaches can help mitigate many of these challenges
