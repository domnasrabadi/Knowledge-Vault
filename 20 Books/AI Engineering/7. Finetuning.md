# 1 Finetuning Overview 
- <mark style="background: #FFB8EBA6;">finetuning</mark> = adapting a model to a specific task by further training whole/part of model
	- adapts the model by adjusting the weights
	- can dramatically improve model's domain specific capabilities
- finetuning is very resource intensive + challenging
	- so one big research motivation is for reducing finetuning's memory requirements
		- focus of this chapter
	- e.g. PEFT, LORA, etc 
- finetuning begins with a base model that has some general capabilities
	- goal is to get good performance on your specific task 
	- LLMs particularly valuable due to their capability for transfer learning for such tasks 
		- OpenAI InstructGPT, 2022 suggested finetuning as unlocking capabilities model already has but difficult to access via prompting alone 
- **transfer learning improves sample efficiency** 
	- <mark style="background: #FFB8EBA6;">sample-efficiency</mark> = allowing model to learn same behaviour with fewer examples
		- reduces need for longer, example-heavy prompts
	- sample efficient models learn effectively from fewer samples
	- another common use-case is training for classification via adding a classification head to the LLM

>[!info] Often you will finetune an already post-trained model

## 1.1 Types of Finetuning
- <mark style="background: #FFB8EBA6;">continual pre-training</mark> = additionally training the model in a self-supervised fashion on your domain data
	- aka <span style="color:rgb(255, 0, 247)">self-supervised finetuning</span>
	- recall, LLMs are trained first via pre-training using self-supervision
		- self-supervision allows model to learn from large amounts of unlabelled data 
			- typically sequences of text that don't require annotation 
	- before finetuning pre-trained model with expensive task-specific data, can finetune it on raw documents for that task 
- <mark style="background: #FFB8EBA6;">infilling finetuning</mark> = similar to above, but using masked-language-modelling as your training objective
	- i.e. getting model to fill in masked tokens
	- aka supervised finetuning with MLM
- <mark style="background: #FFB8EBA6;">supervised finetuning</mark> = using high quality annotated data to refine the model + align to human preference
	- trained auto-regressively usually on `input, output` pairs
		- input can be an instruction
		- output can be a response e.g. summarisation or classification
	- typically requires high quality instruction data which can be challenging + expensive to curate
		- especially for tasks requiring factuality + domain expertise 
- <mark style="background: #FFB8EBA6;">preference finetuning</mark> = usually done with RL, to generate responses that maximise human preference
	- requires comparative data that follows the format (`instruction, win_response, lose_response`)
- <mark style="background: #FFB8EBA6;">long-context finetuning</mark> = requires model architecture modification so model can have greater context length
	- usually done via adjusting positional embeddings
	- e.g. CodeLlama models extended Llama 2 context from 4,096 to 16,384 tokens

# 2 When to Finetune 
- compared to prompt engineering, finetuning requires significantly more resources
	- both data + hardware but also ML talent
	- hence, finetuning generally only tried after extensive prompt engineering efforts 
		- however, you can combine both approaches 
## 2.1 Reasons why you should + should NOT Finetune
- ✅ primary reasons to finetune
	- <span style="color:rgb(0, 176, 80)">tone, style, format customisation</span> 
		- to match your desired tones or formats e.g. following specific output structures 
	- <span style="color:rgb(0, 176, 80)">improving performance + handling edge cases</span>
		- e.g. reducing hallucinations, or addressing errors that are hard via prompt engineering
		- most valuable for enhancing reliability in niche domains and tasks 
	- <span style="color:rgb(0, 176, 80)">bias mitigation + addressing underrepresented domains</span>
		- e.g. making it more gender-neutral or learning specialised jargon 
	- <span style="color:rgb(0, 176, 80)">cost reduction</span> 
		- via distillation, reducing compute costs/latency without compromising quality 
		- less important now with prompt caching
	- <span style="color:rgb(0, 176, 80)">developing new tasks or abilities</span>
		- can help model develop new capabilities e.g. long context 
		- or to help become factually coherent
- ⛔️ reasons to not finetune
	- <span style="color:rgb(255, 136, 0)">risk of overfitting + loss of generalisation</span>
		- can degrade performance for other task - especially bad for applications where you expect diverse prompts 
		- consider using seperate models for different tasks if you need best performance
	- <span style="color:rgb(255, 136, 0)">resource intensive</span> 
		- requires significant compute, talent, cost e.g. large model calls for distillation 
		- also requires ongoing maintenance
		- also needs annotated data - slow + expensive to collect 
		- also needs ML + engineering chops e.g. hot to serve it
- remember: **AI engineering experiments should always start with prompting** (w best practices)
	- ensure you've tested many prompts thoroughly - since performance can really shift with this 
	- Huyen notes this is a very common scenario: 
		- insist on finetuning but their prompting was minimal + unsystematic
			- data was not representative
			- metrics poorly defined with no proper eval pipeline
		- then after refining all this, prompt quality improved enough to be sufficient
	- both finetuning and prompting experiments require systematic processes. 
		- doing prompt experiments enables developers to build an evaluation pipeline, data annotation guideline, and experiment tracking practices that will be stepping stones for finetuning

>[!warning] Bloomberg GPT example
> - BloombergGPT announced March 2023
> 	- Bloomberg wanted a mid-sized model to perform well on financial tasks + proprietary data
> - trained a 50B model, using 1.3 million A100 GPU hours for training
> 	- estimated cost between 1.3-2.6 million USD (not including data costs)
> - in same month, OpenAI updated GPT4 which significantly outperformed it on various financial benchmarks

### 2.1.1 Distillation
- much more common to finetune smaller models rather than large models
	- <mark style="background: #FFB8EBA6;">distillation</mark> = common to finetune the small model to imitate the behaviour of a larger model using data generated by the large model 
- small finetuned, task specific models can outperform much larger general models on specific tasks 
	- e.g. Grammarly 2022, finetuned Flan-T5 on 82,000 input/output pairs to outperform GPT-3
		- despite being 60x smaller
		- Flan-T5 sizes range from 80M to 11b params, GPT-3 = 175 billion params
	- open source community proliferated this trend with models and datasets for all sizes and domains
		- has made finetuning much more viable, attractive
## 2.2 Finetuning and RAG
- once exhausting prompting, how to decide between RAG or finetuning next?
	- answer depends on if failures are caused by information or behaviour of the model
- model fails because it lacks info - RAG can give model access to relevant info sources 
	- caused when model does not have info e.g. private knowledge, or when model's info is outdated
	- 2024 paper "*Finetuning or Retrieval?*" - for tasks requiring up-to date info, RAG outperformed finetuned models
		- further, base models with RAG outperformed finetuned models with RAG
		- hence finetuning model on specific task can degrade abilities elsewhere
- finetuning can help if the model has behavioural issues
	- e.g. failing to follow expected output format 
		- especially for syntaxes with less resources on internet available 


>[!tip]
> *In short, finetuning is for form, RAG is for facts.* 
> 
> - **RAG** gives model external knowledge for more accurate + informative answers
> 	- can also help with hallucinations
> - **Finetuning** helps model understand and follow syntaxes and styles
> 	- can potentially help hallucinations with very good data, but can also worsen if data is poor

- if your have both info + behaviour issues, start with RAG
	- typically easier + less upfront investment on the data 
	- note: doing both empirically shown to give mixed results
		- e.g. same paper above showed doing both gave boost on MMLU only 43% of the time
- an example workflow of deciding what to use to improve AI application performance
	- note: before any of this, need clearly defined eval criteria + pipeline
		- this is the foundation of what you use to benchmark your progress
	1. try to get model to perform well on task via prompting only - use prompting best practices
	2. add more examples to the prompt - might be 1-50
	3. if model fails often due to missing info, connect it to relevant data sources
		- start with basic retrieval first e.g. BM25
	4. depending on failure modes, explore one of these next steps
		- if continued info-based failures, try more advanced RAG methods e.g. embedding based
		- if continued behaviour issues try finetuning
	5. combine both RAG + finetuning for more performance boost

# 3 Memory Bottlenecks 
- below summary covered since many finetuning techniques exist to minimise memory footprint

> [!NOTE] Key Summary of this section
> - memory is bottleneck for LLMs for both inference + finetuning (much higher)
> - key contributors to memory footprint = # parameters, # trainable parameters, numerical representation
> - more trainable params = higher memory footprint - PEFT motivated to reduce this
> - quantisation = converting model format to use fewer bits
> - inference typically done using few bits as possible e.g. 16, 8, even 4 bits
> - FP32 = 4 bytes per weight, reducing this to half decreases entire size by $\frac{1}{2}$
> - training most sensitive to numerical precision, so harder to train in lower precision
> 	- common to use mixed precision e.g. 32 + 16/8 bit

## 3.1 Backprop + Trainable Parameters
- <mark style="background: #FFB8EBA6;">trainable parameter</mark> = parameter that can be updated in finetuning 
	- in pre-training, all params are updated
	- in finetuning, some or all model params can be updated
		- frozen parameters = unchanged params in finetuning e.g. frozen layers
- models typically trained via backprop which has 2 key steps
	- <span style="color:rgb(255, 0, 247)">forward pass</span> = process of computing output using inputs
	- <span style="color:rgb(255, 0, 247)">backward pass</span> = process of updating model weights using aggregated gradients from forward pass
		1. compares computed output against ground truth, calculates difference (loss)
		2. computes how much each trainable param contributed to mistake (gradient)
			- calculated by taking derivate of loss w.r.t. each trainable param 
			- one gradient value per trainable parameter, high gradient = higher loss contribution
		1. adjust trainable parameters using corresponding gradient
			- adjustment determined by optimiser e.g. SGD, Adam
	- when doing LLM inference, only forward pass executed
		- however if doing finetuning, the backward pass has more values
			- each trainable parameter + each gradient + optimiser states

## 3.2 Memory Math 
- useful to know memory footprint so you can allocate right hardware
### 3.2.1 Inference memory
- inference only requires forward pass - which requires model weights + activation values

$$
\begin{gather}
\large{\text{Memory Needed for Inference} = N \times M}
\\ \ \\
\text{where}:  
\begin{aligned} 
N & : \text{model parameter count} \\ 
M & : \text{memory needed for each parameter} 
\end{aligned} 
\end{gather}
$$

- transformers need memory to store $\text{key-value}$ vectors for attention
	- memory for activations of  $\text{key-value}$ vectors grows linearly with sequence length + batch size
		- can assume this to be 20% of memory for model weights
		- higher context size or batch size will need more actual memory 

$$
\begin{gather}
\large{\text{Memory Needed for Inference w KV Activations} = N \times M \times 1.2}
\end{gather}
$$
- model's memory footprint grows rapidly with model size 
	- memory is the bottleneck for operating larger models
	- e.g. 70B model with 2 bytes per param needs 140 GB of memory just for weights

> [!NOTE] *Example Memory Calculation* - 13B Param Model
> - if each param needs 2 bytes - model weights require 13 billion $\times$ 2 bytes = 26GB
> - total memory for inference then is 26GB $\times$ 1.2 = 31.2GB

### 3.2.2 Training memory
- in addition to model weights + activations, training needs **gradients + optimiser states**
	- which both scale with number of trainable params 

$$
\begin{gather}
\large{\text{Memory Needed for Training}}
\\ \\ 
= \text{Model Weights + Activations + Gradients + Optimizer States}
\end{gather}
$$

- recall, in backward pass each trainable param needs 1 value for gradient + 0-2 values for optimiser states
	- 0 to 2 since it depends on the optimiser being used
		- Vanilla SGD has no optimiser state
		- Momentum stores 1 value per trainable param
		- Adam stores 2 values per trainable param 

> [!NOTE] *Example Memory Calculation* - 13B and 1B Param Model
> - given a 13B param to train using Adam Optimiser
> 	- each trainable param will have 3 values for gradient + optimiser states
> 	- if each value takes 2 bytes, memory needed for gradient + optimiser states is:
> 		- $13\text{B} \times 3 \times 2$ bytes = 78 GB
> - given 1B param model with the same
> 	- $1\text{B} \times 3 \times 2$ bytes = 6 GB
- however, in practice, activation memory can be much larger than model weights 
	- especially if activations stored for gradient computation 
		- can be reduced by not storing them i.e. recomputing them when necessary
		- <mark style="background: #FFB8EBA6;">gradient checkpointing</mark> is exactly this, reduces memory requirements but increases training time
	- example below shows memory needed for <span style="color:rgb(0, 176, 80)">activations</span> for different Megatron model scales

## 3.3 Numerical Representations
- values in neural nets traditionally represented as float numbers 
	- each float format usually has the following components
		- <mark style="background: #FFB8EBA6;">sign</mark> = 1 bit to represent number's sign e.g. negative or positive
		- <mark style="background: #FFB8EBA6;">range</mark> = determines range of values format can represent
			- more bits = wider range
		- <mark style="background: #FFB8EBA6;">precision</mark> = determines how precisely a number can be represented
			- lower precision = less precise
			- e.g. $10.1234$ in a format with only 2 decimal digits must become $10.12$
	- **formats with more bits = higher precision**
		- converting from FP32 to FP16 = reducing it's precision
- most common floating point family format is the FP family (from IEEE)
	- <mark style="background: #FFB86CA6;">FP32 (single precision)</mark> = uses 32 bits (4 bytes) to represent a float
	- <mark style="background: #FFB86CA6;">FP64 (double precision)</mark> = uses 64 bits (8 bytes)
	- <mark style="background: #FFB86CA6;">FP16 (half precision)</mark> = uses 16 bits (2 bytes)

![[Screenshot 2024-12-31 at 9.55.16 am.webp| center | 700]]
- FP64 is default for many computations e.g. `numpy` and `pandas` both use it
	- but rare for neural nets due to memory footprint - FP32 + FP16 more common 
- other popular FP formats have been designed for AI 
	- <mark style="background: #FFB86CA6;">BF16 (BFloat16)</mark> = designed by Google for optimal performance on TPUs
		- compared to FP16 - more bits for range, less for precision
		- so it can represent values out of bounds for FP16, but at cost of being less precise 
	- <mark style="background: #FFB86CA6;">TF32 (TensorFloat-32)</mark> = designed by NVIDIA for GPUs

## 3.4 Quantisation 
- fewer bits needed to represent model's values = lower model memory footprint
	- e.g. 10B model in 32bit = 40GB, but if you load 10B model in 16 bit = 20GB
	- low precision generally means anything less than standard FP32
	- inference in lower precision has become standard
		- e.g. PyTorch, Huggingface and others all support this now 
	- backprop is more sensitive to lower precision - hence training is less popular

```python
# PyTorch float16 example
import torch
model = MyModel().to('cuda').eval()
with torch.autocast(device_type = 'cuda', dtype = torch.float16):
	with torch.no_grad():
		output = model(input_tensor)

# Huggingface Transformers float16 example
from transformers import AutoModelForSequenceClassification
model = AutoModelForSequenceClassification.from_pretrained( 
	model_path = 'bert-base-uncased', 
	torch_dtype = torch.float16 
).to('cuda')
```

- <mark style="background: #FFB8EBA6;">quantisation</mark> = reducing model precision
	- cheap and extremely effective way to reduce model's memory footprint 
		- also easy to do + generalises over tasks + architectures
	- ✅ benefits of reduced precision 
		- improves computation speed - further reduces inference latency + training time
		- allows larger batch size = more parallel inputs
	- ⛔️ downsides to reduced precision
		- small changes can cause big performance changes e.g. accidental conversion to infinite values etc
	- became common to use 16 bits in late 2010s
		- has become even more popular with 8bit formats + QLORA which uses 4 bits
			- essentially becoming integer format
		- BitNet, 2023 even attempts 1-bit representation
			- later, Microsoft, 2024 went further and introduced BitNet b1.58
			- only requiring 1.58 bits per parameter with comparable performance to 16bit Llama 2
- to quantise, need to decide what to quantise + when to quantise
	- <span style="color:rgb(255, 136, 0)">what to quantise</span> = **most common with weights rather than activations**
		- since weight activation tends to have more stable impact on performance with less accuracy loss
	- <span style="color:rgb(255, 136, 0)">when to quantise</span> = i.e. either **during training or post-training aka PTQ** (after it's done training)
		- PTQ is much more common and most useful for inference
		- training quantisation not as common but growing - goal is to get model to perform well in low precision inference + reduce training time and cost 
			- **Quantisation-aware training (QAT)** - aims to create high quality model in low precision
			- simulates low precision (e.g. 8bit) behaviour in training, so model learns to produce high quality outputs in low precision
			- but does not reduce training time 
- models can also be served in <mark style="background: #FFB8EBA6;">mixed precision</mark>
	- Apple, 2024 used quantisation scheme with mixture of 2-bit + 4-bit formats 
		- averaging 3.5 bits-per-weight
	- NVIDIA new Blackwell chip also supports inference in 4-bit float
	- lower precision training e.g. QAT, often done in mixed precision
		- copy of weights kept in higher precision but other values (gradients, activations) kept in lower precision
	- <mark style="background: #FFB8EBA6;">automatic mixed precision (AMP)</mark> = portions of model that should be in lower precision set automatically
		- offered by Torch and other ML frameworks

# 4 Finetuning Techniques 
- <mark style="background: #FFB86CA6;">full finetuning</mark>: number of trainable params == number of total model params
	- looks similar to training but instead of starting with randomised weights, finetuning uses pre-trained weights
	- example memory calculation for full finetuning a 7B model
		- using 16-bit format (FP16), loading model weights alone = 14GB for memory
		- using Adam optimiser in 16-bit requires additional 42GB of memory
			- 7B * 3 * 2 bytes = 42GB
		- so total memory for weights, gradients, optimiser states = 14GB + 42GB = 56 GB!
			- and we haven't added activations
	- <mark style="background: #FFB86CA6;">partial finetuning</mark> = only some of model's parameters are updated 
		- e.g. last layer of a 10 layer model - meaning only 10% of params
		- can reduce memory footprint but is **parameter inefficient**
			- since PT requires many trainable params to achieve performance close to a full finetune
		- 2019 study on BERT-large, showed you need at least 25% of params to get close to full FT
## 4.1 Parameter Efficient Finetuning (PEFT)
- due to above - big research question is "how to achieve performance close to full finetune while using significantly fewer trainable parameters"
- <mark style="background: #FFB8EBA6;">PEFT (parameter-efficient finetuning)</mark> = introduced by Housby et al, 2019
	- authors showed inserting additional params into the model at the right places can get strong finetuning performance using a small number of trainable params
		- achieved performance within 0.4% of full FT using only 3% of trainable params
	- inserted 2 adapter modules into each transformer block of BERT 
		- keeps original params unchanged, only updating the adapters

![[Screenshot 2024-12-31 at 10.41.36 am.webp| center | 600]]

- downside is the additional layers increase inference latency slightly 
	- but allows for finetuning on much more affordable hardware making it very accessible
	- PEFT methods are both parameter efficient + sample efficient
		- PEFT can give strong performance with just few thousand examples
		- vs thousands to millions needed for full FT
### 4.1.1 PEFT Techniques
- given appeal of PEFT, many new techniques being developed - most popular is LoRA
- PEFT techniques fall into 2 categories
	- <mark style="background: #FFB8EBA6;">Adapter based methods</mark> = all methods involving additional modules to model weights
		- aka additive methods
		- LoRA, 2021 by far most popular, others include BitFit (2021), IA3 (2022), LongLoRA (2023)
	- <mark style="background: #FFB8EBA6;">Soft-prompt based methods</mark> = modify how model processes input by introducing special trainable tokens
		- additional tokens (soft prompts) then fed into model alongside input tokens 
		- soft prompts different to the inputs (hard prompts) as they are not readable - they are continuous embedding-like vectors, and they are also trainable
		- multiple methods in this subfield including Prefix-tuning, P-tuning, prompt-tuning
			- all mainly differ on location where soft prompts are inserted 
### 4.1.2 LoRA
- <mark style="background: #FFB8EBA6;">Low-Rank-Adaptation (LoRA)</mark> = introduced by Hu et al, 2021 - incorporates additional params that don't impact extra inference latency 
	- instead of additional layers to base model, LoRA uses modules merged back into original layers
	- can apply LoRA to individual weight matrices

>[!info] Matrix-product rules make low-rank factorisation possible
> - recall calculating the shape of a matrix multiplication operation
> 	- let a matrix $M$ be of size $p \times q$ 
> 	- let another matrix $N$ be of size $q \times r$
> 	- you need number of columns in 1st matrix == number of rows in 2nd matrix
>
> ![[Screenshot 2024-12-31 at 10.54.44 am.webp| center | 200]]
> - resulting matrix size of $M \times N$ will then be $p \times r$
> - now we can use 2 smaller vectors instead to represent this $M \times N$ matrix
> 	- by decomposing it into 2 vectors and taking their product 
> 		- where we use rank of 1 to decompose
> 	- where vector $p$ has shape $p \times 1$
> 	- and vector $r$ has shape $1 \times r$
> 	- and multiplying them gives you the original shape $p \times r$


> [!NOTE] LoRA and Low-Rank factorisation
> - LoRA is built upon this concept of **low-rank factorisation**
> 	- a long standing dimensionality reduction technique
> - key idea = factorise a large matrix into a product of 2 smaller matrices to reduce number of parameters
> 	- in turn, reducing computation + memory requirements
> - e.g. $9 \times 9$ matrix factorised into 2 matrices of dimension $9 \times 1$ and $1 \times 9$
> 	- original matrix (full-rank) has 81 parameters
> 	- factorised matrix has 18 parameters in total
> - note: this operation is **lossy** since it only approximates original matrix
> 	- the higher the rank, the more info from original matrix you can preserve

- given a weight matrix, **LoRA decomposes this matrix into product of 2 smaller matrices**
	- then updates these 2 smaller matrices before merging them back to original matrix 
	- given a weight matrix $W$ with shape $n \times m$, LoRA does this:
		1. choose dimension (rank) of smaller matrices = $\large{r}$ is our **LoRA rank**
		2. construct 2 matrices 
			- $A$ with dimensions $n \times r$
			- $B$ with dimensions $r \times m$
		3. their product is $W_{AB}$ which is of same dimensions as $W$ (original matrix) i.e. $n \times m$
		4. add $W_{AB}$ to original weight matrix $W$ to create new matrix $W'$
		5. use $W'$ in place of $W$ as part of the model 
			- can use hyperparameter $\alpha$ to determine how much $W_{AB}$ should contribute to new matrix
			- $W' = W + \frac{\alpha}{r}W_{AB}$
		6. during finetuning, only update parameters in $A$ and $B$, leaving $W$ unchanged

![[Screenshot 2024-12-31 at 10.51.35 am.webp| center | 600]]

- LoRA allows for training even fewer parameters - still param + sample efficient
	- LoRA paper showed GPT-3 finetune of LoRA got same or better performance vs full FT
	- using only 0.0027% of trainable params (4.7 million approx.)
	- how does this even work? many papers have studied the intrinsic dimensions of LLMs
		- i.e. how can this be so effective with just a few thousand examples
		- showed that pre-training implicitly minimises the model's intrinsic dimensions
			- so larger models have lower intrinsic dimensions after training
		- **suggesting pre-training acts as a compression framework for downstream tasks**
			- i.e. the better trained the LLM, the easier it is to finetune the model using a small number of trainable params + small amount of data 
		- because of this success, many have tried to pre-train via LoRA and Huyen thinks this will likely be a research breakthrough in the future
- to apply LoRA, you must **decide what weight matrices to apply it to + the rank of each factorisation**
	- since you can apply it to individual weight matrices, it depends on the model's architecture
	- most commonly applied to the 4 matrices in the attention module
		- query ($W_q$), key ($W_k$), value ($W_v$) and output projection ($W_O$) matrices
		- typically applied uniformly to all matrices of same type within a model 
- 2021 paper, tried multiple variations using a trainable param budget of 18M for GPT-3 175B
	- 18m params would be 0.01% of the total params
	- variations included 
		- 1 matrix with rank 8
		- 2 matrices with rank 4
		- all 4 matrices with rank 2
	- found the last option gave best performance, see result table below

| Weight type            | $W_q$  | $W_k$  | $W_v$  | $W_o$  | $W_q, W_k$ | $W_q, W_v$ | $W_q, W_k, W_v, W_o$ |
| ---------------------- | ------ | ------ | ------ | ------ | ---------- | ---------- | -------------------- |
| Rank $r$               | $8$    | $8$    | $8$    | $8$    | $4$        | $4$        | $2$                  |
| WikiSQL ($\pm 0.5\%$)  | $70.4$ | $70.0$ | $73.0$ | $73.2$ | $71.4$     | $73.7$     | $73.7$               |
| MultiNLI ($\pm 0.1\%$) | $91.0$ | $90.8$ | $91.0$ | $91.3$ | $91.3$     | $91.3$     | $91.7$               |
- ✏️ other LoRA tips
	- applying LoRA to more weight matrices (including FFNN) gives better results
	- paper also suggested if you can only choose 2 attention matrices, prioritise query + value
		- also suggesting increasing $r$ doesn't lead to better performance
	- a small $r$ between 4 and 64 is usually sufficient
	- LoRA hyperparam $\alpha$ (determines contribution of product matrix $W_{AB}$ to new matrix $W'$) can take values where ratio of $\alpha:r$ is between 1:8 and 8:1 but optimal ratio varies 
		- e.g. if $r$ is small, might want larger $\alpha$
		- if $r$ is large, might want smaller $\alpha$ 
		- need to experiment to find best combination of $r, \alpha$ for your use-case
- another benefit of LoRA is the modularity which allows you to serve many different models
	- recall, 2 methods to serve a LoRA-finetuned model
		- merge LoRA weights $A, B$ to original model to create new $W'$ - no extra computation/latency
		- keep $W, A, B$ seperate during serving, requires merging $A, B$ back to $W$ in inference (additional latency)
	- 1st option generally better for single model, 2nd better for **multi-LoRA serving**
		- <mark style="background: #FFB8EBA6;">multi-LoRA serving</mark> = very easy to serve combination of specialised models
			- e.g. one LoRA adapter for each task 
		- Apple used this for different iPhone features using the same 3B model + quantisation allowing on-device
		- modularity of LoRA adapters also means they can be shared + re-used via 🤗
	- main drawback of LoRA = not as performant as full FT

![[Screenshot 2024-12-31 at 11.46.47 am.webp| center | 600]]

- <mark style="background: #FFB8EBA6;">Quantised LoRA</mark> = variation to further reduce memory footprint 
	- via quantising model weights, activations + gradients in finetuning
	- QLoRA, 2023 is best example where they stored model weights in 4 bits but de-quantises/converts them back into BF16 for forward + backward passes
		- original paper used 16 bits
	- QLoRA's 4-bit format known as NF4 (NormalFloat-4) = quantises based on insight that pre-trained weights usually follow a normal distribution with median of 0 
		- other optimisations too e.g. paged optimisers
	- main drawback of QLoRA is possibly increased training time due to conversion steps
## 4.2 Model Merging
- <mark style="background: #FFB8EBA6;">model merging</mark> = creating a custom model by combining multiple models 
	- very experimental, and can be done without GPUs - attractive to indie developers
	- goal = create single more useful model vs using constituent models separately 
		- e.g. model A can answer 60% of questions, model B can answer a different 60%, combining them could get you to 80%
- <mark style="background: #FFB8EBA6;">multi-task finetuning</mark> = important use case for merging, allowing you to combine benefits for specific tasks across different models
	- otherwise would have to do 1 of 2 options 
		- <span style="color:rgb(255, 0, 247)">simultaneous finetuning</span> = create dataset for all tasks, finetune model to learn on this 
			- harder to learn multiple skills at same time, typically requires more data + training time
		- <span style="color:rgb(255, 0, 247)">sequential finetuning</span> = finetune model on each task separately but sequentially 
			- e.g. train model on task A, then task B etc 
			- assumption to learn one task at a time but prone to catastrophic forgetting (forgetting old tasks)
	- <span style="color:rgb(255, 0, 247)">multi-task finetuning</span> - involves finetuning each model on different tasks separately in parallel
		- then merging the final models, less risk of catastrophic forgetting
- many models on 🤗 Open LLM Leaderboard are merged models
	- merged models also promising for on-device - using 1 multi purpose merge model vs many small models
	- merged models **inspired by ensemble methods** = combining multiple algorithms to obtain better performance than could be obtained from any of constituent learning algorithms alone
		- model merging = mixing params of constituent models together
		- ensembling = combining model outputs, keeping constituent models intact

### 4.2.1 Approaches to Model Merging
- 3 main approaches, differing in how constituent parameters are combined
	- you may also mix some of these methods together
	- didn't cover this much, but feel free to go to book chapter if needed
1. <mark style="background: #FFB8EBA6;">Summing</mark> = add weights of each model together
	- main methods = linear combination + spherical linear interpolation + parameter alignment
2. <mark style="background: #FFB8EBA6;">Layer Stacking</mark> = stacks layers of different models
	- "*frankenmerging*", MoE, model upscaling
3. <mark style="background: #FFB8EBA6;">Concatenation</mark> = appending parameters from each model, not memory efficient

## 4.3 Finetuning Tactics (4)
1. <span style="color:rgb(255, 136, 0)">base model</span>
	- consider model size, licenses, benchmark performance
	- start with the cheapest + fastest model to make sure code works as expected
		- then test you data with slightly larger model - training loss should go further down
		- run more experiments with better models to see how far performance can go
		- once you have good results, do a training run with all models
			- then pick best price/performance frontier
	- distillation path is slightly different 
		- start with small dataset + strongest model you can afford 
			- and train best possible model with this small dataset
		- use the finetuned model to generate more training data
		- use this dataset to train a cheaper model
2. <span style="color:rgb(255, 136, 0)">finetuning method</span>
	- recall, full FT requires many examples (10k, 100k, 1 mil etc)
		- PEFT is best place to start with smaller dataset e.g. few hundred examples
		- e.g. LoRA methods
	- can progress to full finetuning if you seek further gains 
3. <span style="color:rgb(255, 136, 0)">finetuning framework</span>
	- easiest to use a finetuning API either from scratch or via a service
		- downside with services is restricted to models they provide
		- suitable for quick and easy testing, but bad for customisation 
	- consider reading large base model Git Repos - they often provide training code
	- main players in finetuning frameworks have gotten popular and should be tried
		- [Llama-Factory](https://github.com/hiyouga/LLaMA-Factory), [unsloth](https://github.com/unslothai/unsloth), [PEFT](https://github.com/huggingface/peft), [Axolotl](https://github.com/axolotl-ai-cloud/axolotl), [LitGPT](https://github.com/Lightning-AI/litgpt)
			- PEFT supported by 🤗, LitGPT supported by Lightning AI
		- all support variety of techniques including adapter methods 
		- [Llama Police](https://huyenchip.com/llama-police) has big list of up-to-date finetuning frameworks
	- can also do distributed training via DeepSpeed, PyTorch Distributed, ColossalAI
4. <span style="color:rgb(255, 136, 0)">hyperparameters</span> 
	- start by checking the finetuning guide for your framework, key ones to consider:
	- <span style="color:rgb(255, 0, 247)">learning rate</span> -  how fast model params change w each step 
		- aka the step size, no universal step size exists
		- need to experiment with different ranges, typically 1e-7 to 1e-3
			- $1×10^{-7} = 0.0000001$
			- $1×10^{-3} = 0.001$
		- common practice to take learning rate from end of pre-train phase and multiply it by constant between 0.1 and 1
		- loss curve can give you feedback on learning rate
			- fluctuating loss curve = learning rate might be too big 
			- stable but slow and long loss curve = learning rate might be too small
			- increase learning rate as high as loss curve remains stable 
		- can also use learning rate scheduler to vary it during training process
	- <span style="color:rgb(255, 0, 247)">batch size</span> - how many examples a model learns from in each step to update it's weights
		- larger batch size helps aggregate signals from more varying examples = more stable updates
			- too small batch size (e.g. < 8) = unstable training
		- larger batch size = faster model can go through training
			- however requires more memory - so limited by hardware 
			- can try gradient accumulation here
	- <span style="color:rgb(255, 0, 247)">number of epochs</span> - 1 epoch = 1 pass over the training data
		- number of epochs = how many times each training example is trained on 
		- small datasets might need more epochs than large datasets
			- e.g. millions of examples - can do 1-2 epochs
			- thousands of examples, can still get gains after 4-10 epochs
		- difference between train loss and validation loss can give you feedback on number of epochs
			- if both train + val loss steadily decrease, can do more epochs (and data)
			- if train loss decreased, but validation loss increases - likely overfitting, use less epochs
	- <span style="color:rgb(255, 0, 247)">prompt loss weight</span> - response tokens need to contribute more to training loss than prompt tokens
		- this determines how much prompts should contribute to loss vs responses
		- 100% means equal contribution as responses
		- typically set at 10% by default
