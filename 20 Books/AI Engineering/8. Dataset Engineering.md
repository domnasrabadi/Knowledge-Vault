- quality of a model determined by the data 
	- goal of <mark style="background: #FFB8EBA6;">dataset engineering</mark> = create a dataset that allows you to train the best model
	- ideally within your allocated compute budget 
- many companies now employ data labellers, dataset creators + data quality engineers
	- either working within or alongside the engineering teams 
- <span style="color:rgb(179, 179, 179)">GPT-3, 2020</span> had 2 people credited with data collecting, filtering, deduplicating + conducting overlap analysis
	- <span style="color:rgb(179, 179, 179)">GPT-4, 2023</span> had 80 people for different data processes
	- ChatML format was created with 11 people, many being senior researchers 
- Dataset engineering includes 3 key steps 
	- <span style="color:rgb(255, 136, 0)">data curation</span> = what data is needed? how much? what quality?
	- <span style="color:rgb(255, 136, 0)">data synthesis</span> = how to create more data, synthetically or via augmentation
	- <span style="color:rgb(255, 136, 0)">data processing</span> = how to manipulate and format data 
- datasets measured differently depending on phase of model 
	- pre-training dataset size = **measured in number of tokens** 
	- supervised finetuning dataset size = **measured in number of examples**
- model-centric vs data-centric AI 
	- <span style="color:rgb(255, 136, 0)">model-centric</span> = improve performance via enhancing models e.g. architectures, size, training techniques
	- <span style="color:rgb(255, 136, 0)">data-centric</span> = improve performance via enhancing data e.g. smaller higher quality datasets
		- Andrew Ng, 2021 created data-centric AI competition where participants had to improve upon same dataset
		- via fixing labels, adding edge case examples, augmenting etc 
# 1 Data Curation
- what data you need depends on your task + what you want to teach model 
	- <mark style="background: #FFB86CA6;">self-supervised finetuning</mark> = requires sequences of data 
	- <mark style="background: #FFB86CA6;">instruction finetuning</mark> = requires `instruction, response` format
	- <mark style="background: #FFB86CA6;">preference finetuning</mark> = requires `instruction, winning response, losing response` format 
	- <mark style="background: #FFB86CA6;">reward models</mark> = requires same data as preference or data with annotated scores for each example
		- e.g. `instruction, response, score` format 
- training data should exhibit behaviours you want model to learn 
	- acquiring high-quality annotations is always challenging 
	- data curation also about removing bad data to unlearn undesirable behaviours 
- more advanced techniques include
	- <mark style="background: #FFB8EBA6;">chain of thought</mark> - teaching model to generate responses step-by-step with working
		- <span style="color:rgb(179, 179, 179)">Chun et al 2024</span> found incorporating these in finetuning data greatly enhances performance in COT tasks
			- almost doubling accuracy for some tasks 
		- creating COT data more tedious + time-consuming since you need to explain steps 
	- <mark style="background: #FFB8EBA6;">tool use</mark> - model's tool use can be improved by showing it tool use examples
		- e.g. asking assistant what task to perform, how to perform + what tools they need
		- also difficult since what tools are efficient for humans might not be efficient for AI 
			- e.g. AIs prefer APIs 
- for conversational applications, need either/both single-turn and multi-turn data 
	- <span style="color:rgb(255, 136, 0)">single turn data</span> - trains model on individual instructions 
		- usually simpler + easier to curate
	- <span style="color:rgb(255, 136, 0)">multi turn data</span> - teaches model how to solve tasks with back and forth
		- e.g. first clarify user intent, then address task, then provide response and add corrections etc 
		- often requires purpose-built scenarios or more involved interactions to capture 
- each application will require different data characteristics
	- different training phases also require different data mixes
	- generally, data curation has 3 steps $\rightarrow$ data quality, data coverage, data quantity 

>[!info] Dataset Engineering as cooking
> - Image you are the chef, your data is the ingredients 
> 	- data quality = quality of your ingredients
> 	- data coverage = mix of what ingredients you have for taste 
> 	- data quantity = how many ingredients you need to make the serving

## 1.1 Data Quality
- small amount of high-quality data can outperform larger amounts of noisy data 
	- <span style="color:rgb(179, 179, 179)">Yi Model, 2024</span> found 10K carefully crafted instructions superior to hundreds of thousands of noisy instructions
	- <span style="color:rgb(179, 179, 179)">LIMA, 2023</span> found 65B model finetuned with 1000 carefully curated prompts + responses can beat GPT-4 in human preference 
	- <span style="color:rgb(179, 179, 179)">Llama 3, 2024</span> also found the same, so they used AI-assisted annotation tools to ensure higher data quality 
- 6 characteristics of high quality data 
	- <mark style="background: #BBFABBA6;">relevant</mark> = examples should be relevant to the task 
	- <mark style="background: #BBFABBA6;">aligned with task requirements</mark> = annotations should meet task requirements
		- e.g. if it requires factual consistency, annotations must be factually correct
		- e.g. if task demands concise answers, annotations should be concise 
	- <mark style="background: #BBFABBA6;">consistent</mark> = annotations should be consistent across examples and annotators 
		- should get similar scores between annotators, mismatches may confuse the model 
		- **having a good annotation guideline is essential** 
	- <mark style="background: #BBFABBA6;">correctly formatted</mark> = should follow the format expected by the model in prod 
		- beware of trailing white spaces, new lines, inconsistent casing, numerical formats 
	- <mark style="background: #BBFABBA6;">sufficiently unique</mark> = unique examples in your data 
		- duplications can introduce biases + cause data contamination 
	- <mark style="background: #BBFABBA6;">compliant</mark> = compliant with all internal + external policies 
		- e.g. no PII 
## 1.2 Data Coverage (or Diversity)
- depending on different tasks your model is required to solve - coverage requires sufficient data diversity 
	- you need data that captured diverse usage patterns 
	- e.g. both detailed and short instructions, with and without typos 
- different applications have different dimensions of diversity 
	- e.g. chatbot to recommend products doesn't need domain diversity but cultural + linguistic diversity 
	- for general purpose chatbots - finetuning data should be diverse + cover wide range of topics + speaking patterns
- <span style="color:rgb(179, 179, 179)">Ding et al, 2023</span> - most straightforward way to improve LLM performance = increase quality + diversity of training data
	- <span style="color:rgb(179, 179, 179)">NVIDIA, Nemotron, 2024</span> - focused on data with task diversity, topic diversity, instruction diversity
		- e.g. using different output formats, instructions with different output lengths + instructions for open/closed responses
	- <span style="color:rgb(179, 179, 179)">Shen et al, 2024</span> - showed adding more heterogeneous data can sometimes worsen performance
- Llama 3 didn't change anything architecture wise, mostly by improvements in data quality, diversity and training scale 
	- Llama 3 paper covered many useful tips in the paper - especially on post-training data mix 
	- used a mix of real + synthetic data, useful to compare % ratio between them 
- Example below of Llama 3, data mixes for various training phases

|                   | Pre-training | Supervised Finetuning | Preference Finetuning |
| ----------------- | :----------: | :-------------------: | :-------------------: |

- how to choose right data mix?
	- ideally, should accurately reflect real world application usage, can also experiment to find optimal data mixes 
		- <span style="color:rgb(179, 179, 179)">Meta, 2023</span> - performed ablations on different data mixes - chose the best mix derived from experiments
			- for each candidate data mix, trained several small models
			- then used that to predict performance of large model on that mix

## 1.3 Data Quantity 
- asking how much data you need is like asking how much money you need - more is generally better
	- pros for both training on small + large sets as found in research 
	- <span style="color:rgb(179, 179, 179)">Hernandez et al 2021</span> - found finetuning small models on lots of data is worse (ossification)
- 3 factors determine how much data you need 
	- <mark style="background: #FFB86CA6;">finetuning techniques</mark> - full FT is preferable, but requires orders of magnitude more data 
		- use PEFT for few hundred/thousand
		- use full FT for millions of `instruction, response` pairs
	- <mark style="background: #FFB86CA6;">task complexity</mark> - simple tasks require less data than complex tasks 
	- <mark style="background: #FFB86CA6;">base model performance</mark> - closer base model is to desired performance, less data needed to FT 
		- fewer examples to finetune big models (opposite to pre-training needs)
- OpenAI finetuning guide suggests: 
	- for fewer examples e.g. 100, more advanced models give better finetuning performance
	- for many examples, most models converge to very good performance

![[Screenshot 2025-01-06 at 8.20.03 pm.png| center | 500]]

- if you have small amount of data - try PEFT methods on more advanced models
	- if you have large amount of data, use full finetuning with smaller models
- before curating larger dataset, start small + well-crafted dataset
	- e.g. 50 examples, to see if finetuning improves the model 
		- if no improvements even with small data, more data unlikely to help 
	- be careful of other things that impact finetuning results
		- e.g. hyperparameters, data quality, poorly crafted prompts 

> [!NOTE] You should notice performance improvements after finetuning with just 50-100 examples

- if you do not have high quality data readily available, you can use some less relevant data sources via below methods
	- <span style="color:rgb(255, 0, 247)">self-supervised to supervised</span> = first finetune in self-supervised fashion, then further FT on QA pairs
	- <span style="color:rgb(255, 0, 247)">less relevant data to relevant data</span> = FT first on related task, then further FT on your actual task 
	- <span style="color:rgb(255, 0, 247)">synthetic data to real data</span> = start with lots of synthetic data, then FT on real smaller dataset
- experimenting with small dataset can help estimate how much data you will need 
	- run experiment by finetuning on different subsets of dataset 
		- e.g. 25% then 50% then 100%
		- plot performance scale with dataset sizes
	- steep performance gain with slope == increasing dataset size likely to give better performance
	- plateaus in performance indicate diminishing return to more data 
![[Screenshot 2025-01-06 at 8.20.14 pm.png| center | 600]]

- more data generally improves performance but so does data diversity of examples
	- <span style="color:rgb(179, 179, 179)">Chung et al 2022</span>, showed model benefits greatly from exposure to diverse task in finetuning 
	- diversity reflected in different ways:
		- task types e.g. summarising, QA, etc 
		- topic diversity e.g. fashion, finance, tech 
		- expected output formats e.g. JSON, yes-no etc

## 1.4 Data Acquisition + Annotation
- <mark style="background: #FFB8EBA6;">data acquisition</mark> = gathering data via methods e.g. public data, purchasing private data, annotating data, synthetic creation
	- most important data source is your actual application's data - matches distribution you care about
		- user generated data includes user content, system generated data from user usage or user feedback
	- matching production distribution is very hard to achieve with other data sources

> [!NOTE] Example of Creating an Instruction-Response Dataset
> can develop datasets using multiple sources + acquisition channels, e.g. creating an `instruction, response` dataset:
>1. find available public datasets with similar characteristics e.g. 10k examples
>2. remove low quality instructions e.g. 9k remaining
>3. remove low quality responses e.g. 6k remaining of high quality 
>4. manually write responses for good instructions but bad responses e.g. can increase back to 9k
>5. realising not enough data for certain topic, add additional data using an instruction template for that topic
>	1. use AI to create additional 2k examples for that topic, using 10 different instruction templates 
>6. manually annotate these new instructions e.g. now at 11k 

- example sources for finding data 
	- Huggingface, Kaggle, Google Dataset Search, data.gov, ICPSR, UCL ML Repo, OpenML, AWS Open Data, Eleuther AI Harness
### 1.4.1 Annotation Guidelines
- likely will need to annotate your own data - annotation can be challenging
	- due to complexity of creating clear annotation guidelines
		- <span style="color:rgb(179, 179, 179)">Linkedin, 2024</span> mentioned annotation guidelines were one of most challenging parts of AI engineering pipeline 
	- should be used for both manual + AI powered annotations
- some tips 
	- try to explicitly state what good looks like + why it is good 
	- can a response be correct but unhelpful?
	- what's the difference between a score of 3 vs 4?
- evaluation examples can also be augmented or used as seed examples for new synthetic data

# 2 Data Augmentation + Synthesis (Synthetic Data)
- long standing goal in AI to be able to create data programatically 
	- <mark style="background: #FFB8EBA6;">data augmentation</mark> = creates new data from existing real data 
	- <mark style="background: #FFB8EBA6;">data synthesis</mark> = generates new data to mimic properties of real data 
- there are simple libraries available for data augmentation + generating fake data 
	- e.g. `Faker` and `Chance` help create simple fake data for names, addresses, phones etc for testing
- mixing human + synthetic data often produces the best value
## 2.1 Why Data Synthesis
- synthetic data is appealing for creating the golden data trio (quality, quantity, coverage)
	- <mark style="background: #FFB86CA6;">increase data quantity</mark> 
		- allows you to produce data at scale, more data == better generalisation
	- <mark style="background: #FFB86CA6;">increase data coverage</mark> 
		- using targeted characteristics for improving specific behaviours
		- allows for robustness via adversarial examples
		- allows for addressing class imbalance 
		- <span style="color:rgb(179, 179, 179)">Anthropic, 2022</span> discussed multiple synthesis methods for generating specific datasets to test 154 AI behaviours
			- including personality traits, political views, ethical stances, social biases 
			- found LLM written datasets approach quality of human ones, sometimes even exceeding them 
	- <mark style="background: #FFB86CA6;">increase data quality</mark>
		- sometimes synthetic data can actually be better than the real data 
			- humans might have fundamental limitations e.g. tool use data for AI training
		- some teams also prefer using AI for generating preference data - can be much more consistent and reliable
	- other reasons
		- to mitigate privacy concerns
		- to distil cheaper/faster models 
## 2.2 Traditional Data Synthesis Techniques
- procedural generation = using algorithms to create data aka manual generation 
- 2 broad types include:
	- <mark style="background: #FFB8EBA6;">rule based</mark> data synthesis = generate data using predefined rules + templates
		- common to use templates for documents that follow specific structure
			- can also be used to follow a certain grammar or syntax e.g. like AlphaGeometry, 2024 did 
		- can be applied using simple transformations
			- e.g. CNNs use this via rotation, cropping, scaling, erasing etc images
			- text can use random replacement, deletion, insertion
			- similar words can be retrieved using synonym dictionary or embedding search
		- can also be used to mitigate potential data biases
			- e.g. replacing gender or occupation words for equal outcomes
			- can also be used with perturbation for improving ability to deal with noise 
				- to help with attacks 
			- perturbation also helpful with performance e.g. <span style="color:rgb(179, 179, 179)">Devlin, 2018</span> replaced 1.5% of words randomly and got small boost
	- <mark style="background: #FFB8EBA6;">simulation based</mark> data synthesis = collecting data through simulated experiments 
		- simulations allow for large scale experiments with low cost, and no accidents/damage
			- e.g. driving a course with a vehicle virtually 
		- simulations commonly used to generate data to teach model to use tools
		- also particularly valuable for generating data for rare events 
			- e.g. rare economic events, manufacturing defects, temperature changes etc 
## 2.3 AI-Powered Data Synthesis
- virtually infinite ways for humans and AI to create new data 
	- powerful AI models open many new possibilities e.g. being able to simulate humans 
		- self-play was used heavily for AlphaGo
- self-play also used for general agents e.g. negotiate + interact with each other
	- then seeing which strategies or interactions worked better
	- can assign different personas and roles to agents
- AI paraphrasing and translation also very helpful in augmentation 
	- e.g. creating new variants of the same example with 3 different personas or styles of writing 
	- <span style="color:rgb(179, 179, 179)">Yu et al, 2023</span> rewrote 15k examples from MATH + GSM8k to create 400k dataset
		- new model trained on this outperformed much larger models 
- can be used for translation to low-resource languages 
	- one verification method is using back-translation e.g. translate X to Y, then back to X
	- can also be used for programming languages
	- Llama 3 used code translation in SFT data with wide range of programming languages
		- used back-translation to generate code explanations + documentation
		- started with code snippets, then used AI to generate code snippets from the explanations + doco 
		- if generated code was functional + faithful to original, they added it to SFT data 
- synthetic data can be created for both pre-training + post-training
	- post-training much more common since it can target specific areas, and you want diverse pre-training data 
		- instruction and preference data is also more difficult to annotate and create so more useful there 
	- <span style="color:rgb(179, 179, 179)">Cosmopedia, Huggingface 2024</span> - created 25 billion token dataset generated by Mixtral7x8b to create textbook quality data 
	- <span style="color:rgb(179, 179, 179)">NVIDIA, 2024</span> trained model to pick best of multiple answers + accounted for model biases e.g. first-position bias
		- by swapping order of response and judging twice
### 2.3.1 Instruction Data Synthesis
- AI can be used to create either `instruction`, the `response` or both `instruction, response`
	- can also use human to create instruction, AI to generate response 
- how to generate instructions + responses
	- start with a list of topics, keywords and instruction types you want in the dataset
	- for each item in the list, generate $N$ examples per template 
	- for responses, can generate 1 or more responses per instruction 
- many creative ways to synthesis instruction data with certain characteristics 
	- examples
		- <span style="color:rgb(179, 179, 179)">UltraChat, 2023</span> asked GPT to create 30 diverse topics, then for each topic, 30-50 subtopics
			- then used GPT to create instructions + responses to create a multi-turn dialogue dataset
		- <span style="color:rgb(179, 179, 179)">Alpaca, 2023</span> started with 175 `instruction, response` examples from Self-Instruct seed dataset
			- then used GPT to create 52k examples that mirrored these 
		- multiple papers used **reverse instruction** approach 
			- take existing long-form high quality content e.g. stories, books, wikipedia articles 
			- get AI to generate prompts to output such content 
			- yielded higher quality instruction data + avoided hallucinations in responses 
	- reverse instruction can be used for creating powerful models without manual annotations
		- <span style="color:rgb(179, 179, 179)">Li et al, 2023</span> - started with small number of seed examples to train a weak model 
		- used the weak model to generate instructions for existing high quality content
			- to create high-quality instructions
		- finetuned the weak model with this new high-quality instruction data
		- repeat until desired performance was reached 
- <span style="color:rgb(179, 179, 179)">Llama 3 paper, 2024</span> also used AI to create coding data from scratch 
	- use AI to generate large collection of coding problem descriptions across wide variety of topics
	- given problem description + programming language, generate a solution
		- found including good programming practices + COT helped improve responses
	- to ensure quality of generated data, used rigorous correctness analysis + error correction pipeline 
		- run generated code through parsers/linters to find syntactic errors, missing imports, uninitialised variables
		- use unit tests to catch execution errors (unit tests created from AI too)
		- when solution fails at any step, ask AI to revise
			- include original problem description, faulty solution, feedback from linter, unit tests + error 
		- only examples passing all checks included in final SFT dataset 

> [!NOTE] Llama 3's innovative synthetic data pipeline
> - use AI to generate problem descriptions
> - use AI to generate solutions to each problem in different languages
> - use AI to generate unit tests to test the generated code 
> - prompt AI to fix errors in the new code 
> - use AI to translate the code to other languages, keeping only those that pass unit tests 
> - use AI to generate conversations, explanations, documentation about the code
> 	- keeping only that that pass back-translation verification 

### 2.3.2 Data Verification
- synthetic data quality can be judged similar to other AI outputs $\rightarrow$ functional correctness + LLM-judges
	- above shown how Llama 3 used functional correctness heavily 
	- can also use AI verifiers - small specialised or large LLM judge 
- with LLM-judges, can describe quality requirements + instruct model to determine if example meets them 
	- e.g. detecting for hallucinations and filtering those out 
	- can also try create very similar data by measuring if AI can detect difference between real and synthetic 
		- if easy to differentiate, new synthetic data is not good 
- can also filter poor quality data via heuristics 
	- e.g. too short or long for your application 
	- e.g. filtering out using keywords, users, creation date, metadata, sources 
	- <span style="color:rgb(179, 179, 179)">Self-Instruct, 2022</span> used following heuristics 
		- repetitive examples, length requirements, examples with same instruction but different outputs, outputs that are repetition of the input 
### 2.3.3 Limitations to Synthetic Data 
- <span style="color:rgb(255, 136, 0)">quality control</span> - hard to use if we cannot verify quality, little metrics available to test for this 
	- might also perpetuate biases of the LLM creating the data 
- <span style="color:rgb(255, 136, 0)">superficial imitations</span> - imitations are not truly useful, often struggling with factual accuracy or beyond task generalisation
	- even worse - can hallucinate or give wrong answers 
- <span style="color:rgb(255, 136, 0)">potential for model collapse</span> - some studies shown training recursively on synthetic AI data can irreversibly damage the model 
	- likely due to the probability distribution of tokens, phrases, events
		- with each training run, low-probability events are drowned out and missed 
	- <span style="color:rgb(179, 179, 179)">Gerstgrasser et al 2024</span>, showed you can avoid this by mixing it with real data 
- <span style="color:rgb(255, 136, 0)">lineage obscurity</span> - can regurgitate user pre-training data without warning 
	- might cause copyright/IP concerns 
## 2.4 Model Distillation
- <mark style="background: #FFB8EBA6;">model distillation</mark> = method where small student model trained to mimic larger teacher model 
	- aka knowledge distillation introduced by <span style="color:rgb(179, 179, 179)">Hinton, 2015</span>
	- very useful since the smaller, faster student model can often retain performance comparable to the teacher
		- e.g. DistilBERT = 40% size of BERT but with 97% of the performance, and 60% faster
- common pattern is to create synthetic instruction data with adapter-based techniques e.g. LoRA 
	- allows you to greatly reduce inference cost + latency 
- model distillation however, assumes the teacher's performance is the gold-standard 
	- **model bootstrapping w reverse instruction** = can also use smaller models to help train larger model
- however - as stated in Llama 3 paper, only by introducing mechanism to verify quality of synthetic data
	- they were able to continually improve model using it's own generated data

# 3 Data Processing
- 💡 very useful tips when working with large datasets 
	- **try quicker steps first** e.g. deduplicate before annotating
	- **always do trial runs to validate processing scripts** work as expected before applying to entire dataset
	- **avoid changing data in place**
		- keep copies of original data - in case of bugs + for others to reproduce 
## 3.1 Inspect Data
- first step to inspect data + get sense of the quality - 💡 some tips
	- via collecting information + statistics e.g. where it comes from, how was it processed, what has it been used for?
	- plot distribution of tokens, input lengths, response lengths
	- what special tokens are included
	- topic and language distributions 
- can be creative in understanding your data 
	- e.g. <span style="color:rgb(179, 179, 179)">Microsoft, 2023</span> plotted distribution of `verb, direct-object, noun` pairs and response length to compare GPT-3 to GPT-4 generations

![[Screenshot 2025-01-06 at 8.21.03 pm.png| center | 600]]

- plot distributions by data source, time, annotator etc 
	- any patterns for groups of these e.g. scores for longer/shorter responses?
	- any outliers? what could be causing them + how should they be handled 
	- what distribution should they follow? 
- for annotations - do some annotators have biases?
	- e.g. much shorter/longer, specific language, tendency towards scores 
	- very useful to compute inter-annotator disagreement e.g. Cohen's Kappa, Spearman Correlation
		- check examples with conflicting annotations + resolve those conflicts 

> [!NOTE] Best thing to do when starting - just spend 15 mins inspecting your data manually!

## 3.2 Deduplicate Data
- duplicated data can skew distribution + introduces biases into the model 
	- ensure there are no duplicates between train and test 
		- <span style="color:rgb(179, 179, 179)">Anthropic, 2022</span> found duplicating 0.1% of the data 100 times i.e. 10% can cause model to get performance of a model half it's size i.e. 800M model degrades to performance of a 400M model
	- duplicates hurt not just performance, but compute + training time too 
- types of duplications 
	- whole document duplications - same documents appears more than once
	- intra-document duplications - same paragraph appears twice in same document
	- cross-document duplications - same quote appears in many documents 
- methods to deduplicate data 
	- <mark style="background: #FFB86CA6;">pairwise comparisons</mark> = compute similarity score to all other examples 
		- e.g. via exact match, n-gram match, fuzzy match, embedding similarity
		- can be expensive for large datasets
	- <mark style="background: #FFB86CA6;">hashing</mark> = hash examples into different buckets + check examples falling into same bucket 
	- <mark style="background: #FFB86CA6;">dimensionality reduction</mark> = reduce dimensionality first, then do pairwise comparisons
		- or manual inspection for higher level topic analysis 
	- many libraries available to help with deduplication too e.g. `dupeGuru`, `Dedupe`, `datasketch`, `TextDistance`, `TheFuzz`
## 3.3 Clean and Filter Data
- clean data is required for making sure models perform well + are safe 
	- manual inspection is also very important 
- first - remove any extraneous formatting tokens 
	- e.g. <span style="color:rgb(179, 179, 179)">Databricks</span> found removing rubbish HTML/Markdown tokens improved model accuracy by 20% + reduced input tokens 60%
	- need to clean for anything that is non-compliant e.g. PII, sensitive data, copyrighted data, toxic data 
- can also perform filtering using heuristics to detect low-quality data 
		- e.g. <span style="color:rgb(179, 179, 179)">Kern et al, 2024</span> found annotations in 2nd half of sessions were lower quality due to fatigue 
- smarter filtering methods when you have too much data
	- <mark style="background: #FFB8EBA6;">active learning</mark> = find examples most helpful for model to learn from
	- <mark style="background: #FFB8EBA6;">importance sampling</mark> = find examples most important to the task 
## 3.4 Format Data
- after deduping + cleaning data, need to get it in correct format required for the model
	- **each model uses specific tokenizer + expects data in specific chat template**
	- getting wrong format/chat template can cause bugs in the model 
- for SFT, data will need to be in `instruction, response`
	- can further decompose into `system prompt, user prompt, response` format 
	- finetuning instructions can also be less verbose than normal prompt engineering since they will learn from examples directly
- different finetuning data formats can impact finetuned model's performance
	- experiment with different formats to see what works best

# 4 Summary 
- To build a dataset to train a model, you start by thinking through the behaviours you want your model to learn and then design a dataset to show these behaviours
- While how much data a model is trained on grabs headlines, having high-quality data with sufficient coverage is just as important
- Just like real data, synthetic data must be evaluated to ensure its quality before being used to train models
- Data is challenging because many steps in dataset creation aren’t easily automatable. It’s hard to annotate data, but it’s even harder to create annotation guidelines
	- even harder to automate verifying it 
- so many ways people construct and evaluate data
