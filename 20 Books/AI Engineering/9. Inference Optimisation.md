# 1 Understanding Inference Optimisation
- new models come and go - but people always want to make them better, cheaper faster 
	- inference optimisation can be done at 3 levels
		- model
		- hardware
		- service
## 1.1 Inference Overview
- inference server = the component that runs model inference in production 
	- hosts the available models + has access to necessary hardware 
- optimisation is all about identifying bottlenecks + addressing them
### 1.1.1 Computational bottlenecks
- 2 types of computational bottlenecks
	- <mark style="background: #FFB8EBA6;">compute-bound</mark> = inference time determined by computation needed
		- can be sped up by spreading out to more chips or more powerful chips e.g. higher FLOP/s
	- <mark style="background: #FFB8EBA6;">memory-bandwidth bound</mark> = tasks constrained by data transfer rate within the system
		- e.g. movement from memory to processors 
		- can be sped up by using chips with higher bandwidth 

![[Screenshot 2025-01-06 at 8.22.09 pm.png| center | 600]]

- different model architectures/workloads have different computational bottlenecks
	- e.g. in transformers there are 2 main steps
		- <mark style="background: #FFB8EBA6;">prefill</mark> = processing input tokens in parallel, limited by number of operations hardware can handle 
			- hence **compute-bound**
		- <mark style="background: #FFB8EBA6;">decode</mark> = model generates output tokens one at a time
			- involving loading large weight matrices onto GPUs - hence **memory bandwidth bound**

![[Screenshot 2025-01-06 at 8.22.20 pm.png| center | 600]]

- the main bottlenecks in prefill + decoding include:
	- context length 
	- output length
	- request batching strategies 
### 1.1.2 Online vs Batch Inference
- API providers often provide 2 methods to inference - online or batch 
	- online optimises for latency (request processed as soon as arrived), batch optimises for cost/throughput
- batch is favoured for use cases with less stringent latency requirements e.g.
	- synthetic data generation
	- periodic reporting
	- onboarding new customers, processing all their docs
	- migrating to new model that requires reprocessing all data
	- generating personalised recommendations/summaries for large customer base
	- knowledge base updates to reindex enterprise data
- online APIs are best for use cases that require real-time responses
	- e.g. customer support chatbots, coding assistants
	- online APIs usually offer streaming mode too - return each token as it is generated 
## 1.2 Inference Performance Metrics
- important to first understand what you are optimising for 
	- for the user - priority is latency 
	- for the system - priority is throughput and utilisation - since they determine cost 
- Latency related metrics include (more important for streaming mode):
	- <mark style="background: #FFB8EBA6;">latency</mark> = measures time from when user send query, till when they receive complete response 
	- <mark style="background: #FFB8EBA6;">time to first token</mark> (TTFT) = how quickly first token is generated after user sends query 
		- corresponds to duration of prefill step + depends on input length
	- <mark style="background: #FFB8EBA6;">time per output token</mark> (TPOT) = how quickly each output token generated after first token 
		- e.g. each token takes 100ms, a response with 1k tokens will take 100 seconds
		- TPOT does not need to be much faster than human reading speed i.e. 120ms/token
			- hence 5-8 tokens a second is sufficient for most use cases
	- <mark style="background: #FFB8EBA6;">time between tokens</mark> & <mark style="background: #FFB8EBA6;">inter-token latency</mark> = measures time between output token
		- variations include time between tokens + inter-token latency 
	- total latency can be computed as below 

$$
\large
\text{Latency} = TTFT + TPOT \times \text{number of output tokens}
$$
- different applications prioritise different metrics 
	- e.g. prefer instant first tokens and longer wait between tokens
	- or slightly longer for first token, but faster for the rest
	- some teams use time to publish as a metric instead - more explicit to measure when user actually first sees it 
- **latency is a distribution - the average can be misleading**
	- hence best to look at latency in percentiles
		- typical to check p90, p95, p99
	- also useful since outliers bound to exist with large volume of requests 
	- also useful to plot TTFT values against input lengths 
### 1.2.1 Throughput & Goodput
- <mark style="background: #FFB8EBA6;">throughput</mark> = number of output tokens per second
	- should count inputs vs outputs separately since prefill vs decode have their own bottlenecks 
	- can also be measured with number of completed requests within a period e.g. Requests Per Second (RPS)
	- throughput also directly linked to compute cost - higher == cheaper 
		- smaller models + better chips usually have higher throughput
- <mark style="background: #FFB8EBA6;">goodput</mark> = number of requests per second that satisfy the SLO/SLA 
	- more useful in context of your applications constraints
		- e.g. you have objective of TTFT <= 200ms and TPOT <= 100ms
		- inference service can do 100 requests per minute
		- however only 30/100 meet the SLO - hence goodput = 30 requests per minute 
### 1.2.2 Utilisation, MFU, MBU
- utilisation metrics measure how efficiently a resource is being used
	- quantifies proportion of resource actively used to total available capacity 
	- e.g. `nvidia-smi` command which shows GPU util is slightly misleading
- <mark style="background: #FFB8EBA6;">MFU - Model FLOP/s Utilisation</mark> = ratio of observed throughput (tokens/s) relative to theoretical maximum of system at peak FLOP/s
- <mark style="background: #FFB8EBA6;">MBU - Model Bandwidth Utilisation</mark> = measures % of achievable memory bandwidth used 
	- e.g. chip with 1TB/s of peak bandwidth operating at 500GB/s = MBU of 50%

$$
\text{Memory Bandwidth for LLM Inference = param count} \times \text{bytes/param} \times \text{tokens/s} 
$$
$$
\text{MBU = } \frac{\text{(parameter count} \times \text{bytes/param} \times \text{tokens/s})}{\text{theoretical bandwidth}} 
$$

- what is a good MFU or MBU depends on hardware, model and workload 
	- compute-bound workloads usually have higher MFU and lower MBU
	- vice versa for bandwidth bound workloads 
- training is often easier to optimise due to batching of workloads
	- hence training MFU usually higher than inference MFU 
	- anything with training MFU of > 50% is considered good, > 70% is considered very good 

![[Screenshot 2025-01-08 at 12.52.46 pm.webp| center | 600]]

> [!NOTE] Higher utilisation not important if cost and latency both increase too!

## 1.3 AI Hardware
- AlexNet, 2014 was first real model to successfully use GPUs + sparked what they can do for deep learning
	- before this, people typically used thousands of CPUs
- <mark style="background: #FFB8EBA6;">AI accelerator</mark> = chip designed to accelerate specific type of computational workflow e.g. AI training
	- NVIDIA GPUs are most common type and one of biggest economic drivers for AI boom 
	- now many other players including AMD, Google TPUs, Groq's LPU and others 
	- an emerging market is specialised chips for inference - since inference accounts for majority of workloads
- CPU vs GPUs
	- CPUs designed for general purpose usage 
		- a few powerful cores (up to 64 for high end consumer machines)
		- can handle multi-threaded workloads, but optimised for high single thread performance 
		- e.g. running OS, handing complex sequential processes 
	- GPUs designed for parallel processing 
		- thousands of smaller, less powerful cores optimised for tasks that can be broken down 
		- these tasks are much smaller independent calculations e.g. matrix multiplication
- chips for training vs inference 
	- training demands much more memory due to backprop + usually needs higher precision
		- training also emphasises throughput 
	- inference instead aims to minimise latency 
		- inference chips also optimised for lower precision + faster memory access 
		- instead of larger memory capacity 
- different hardware is often specialised to different data types + model architectures 
	- e.g. scalars, vectors and tensors 
	- GPUs were traditionally designed for vector operations, now many include tensor + matrix cores
	- e.g. Google TPU primarily uses tensors as their compute primitive 

![[Screenshot 2025-01-06 at 8.22.42 pm.png| center | 600]]

### 1.3.1 Computational Capabilities
- compute capabilities typically measured by number of operators a chip can perform within a period
	- FLOP/s = measures peak number of floating-point operations per second 
	- depends on precision, higher precision == lower FLOPs
### 1.3.2 Memory size & Bandwidth 
- GPUs have many parallel cores - hence data needs to move from memory to these cores
	- so data transfer speed (bandwidth) is important 
	- GPU memory has higher bandwidth + lower latency vs CPU memory 
	- GPU memory is also more expensive because of this 
- 3 levels of memory within a GPU 
	- <mark style="background: #FFB8EBA6;">CPU memory (DRAM)</mark> = lowest bandwidth amongst all 3 - 25gb/s to 50gb/s 
		- CPU memory sizes vary, consumer laptops usually have 16-64GB
	- <mark style="background: #FFB8EBA6;">GPU High-Bandwidth Memory (HBM)</mark> = the memory dedicated to the GPU
		- located very close to the GPU for faster access
		- has significantly higher bandwidth - 256gb/s to over 1.5TB/s
		- consumer GPUs usually have around 24-80gb of HBM 
	- <mark style="background: #FFB8EBA6;">GPU on-chip SRAM</mark> = integrated directly on the chip, stores frequently accessed data/instructions instantly 
		- includes L1 + L2 caches and has extremely high data transfer speeds
		- fastest of 3 - usually exceeding 10TB/s
		- size of SRAM is very small, usually 40mb and under 

![[Screenshot 2025-01-06 at 8.22.54 pm.png| center | 600]]

- most GPU optimisations based on optimising these 3 levels e.g. FlashAttention
	- `PyTorch` and `TensorFlow` right now do not support granular access of memory control
	- need to use specialised GPU programming languages e.g. <span style="color:rgb(179, 179, 179)">NVIDIA CUDA</span>, <span style="color:rgb(179, 179, 179)">OpenAI Triton</span>, <span style="color:rgb(179, 179, 179)">AMD ROCm</span>
### 1.3.3 Power Consumption 
- chips use transistors to do computations - binary switches which require energy
	- 1 chip can have billions of transistors e.g. NVIDIA A100 has 54 billion, H100 has 80 billion 
	- these produce lots of heat + use power and need cooling 
- e.g. NVIDIA H100 running at peak for 1 year uses 7000 kWh
	- average US household annual electricity consumption = 10,000 kWh
	- hence power consumption + electricity is a bottleneck to scaling up compute 
### 1.3.4 How to Pick a GPU 
- 3 main numbers you should look at that tell you most of the story 
	- FLOP/s
	- memory size
	- memory bandwidth

# 2 Inference Optimisation Techniques 
- recall 3 levels to try and optimise for inference - model, hardware, service level 
	- model optimisation is like crafting better arrows
	- hardware optimisation is like creating stronger + better archers 
	- service optimisation like refining the entire shooting process, bow, aiming conditions 
- optimisation techniques usually involve techniques at more than 1 level 
## 2.1 Model Optimisation
- model-level optimisation = make model more efficient by modifying model itself which can also alter behaviour 
	- almost all LLMs today based on transformer - and it's autoregressive nature
	- inference is resource-heavy for transformers due to 3 characteristics:
		- <span style="color:rgb(255, 136, 0)">model size</span>
		- <span style="color:rgb(255, 136, 0)">autoregressive decoding</span>
		- <span style="color:rgb(255, 136, 0)">attention mechanism</span> 
- below are different strategies for optimising each of these 
### 2.1.1 Model Size Optimisation 
- **model compression** = techniques to reduce a model's size, includes distillation and quantisation 
- **model distillation** = trying to compress the capabilities of a large model into a smaller model 
	- <mark style="background: #FFB8EBA6;">pruning</mark> = method to capture the best subset of model parameters from a large model that retain it's abilities 
	- pruning neural networks can involve either removing entires nodes of the network, or setting them to 0 (sparse)
		- both aim to reduce number of non-zero params to speed up + reduce memory of model 
	- pruning can also help discover promising model architectures 
		- e.g. smaller subsets that can be further finetuned or trained from scratch 
- <mark style="background: #FFB8EBA6;">model quantisation</mark> = most popular approach, easy to use, very flexible and extremely effective 
	- involves reducing precision for the model's parameters e.g. 32bit to 16bit - reduces memory by 50%
	- however, we are close to limit of quantisation - cannot go lower than 1 bit per value 
### 2.1.2 Autoregressive Decoding Optimisation
- recall LLMs are autoregressive - generate one token after another - this can be slow + expensive process
	- for API providers, output tokens usually 2x-4x cost of an input token 
	- i.e. decoding much more expensive than prefilling 
	- multiple techniques have been developed to address this, maybe one day a new architecture removes it entirely 
- <mark style="background: #FFB8EBA6;">speculative decoding</mark> = aka speculative sampling, uses faster/less powerful model to generate sequence of tokens
	- then verified by **target model**, the faster model called the **draft/proposal model** 
	- if draft sequences rejected, target model generates the entire response on it's own 
	- however, has some extra optimisations
		- verification is parallelisable hence quick - turns time complexity to that of prefilling 
		- some output tokens easier to predict than other - so draft model can get these right 
		- decoding is memory bandwidth bound, so in prefill, idle FLOPs can give free verification

$$
\begin{gather}
\textbf{Speculative Decoding Process} \\ \ \\
1. \text{ Draft model generates sequence of K tokens } x_{t+1}, x_{t+2}, ... \\ \ \\
2. \text{ Target model verifies these K generated tokens in parallel} \\ \ \\
3. \text{ Target model accepts longest subsequence of draft tokens} \\ \ \\
4. \text{ after accepting K draft tokens, Target model generates one extra token} \\ \ \\
5. \text{ returns to step 1 and repeats}
\end{gather}
$$
- speculative decoding has become popular + implemented into many inference frameworks
	- e.g. PyTorch, vLLM, llama.cpp
- <mark style="background: #FFB8EBA6;">inference with reference</mark> = for responses that copy some of the inputs, just copy them instead of regenerating
	- e.g. filling up a code snippet, adding fields to a template etc 
	- instead of using draft model for candidate tokens, uses the input to do so 
		- really only useful for scenarios with significant overlap between context + outputs 
		- e.g. retrieval systems, coding, multi-turn conversations
	- challenge is in creating algorithm to find most relevant text span from context at each decoding step 
		- simplest approach = find text span that matches current tokens 
- <mark style="background: #FFB8EBA6;">parallel decoding</mark> = focuses on breaking sequential dependency, generate multiple tokens simultaneously 
	- so model will generate $x_{t+2}$ before it knows or at same time as $x_{t+1}$
		- effectively works since existing sequence is often enough to predict new *few* tokens
	- parallel tokens can be generated by same decoder or different decoding heads 
		- however still needs verification to ensure they fit together 
		- <span style="color:rgb(179, 179, 179)">Lookahead decoding by Fu et al 2024</span> uses this process:
			- known as Jacobi method/decoding

$$
\begin{gather}
\textbf{Lookahead Parallel Decoding} \\ \ \\
1. \text{ K future tokens generated in parallel}  \\ \ \\
2. \text{ K tokens verified for coherence/consistency with context}  \\ \ \\
3. \text{ If any token fails, regenerate the failed tokens }  
\end{gather}
$$
### 2.1.3 Attention Mechanism Optimisation
- recall, in decoding - generating each token requires $key$ & $value$ vectors for all previous tokens
	- rather than recompute them each time, you can cache the most recent ones 
	- <mark style="background: #FFB8EBA6;">KV cache</mark> = cache that stores key & value vectors for re-use
	- note: KV cache only used in inference, not training

![[Screenshot 2025-01-06 at 8.23.22 pm.png| center | 600]]

- attention has quadratic time complexity - $O(n^2)$ where $n$ = sequence length 
	- since one decoding step needs to compute attention scores of all previous tokens 
	- KV Cache instead grows linearly with sequence length 
		- however KV Cache size also grows with larger batch sizes 

$$
\begin{gather}
\large
\textbf{Calculating KV Cache Size} \\ \ \\
\large= 2 \times \text{Batch Size} \times \text{Sequence Length} \times \text{Num. Transformer Layers} \times \text{Model Dimension} \times \text{Byte/Param}
\end{gather}
$$

> [!NOTE] example KV cache size calculation for Llama 2 13B 
> - Num. Transformer Layers = *40*
> - Model Dimension = *5,120*
>- Batch Size = *32*
>- Sequence Length = *2,048*
>- Bytes per Param = *2*
>  
 Memory Needed for KV Cache = $2 \times 32 \times 2,048 \times 40 \times 5,120 \times 2 = 54$GB 

- 3 methods have been designed to make attention more efficient 
	- <mark style="background: #FFB86CA6;">redesigning attention mechanism</mark>
	- <mark style="background: #FFB86CA6;">optimising KV cache</mark> 
	- <mark style="background: #FFB86CA6;">writing kernels for attention computation</mark> 
- redesigning attention mechanism 
	- <span style="color:rgb(255, 136, 0)">local windowed attention</span> = attends to only fixed size window of nearby tokens 
		- can be interleaved with global attention
	- <span style="color:rgb(255, 136, 0)">cross layer attention</span> = reduces number of KV pairs, shares across adjacent layers
	- <span style="color:rgb(255, 136, 0)">multi-query attention</span> = reduces number of KV pairs, shares across query heads
	- <span style="color:rgb(255, 136, 0)">grouped query attention</span> (GQA) =  generalisation of multi-query attention 
		- groups query attention heads into smaller groups + shares KV pairs only among query heads in same group 
- optimising KV cache size 
	- <span style="color:rgb(255, 136, 0)">PagedAttention</span> = divides KV cache into non-contiguous blocks, reduces fragmentation + shares memory 
	- <span style="color:rgb(255, 136, 0)">KV Cache Quantisation</span>
	- <span style="color:rgb(255, 136, 0)">adaptive KV Cache compression</span>
	- <span style="color:rgb(255, 136, 0)">selective KV Cache</span>
- writing kernels for attention operation
	- most effectively done when considering hardware that will execute the computation
		- requires very deep understanding of hardware architecture 
		- also very dependent on hardware e.g. need to update kernels for new hardware releases 
	- <mark style="background: #FFB8EBA6;">kernel</mark> = code optimised for a specific chip 
		- e.g. matrix multiplication, attention computation, convolutions 
	- <span style="color:rgb(255, 136, 0)">FlashAttention</span> - most well known kernels optimised for Attention
	- common types of kernel operations to optimise computations
		- **vectorisation** = process multiple contiguous data elements simultaneously to reduce latency and data I/O operations
		- **parallelisation** = split input arrays into independent chunks so multiple cores or threads can process them in parallel, speeding up computations
		- **loop tiling** = reorganise loop data access to suit the hardware’s memory layout and cache, which is hardware-dependent
		- **operator fusion** = merge multiple operators into a single pass to minimize redundant reads and writes, requiring in-depth knowledge of the model’s specific operators
## 2.2 Inference Service Optimisation
- most of the service-level optimisations focus on resource management 
	- i.e. given fixed compute + memory with dynamic workloads, how to efficiently allocate them to optimise cost/latency 
- <mark style="background: #FFB8EBA6;">batching</mark> = one of easiest ways to reduce cost, group seperate requests + process at once 
	- static batching = group fixed number of inputs in a batch then process
	- dynamic batching = set maximum time window for each batch 
		- so you process some at each interval rather than wait to fill up allocated spots
	- continuous batching = return response as soon as batch completed
		- selectively batches operations that don't cause sequential dependencies 
- <mark style="background: #FFB8EBA6;">decoupling prefilling and decoding</mark> = split decode + prefill to different machines 
- <mark style="background: #FFB8EBA6;">prompt caching</mark> = stores overlapping segments for re-use to avoid re-computing them 
	- e.g. system prompts 
	- prompt caches only need to process the first query then store them for later use 
	- very useful for applications with long system prompts - can reduce cost and latency 
		- only have to pay little extra fro cache storage e.g. $1 per million tokens per hour
		- e.g. Anthropic's caching effects below 

| Use case                                                   | Latency w/o caching (time to first token) | Latency with caching (time to first token) | Cost reduction |
|------------------------------------------------------------|-------------------------------------------|--------------------------------------------|----------------|
| Chat with a book (100,000-token cached prompt)            | 11.5 s                                     | 2.4 s (−79%)                                | −90%           |
| Many-shot prompting (10,000-token prompt)                 | 1.6 s                                      | 1.1 s (−31%)                                | −86%           |
| Multi-turn conversation (10-turn convo with a long system prompt) | ~10 s                                      | ~2.5 s (−75%)                               | −53%           |

- <mark style="background: #FFB8EBA6;">parallelism</mark> = split into 2 families - data and model parallelism 
	- LLMs have also had specific parallelism strategies developed e.g. context + sequence parallelism 
		- often combines multiple strategies 
	- model parallelism = split same model across machines 
	- context parallelism = input sequence split across machines, processed separately 
	- sequence parallelism = operators needed for entire input split across machines e.g. attention on machine A, FFNN on B
