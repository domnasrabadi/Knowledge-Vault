# 1 Understanding Kinds of LLMs
- LLM providers come in different forms
	- AI labs providing proprietary LLMs
		- OpenAI, Anthropic, Google, Mistral 
	- Labs providing Open Source LLMs
		- DeepSeek, Meta, Cohere, Google, Mistral
	- Self organising collectives + research orgs 
		- EleutherAI
	- Academia and government 
- models usually come in multiple variants when released
	- sizes e.g. 7B, 13B, 70B
	- model types e.g. instruct, chat, long-context, domain-specific 
		- often trained via RLHF, RLAIF, Constitutional AI 
		- no free lunch w long context - lost in middle problem
- what is open source
	- <mark style="background: #FFB8EBA6;">open source</mark> = released under license allowing users to study, use, modify, redistribute to anyone for any purpose 
	- for an LLM to be considered fully open, OS Initiative needs the following to be published
		- <span style="color:rgb(255, 0, 247)">model weights</span>: all model params + config setting
			- allowing modifications + updates to the model
			- recommended to also release checkpoints from various training phases 
		- <span style="color:rgb(255, 0, 247)">model code</span>: training scripts, hyperparam configs, data pre-processing code
			- comparable to providing source code vs just the binary
			- sharing details on infrastructure + setup best for reproducibility but not foolproof
		- <span style="color:rgb(255, 0, 247)">training data</span>: dataset used for training, details on how it was sourced 
			- ideally info or code re pre-processing steps + order of data feeding
	- training data often the competitive advantage and hence often not released 
		- also often might be legal issues involved around copyright
	- for practitioners, best to use LLMs with permissive licenses for commercial use
		- e.g. Apache 2.0 and MIT 
# 2 How to Choose an LLM for your Use-Case
- some considerations
	- cost: expenses for inference, fine-tuning, software scaffolding, monitoring, deployment, and maintenance
	- time per output token (TPOT): speed of text generation as experienced by the end user
	- task-performance: performance requirements using metrics like precision and accuracy for your needs
		- specific tasks the LLM will perform, such as summarization, question answering, or classification
	- capabilities required: if the model can handle tasks that require skills like arithmetic reasoning, logical reasoning, planning, and task decomposition
		- some might only work with larger models
	- licensing: allows for your intended usage, keeping in mind restrictions on certain applications
- LLM evaluation currently done in several different ways, examples
	- EleutherAI LM Eval Harness
		- supports benchmarking on over 400 different benchmarks
		- varied skills e.g. open QA, arithmetic, reasoning, linguistic tasks, translation, toxicity detection etc 
	- 🤗 Open LLM Leaderboard
		- combines 6 key benchmarks, takes average
	- HELM by Stanford
		- wide variety of metrics (59) across many tasks 
	- ELO Rating
		- used in chess to rank players, used by LMSYS Org Chatbot Arena
		- users choose best response, takes ranking aggregated - however has many human biases at play
			- e.g. prefer longer texts, overlook subtle factual issues, indecisiveness, order
- why benchmark evals can be unreliable
	- many ways you can eval a task e.g. MMLU using multiple choice answers
	- options to eval include
		- pick token w highest output probability from A, B, C, D
		- pick token w highest output probability from entire vocab + use that to match to the answer
		- produce normalised sum of probabilities of token sequence, followed by label with correct answer
	- each can produce vastly different result, lead to different leaders - noticed by Huggingface when reproducing 3rd party evals
	- when interpreting evals in papers, try to methodologically ask as many questions as possible
		- seeing if they are answered by the authors
		- e.g. what does data look like? do we have access? how difficult? what % are difficult? what scenarios covered?
- robust evals further complicated by sensitivity to prompts + probabilistic nature 
# 3 Loading LLMs
- LLMs can be loaded in different precisions + impact memory requirements
	- <span style="color:rgb(255, 0, 247)">Float32 (FP32)</span> = 32bit FP rep, each param takes 4 bytes of storage
	- <span style="color:rgb(255, 0, 247)">Float16 (FP16)</span> = 16bit rep, comes with under/overflow problems for very large/small numbers
	- <span style="color:rgb(255, 0, 247)">bfloat16 (BF16)</span> = like FP16 but helps with under/overflow 
	- <span style="color:rgb(255, 0, 247)">Int8</span> = 8bit rep, usually 20% slower than running FP16
	- <span style="color:rgb(255, 0, 247)">FP8, FP4</span> = 8bit + 4bit floating point representation
- libraries + applications people use
	- accelerate library by huggingface - splits between GPU and CPU 
	- Ollama - allows local usage w many open models
	- usual inference APIs
# 4 Decoding Strategies
- Greedy decoding = simplest form, pick token with highest probability 
	- leads to repetitive outputs 
	- not suitable unless generating really short sequences e.g. classification
- Beam search = picks top $n$ probs, generates continuations for those and picks highest cumulative prob 
	- $n$ i.e. beam size is key hyperparam
	- below shows how to use beam search in `transformers` library

```python
output = model.generate(
	**inputs, 
	max_new_tokens=50, 
	num_beams = 3          # num_beams is n
)
print(tokenizer.decode(output[0], skip_special_tokens=True))
```

- top-k sampling = sample from distribution of just $K$ tokens from output distribution with highest prob 
	- probability mass redistributed over $K$ tokens + model samples from this
	- `transformers` library uses as below 

```python
output = model.generate(
	**inputs, 
	max_new_tokens=50, 
	do_sample=True, 
	top_k=40
)
print(tokenizer.decode(output[0], skip_special_tokens=True))
```

- top-p sampling = like top-k but makes candidate tokens dynamic 
	- choosing smallest number of tokens whose cumulative distribution exceeds given probability $p$

```python
output = model.generate(
	**inputs, 
	max_new_tokens=50, 
	top_p=0.9
)
print(tokenizer.decode(output[0], skip_special_tokens=True))
```

# 5 Running Inference
- LLM outputs not consistent, different for multiple generations across same prompt 
	- unless using greedy, fixed seed, always sampling from a distribution
- structured outputs often done via providing a JSON schema
	- model tries to adhere to schema with output, usually best with larger models
		- other packages include LMQL and Guidance
	- <span style="color:rgb(255, 0, 247)">restricting output to finite token set</span> = useful for classification
	- <span style="color:rgb(255, 0, 247)">controlling output format via regex</span> = enables to specify custom formats e.g. date types
	- <span style="color:rgb(255, 0, 247)">controlling output format via context-free-grammars (CFG)</span> = defines rules that strings must follow 
		- effective for sequence tagging tasks e.g. NER
# 6 Model Debugging & Interpretability
- LIT-NLP from Google helpful to show model behaviour + debugging
	- Visualization of the attention mechanism
	- Salience maps, which show parts of the input that is most paid attention to by the model
	- Visualisation of embeddings
	- Counterfactual analysis - how your model behaviour changes after a change to input e.g. adding/removing a token
- Anthropic Mechanistic Interpretability 
	- introduced notion of features = linear combinations of multiple neuron activations 
	- more interpretable to do this than single neuron, since each neuron represents 1 feature (monosemanticity)
