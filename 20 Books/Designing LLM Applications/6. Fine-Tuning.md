# 1 Why Finetune
- LLMs can adhere to only a finite set of instructions in the prompt
	- and its effective context window is much smaller than the advertised context window
- can accomplish tasks that can't be done by ICL via finetuning
	- by providing a dataset of input-output pairs, such that the model learns the input-output mapping by updating its weights
	- fine-tuning the model massively improves performance
- Leveraging your domain expertise and knowledge of intended use cases to construct the dataset can be highly effective 
	- author - "at my company, which specialises in the financial domain, this technique delivered the single largest boost in performance"
# 2 Finetuning Workflow
- many libraries exist today to make FT easier
	- `{python}transformers`, `{python}accelerate`, `{python}peft`, `{python}trl`, `{python}bitsandbytes`
		- most are quite new so will change quite rapidly 
	- `{python}datasets` library also very good to handle training + FT datasets
		- also abstractions for efficiently handling large datasets
- in transformers, the `Trainer` & `TrainingArguments` class is the main way
	- `TrainingArguments` has 117 arguments available - we will cover just most important
	- e.g. learning algos, memory + space optimisations, quantisation, regularisation, distributed training 
## 2.1 Learning Algorithms
### 2.1.1 Optimisers
- optimisers are very key for backprop 
	- most common are **AdamW** and **Adafactor**
	- others include SGD, RMSProp, Adagrad, Lion
- memory requirements for optimisers
	- **SGD**, **Adafactor** - 4 bytes per parameter
	- **AdamW** - 8 bytes per parameter 
		- e.g. 7B model with full FT = $7^8$ = 56GB of memory to store optimiser states alone
		- even more needed to store params, gradients, forward activations 
	- 8-bit optimisers recently introduced to perform quantisation of optimiser state
		- recall, 8-bits = 1 byte 
		- so AdamW 8-bit needs only 14gb memory for optimiser state 
		- available via bitsnbytes library + supported by 🤗
	- default optimiser in HF is AdamW
		- for RL, SGD seems to work well
		- 8-bit AdamW good choice if memory constrained
```python
from transformers import TrainingArguments
optim = 'adamw_bnb_8bit'

```
### 2.1.2 Learning Rates + Learning Rate Schedulers
- for each optimiser, certain learning rates shown to be very effective
	- AdamW best with 1e-4 and weight decay of 0.01 
		- weight decay = regularisation technique to avoid overfit 
		- default values for other optimiser params also quite good e.g. `adam_beta1`, `adam_beta2`, `adam_epsilon`
- towards end of training, ideally want to lower the learning rate to avoid overshooting convergence 
	- likewise, want less learning at the very start to avoid overfitting to first few batches
	- <mark style="background: #FFB8EBA6;">learning rate schedules</mark> = automatically adjust learning rate when training progresses
- 🤗 supports multiple types of schedulers
	- <span style="color:rgb(255, 0, 247)">Constant</span> = vanilla version, LR remains constant throughout training
	- <span style="color:rgb(255, 0, 247)">Constant with Warmup</span> = LR starts from zero, increased linearly toward specified LR during warmup phase
		- remains constant after warmup phase complete 
	- <span style="color:rgb(255, 0, 247)">Cosine</span> (Cosine Annealing) = LR has warmup phase, then slowly declines to zero per cosine function
	- <span style="color:rgb(255, 0, 247)">Cosine with Restarts</span> (Cosine Annealing w Warm Restarts) = after warmup, LR decreases to zero with cosine function
		- but undergoes several hard restarts where LR shoots back to specified LR after reaching zero 
	- <span style="color:rgb(255, 0, 247)">Linear</span> = similar to cosine, except LR decreases to 0 linearly rather than cosine function

![[Screenshot 2025-02-08 at 12.49.35 pm.webp| center | 600]]
- for AdamW, use schedulers with warmup phase 
	- to prevent getting trapped in bad minima 
	- empirically found that cosine annealing outperforms linear decay 
```python
optim = "paged_adamw_32bit"
learning_rate = 3e-4
weight_decay = 0.01
lr_scheduler_type = 'cosine'
warmup_ratio = 0.03  #The proportion of training steps to be used as warmup
```

## 2.2 Memory Optimisation
- <mark style="background: #FFB8EBA6;">gradient checkpointing</mark> = in forward pass of backprop, activations computed + stored in memory to be used in backward pass 
	- saves memory at cost of more compute - allows you to train w batch sizes that are too big for memory 
	- can do this partially too, recomputing missing activations on the fly 
- <mark style="background: #FFB8EBA6;">gradient accumulation</mark> = simulates a larger batch size by calculating gradient updates after several batches by summing or averaging 
	- can make training slower, but simulates bigger batch sizes 
- <mark style="background: #FFB8EBA6;">quantisation</mark> = reducing precision of parameters to reduce memory footprint 
	- e.g. using `bf16` - sound tradeoff between memory savings + performance 
```python
gradient_accumulation_steps = 4
bf16 = True
gradient_checkpointing = True
```
## 2.3 Regularisation
- **well calibrated model = correlation between output probability + task accuracy**
	- e.g. model that produces output prob of 0.9 - then 90% of these should be correctly classified 
	- output probability should accurately reflect the confidence in classification decision 
- **model being well-calibrated implies it is not overconfident** 
	- helps in nuanced handling of examples w low output probabilities 
	- e.g. passing those examples to a bigger model 
- <mark style="background: #FFB8EBA6;">label smoothing</mark> = regularisation technique to prevent model from becoming overconfident by “softening” the hard one-hot labels
	- usual training involves training against hard target labels (e.g. 0 or 1 for binary classification)
		- using cross-entropy for loss func, pushes model logits closer to 0 or 1 
		- making model highly confident 
	- label-smoothing involves using regularisation term that is subtracted or divided from the hard target label 
		- instead of assigning a probability of 1 to the correct class and 0 to the others, 
			- you assign a slightly lower probability (e.g. `0.9`) to the correct class 
			- and distribute the remaining probability mass (e.g. `0.1`) among the other classes
		- combats overfit + aids model calibration 
	- especially useful when input dataset is noisy 
		- e.g. has some inaccurate labels 
		- prevents model from learning too much from incorrect examples

## 2.4 Noise Embeddings
- finetuning datasets generally small in size e.g. < 50k rows
	- don't want to overfit on stylistic characteristics e.g. formatting, wording, length
- can address via adding noise to input embeddings 
	- studies shown this reduces tendency to overfit on stylistic parts
		- empirically found to be very effective in reducing overfit 
	- side effect = generates longer/verbose-r texts
		- measured via token diversity of outputs - longer text actually more informative, not just repetitive 
```python
# Label 0 will be transformed to label_smoothing_factor/num_labels
# Label 1 will be transformed to 1 - label_smoothing_factor +
#label_smoothing_factor/num_labels

label_smoothing_factor = 0.1
neftune_noise_alpha = 5
```
## 2.5 Batch Size
- <mark style="background: #FFB8EBA6;">batch size</mark> = 2nd most important hyperparam after learning rate 
	- larger batch size == faster training 
	- but also requires more memory 
	- sometimes large batch sizes can also lead model to land in sharp local minima (overfit)
- batch size should always be a number that is a power of 2 
	- e.g. 2, 4, 8, 16, 32, 64, 128 ... largely due to how memory is organised in chips 
- batch size + learning rate relationship - extremely complex and depends on other factors e.g. architecture 
	- LR tips
		- high LR == fewer steps, faster training but at risk of overfit 
		- lower LR == more steps, longer training but at risk of narrow sub-optimal minima 
	- batch size tips
		- smaller batches == greater variance between examples in each batch (more noise to gradient estimates) 
			- noise can help escape minima + flavour flatter regions (better generalisation)
		- larger batches == more stable gradient estimates
			- but can lead to convergence in sharper local minima 
	- thus, theoretically - high LR + lower batch size could be more effective for convergence
		- not always true in practice 
- miscellaneous other hyperparameters
	- `max_grad_norm` = used for gradient clipping (to manage exploding grads)
		- it is the threshold for gradient clipping
		- if L2 gradient norm > threshold - then it will be rescaled to `max_grad_norm`
	- `group_by_length` = used to group examples with similar lengths in same batch
		- so padding tokens can be optimised 
	- `max_train_epochs` = number of passes over training dataset
		- usually set to less than 5 to prevent overfitting
```python
max_grad_norm=2
group_by_length=True
max_train_epochs=3
```
## 2.6 PEFT
- can now fill hyperparams for the `{python}peft` library - used for parameter-efficient fine-tuning
	- update small proportion of params in model while still getting good performance gains 
	- mainly uses LoRA techniques 
- some LoRA hyperparameters to consider
	- `r` = attention dimension of LoRA
	- `lora_alpha` = alpha parameter in LoRA
	- `lora_dropout` = dropout prob used in layers being tuned (reduces overfit)
	- `layers_to_transform` = specifies layers to apply LoRA transformation to 
- some default recommended values
```python
r = 64
lora_alpha = 8
lora_dropout = 0.1
```
## 2.7 Reduced Precision
- `{python}bitsandbytes` library facilitates working w reduced precision - supported by HF 
- some relevant params to use 
	- `load_in_8bit`/`load_in_4bit` - load model in 4 or 8 bit mode
	- `llm_int8_threshold` - threshold of values beyond which FP16 will be used
		- since int8 quantisation works well only for values < ~5/6
	- `llm_int8_skip_modules` - specify the exceptions for which we do not want int8 quantisation
	- `llm_int8_enable_fp32_cpu_offload` - specifies which parts of model to run in int8 on GPU vs FP32 on CPU
		- useful when model too large to fit on GPU
	- `bnb_4bit_compute_dtype` - sets the computational type, regardless of what the input type is
	- `bnb_4bit_quant_type` - options here are FP4 or NF4 - used to set quant type in the 4 bit layers
```python
use_4bit = True
bnb_4bit_compute_dtype = 'float16'
bnb_4bit_quant_type = 'nf4'
use_nested_quant = False
```
- finally can also use `{python}trl` library (transformers reinforcement learning)
	- provides support for supervised FT 
```python
max_seq_length = 128 # Packing = place multiple instructions in the same input sequence
packing = True
```
## 2.8 The Workflow
```python
# Ensure that the specified versions of these libraries are installed.
!pip install transformers==4.35.0 accelerate==0.24.0 peft==0.6.0
bitsandbytes==0.41.0  trl==0.7.4

from datasets import load_dataset
from transformers import TrainingArguments, BitsAndBytesConfig
from transformers import LlamaForCausalLM, LlamaTokenizer
from peft import PeftModel, LoraConfig
from trl import SFTTrainer

train_params = TrainingArguments(
    optim = "paged_adamw_32bit",
    learning_rate = 3e-4,
    weight_decay = 0.01,
    lr_scheduler_type = 'cosine',
    warmup_ratio = 0.03,
    gradient_accumulation_steps = 4,
    bf16 = True,
    gradient_checkpointing = True,
    label_smoothing_factor = 0.1,
    neftune_noise_alpha = 5,
    per_device_train_batch_size = 8,
    per_device_eval_batch_size = 8,
    max_grad_norm=2,
    group_by_length=True,
    max_train_epochs=3,
    output_dir = '/model_outputs',
    save_steps = 50,
    logging_steps = 10
    )


quantize_params = BitsAndBytesConfig (
    use_4bit = True,
    bnb_4bit_compute_dtype = 'float16',
    bnb_4bit_quant_type = 'nf4',
    use_nested_quant = False
    )


lora_params = LoraConfig (
    r = 64,
    lora_alpha = 8,
    lora_dropout = 0.1
    )

model = LlamaForCausalLM.from_pretrained(
    pretrained_model_name_or_path = 'meta-llama/Llama-2-7b',
    quantization_config=quantize_params,
    device_map='auto'
    )

tokenizer = LlamaTokenizer.from_pretrained('meta-llama/Llama-2-7b')

tune_data = load_dataset("csv", data_files='/path/to/finetune_data.csv')

sft = SFTTrainer (
    model = model,
    args = train_params,
    train_dataset = tune_data,
    tokenizer = tokenizer
    peft_config = lora_params,
    max_seq_length = 128,
    dataset_text_field = 'text',
    packing = True
    )

sft.train()
sft.model.save_pretrained('/path/to/llama-2-it.csv')
```

# 3 Finetuning Datasets
- typical example in a fine-tuning dataset consists of:
	- **instruction** = describes the task and specifies the desired output format
		- contains positive and/or negative examples of the task 
		- can also contain constraints and exceptions to be followed
	- **optional input** = our example is the sentence or paragraph for the model to evaluate
	- **output** = correct answer to the task in the format specified in the instruction
- FT datasets can be multi-task or single-task
	- multi-task good for instruction tuning, and can be used as intermediate step before single task FT 
	- some examples

## 3.1 LLM-Generated instruct data
- constructing these by hand is painstaking
	- LLMs also excel at paraphrasing + synthetic data gen 
- <span style="color:rgb(255, 136, 0)">Self-Instruct</span> + <span style="color:rgb(255, 136, 0)">Unnatural Instructions</span> were some of the first papers to do this
	- both started with seed set of high-quality hand generated examples
	- then via few-shot learning, LLM created more examples with more diversity 
- how to prompt to create instruct data 
	- using an instruction, you can either ask it to generate inputs, outputs or both together
		- beneficial to use combination of these techniques 
	- input-first = LLM asked to generate input instance for given instruction 
		- then subsequently, ask to generate output label for that input - however can lead to class imbalance 
		- with certain labels being overrepresented
	- better idea is to mix w output-first generation
		- ask LLM to generate output label first, then ask it to generate input text that satisfies the label
- <span style="color:rgb(255, 136, 0)">Evol-Instruct</span> proposed structured way to generate synthetic instructions via making controlled edits to the seed examples
	- controls for diversity and relevance to your seed examples well
	- 3 steps 
		- <span style="color:rgb(255, 0, 247)">instruction evolution</span> = seed examples evolved using depth + breadth strategies
			- depth evolution = increasing complexity + difficulty via 5 types of prompts
				- adding constraints
				- increasing reasoning steps 
				- asking deeper questions 
				- asking more specific questions
				- increasing complexity of the input 
			- breadth evolution = increases topic coverage by generating new instruction from same domain as original
		- <span style="color:rgb(255, 0, 247)">response generation</span> = response for evolved instruction is generated 
			- using humans or LLMs
		- <span style="color:rgb(255, 0, 247)">candidate filtering</span> = candidate instances where quality criteria not met are filtered out 
			- can use heuristic or LLM to filter
- been shown to be beneficial to mix some instruct data in pre-training too
