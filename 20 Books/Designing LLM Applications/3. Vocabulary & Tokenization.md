# 1 Intro to Tokenizers + Vocab 
- average english speaker has vocab of 20k to 35k words
	- every language model has it's own vocab - common ranges = 5k to 500k tokens
	- vocab often found in `tokenizer.json` file of LLMs
- each token connected to an input id aka token index 
	- used to have cased vs uncased vocabs e.g. BERT but often have cased is always better 
	- especially when training on huge bodies of text - model can learn distinctive representations for them 
		- e.g. web vs Web
- handling new words is very common - many new words invented over time
	- and millions of domain-specific words 
	- OOV (out of vocab) words usually handled with `<UNK>` unknown tokens 
		- these always have same embedding which is undesirable + often not used in the model 
	- to solve for this, people use subword tokenizers e.g. BPE - most common in LLMs today
- vocab sizes vary broadly 
	- e.g. Llama 3 = 128k, Gemma 2 = 256k
		- multilingual models often have larger vocabs
	- how to find optimal vocab size 
		- larger vocab = fewer number of tokens required to represent a text - more efficient 
		- so for same compute, you get more processed text
		- but as vocab size increases, more rare tokens get deficient representations
	- Tao et al devised scaling laws for vocab sizes
		- optimal vocab size increases as model size + compute size increase
		- note that current models have suboptimal size + can benefit from larger
	- larger models usually more robust to misspellings 
# 2 Tokenizer
- tokenizer has 2 key stages
	- tokenizer pre-training - run over large body of text to generate vocab 
	- processing during training + inference - uses algo to break text sequences into valid tokens 
- process
	1. feed raw text into tokenizer
	2. breaks text into tokens that are apart of the vocabulary 
	3. maps tokens to indices 
	4. sequence of input ids fed into LLMs
	5. and mapped to corresponding embeddings
- in HF, the `encode()` function tokenises + returns token indices 
	- vice versa of this is `convert_ids_to_tokens()` function - ids to words 
- non trivial amount of LLMs failures can be attributed to way text was tokenized 
	- e.g. math with numbers + how many R in strawberry 
	- especially true when target domain different from pre-training domain 
- is it possible to remove tokenization step? 
	- many forays into tokenization free language modelling
		- e.g. CANINE = unicode code-points for inputs, using hashed embeddings to make embedding space smaller
		- ByT5 = byte inputs (259 in total vocab) reducing embedding layer size dramatically
		- CharFormer = also uses bytes, passes to gradient-based subword tokenizer, to construct latent subwords
## 2.1 Tokenization Pipeline 
- Huggingface tokenizers have 4 step pipeline
	1. Normalisation
	2. Pre-tokenisation
	3. Tokenization
	4. Post-processing
- <span style="color:rgb(255, 0, 247)">Normalisation</span> 
	- convert to lowercase (if uncased), strip accents, unicode normalisation

```python
# example of normalisation 
tokenizer = AutoTokenizer.from_pretrained("bert-base-uncased")
print(tokenizer.backend_tokenizer.normalizer.normalize_str('Pédrò pôntificated at üs:-)')
# >>> pedro pontificated at us:-)
```

- <span style="color:rgb(255, 0, 247)">Pre-tokenisation </span>
	- optional step, often doing subword tokenization 
	- very useful in english - common to split on whitespace, but also other parts 
	- see example below - word tokens AND character offsets are returned
		- i.e. to show what word it joins to 

```python
# pre-tokenization
tokenizer = AutoTokenizer.from_pretrained("google/flan-t5-xl")
tokenizer.backend_tokenizer.pre_tokenizer.pre_tokenize_str(
	"I'm starting to suspect - I am 55 years old!   Time to vist New York?")

# ('▁starting', (3, 12)),
# ('▁to', (12, 15)),
# ('▁suspect', (15, 23)),
# ('▁-', (23, 25)),
# ('▁I', (25, 27)),
# ('▁am', (27, 30)),
# ('▁55', (30, 33)),
```

- <span style="color:rgb(255, 0, 247)">Tokenization</span> 
	- main tokenization step e.g. applying the algorithm 
		- examples include BPE, Byte BPE, WordPiece, UnigramLM
	- tokenizer comprises of a set of rules learned in pre-training 
	- how *BPE* works - simplest + most common 
		- training stage
			- normalise + pre-tokenize, recording unique tokens in outputs + their frequency 
			- construct initial vocab of the unique chars making up these tokens 
			- starting here, add new tokens with merge rules
				- merge rule is simple - create new token using most frequent consecutive pair of tokens
				- continue merging until reaching desired vocab size 
		- inference stage
			- once trained, can use algo to divide text into proper subword tokens 
			- then feed text into the model 
	- how *WordPiece* works
		- similar to BPE, instead of frequency approach, uses maximum likelihood 
		- frequency of token pairs in dataset normalised by product of frequency of individual tokens
		- pairs with highest resulting score then merged 
			- so token pairs made up of tokens with individually low frequency get merged first 
		- at inference, merge rules not used, instead for each pre-tokenized token in input
			- tokenizer finds longest subword from vocab in the token + splits on it 
			- e.g. understanding = "*understand*" + "*ing*" 
- <span style="color:rgb(255, 0, 247)">Post-processing</span>
	- where special model-specific tokens added, examples
		- `[CLS]` for classification tokens  
		- `[SEP]` for separation
		- `<PAD>` to indicate padding when input < max seq length
		- `<EOS>` to indicate end of sequence - LLM stops generating after outputting this token
		- `<UNK>` to indicate OOV term
		- `<TOOL_CALL>` and `</TOOL_CALL>` - content between these used as inputs to tool e.g. API/sql 
	- Galactica model by Meta introduced several domain specific tokens + rules to work with specific domains
		- `[START_REF]` and `[END_REF]` for wrapping citations
		- `<WORK>` to wrap tokens making up internal memory 
		- numbers handled by assigning each digit it's own token 
		- `[START_SMILES]`, `[START_DNA]`, `[START_AMINO]`, `[END_SMILES]`, `[END_DNA]`, `[END_AMINO]`
			- for protein sequences, DNA sequences and amino acid sequences 
- 2 popular metrics for evaluating tokenizers 
	- <mark style="background: #FFB8EBA6;">fertility</mark> = measures avg number of tokens needed to represent a dataset 
		- calculated by dividing number of tokens in dataset by number of words in dataset
		- higher fertility = lower compression power of tokenizer 
	- <mark style="background: #FFB8EBA6;">parity</mark> = measure of how fairly tokenizer treats 2 languages
		- calculated by ratio of tokens needed to represent same data in 1 language versus the other 
## 2.2 Domain Specific Tokens
- compression ratios for specific domains often lower since they won't have their own words + get split into multiple tokens 
	- one way to adapt for this = learn good vector representations for domain specific terms
	- can add new tokens to existing tokenizers
	- and continue pre-training the model on domain specific data to learn better representations
		- e.g. example below *"The addition of CAR-T cells and antisense oligonucleotides drove down incidence rates."*
		- before
			- `_The`, `_addition`, `_of`, `_C`, `AR`, `-T`, `_cells`, 
			- `_and`, `_anti`, `s`, `ense`, `__`, `oli`, `gon`, `u`, `cle`, `o`, `t`, `ides`, `_drove`, `_down`, 
			- `_incidence`, `_rates`, `.`, `</s>`
		- after 
			- `_The`, `_addition`, `_of`, `_CAR-T`, `_cells`, 
			- `_and`, `antisense`, `oligonucleotides`, `_drove`, `_down`, 
			- `_incidence`, `_rates`, `.`, `</s>`
		- notice the key medical words now get their own proper tokens 
			- but still need to learn good embedding vectors for these via continual pre-training

```python
from transformers import T5Tokenizer, T5ForConditionalGeneration
tokenizer = T5Tokenizer.from_pretrained("google/flan-t5-large")
model = T5ForConditionalGeneration.from_pretrained("google/flan-t5-large", device_map="auto")

tokenizer.add_tokens(["CAR-T", "antisense", "oligonucleotides"])
model.resize_token_embeddings(len(tokenizer))
```
