# 1 Introduction to embeddings
- keyword search is one way to retrieve data from text datasets
	- limited in effectiveness due to many ways you can express a statement 
	- using a catch-all regex could give many FPs, hence need to move beyond keyword search
- <mark style="background: #FFB8EBA6;">representation learning</mark> = sub-field of machine learning to represent data in a way that captures its meaningful features
	- often in a low dimensional space
	- <mark style="background: #FFB8EBA6;">embedding</mark> = represent text as vectors capturing semantic & pragmatic features
	- based on encoder-only models (BERT, MPNET) often fine-tuned on paraphrase/QA/NLI tasks
```python
from transformers import AutoTokenizer, AutoModel
import torch

tokenizer= AutoTokenizer.from_pretrained("sentence-transformers/msmarco-distilbert-base-tas-b")
model = AutoModel.from_pretrained("sentence-transformers/msmarco-distilbert-base-tas-b")

input = tokenizer(
	"American pizza is one of the nation’s greatest cultural exports",
	padding=True, 
	truncation=True, 
	return_tensors='pt'
)

with torch.no_grad():
	output = model(**input, return_dict=True)
	embedding = output.last_hidden_state[:, 0]
print(embedding)
```
- embedding extraction methods:
    - `<CLS>` token from last layer (eg DistilBERT)
    - <span style="color:rgb(255, 0, 247)">mean pooling across tokens</span> = average is taken across all token outputs in the sequence
    - <span style="color:rgb(255, 0, 247)">max pooling across tokens</span> = maximum value in each dimension across all tokens is taken
    - <span style="color:rgb(255, 0, 247)">weighted mean</span> (more weight to later tokens)
    - <span style="color:rgb(255, 0, 247)">last token output</span> = embedding is just the encoder output of the last token
- quality of token representation depends on pre-training objectives 
	- e.g. BERT’s pre-training objective (next sentence prediction) ensures that the `[CLS]` token is much richer in representation vs RoBERTA
		- RoBERTa = does not use NSP hence start token not as informative
	- trend now is decoder-based models are being used for embeddings
		- longer sequence lengths + larger dimensions e.g. Jina, Cohere, OpenAI Embeddings
# 2 Similarity measures
- common measures: dot product, cosine similarity, euclidean distance

$$
\begin{gather}
\mathbf{u} \cdot \mathbf{v} = \sum_{i=1}^{n} u_i\,v_{i}
\\ \ \\ 
\text{cosine\_sim}(\mathbf{u}, \mathbf{v}) = \frac{\mathbf{u} \cdot \mathbf{v}}{\|\mathbf{u}\|\;\|\mathbf{v}\|} = \frac{\sum_{i=1}^{n} u_i\,v_i}{\sqrt{\sum_{i=1}^{n} u_i^2}\,\sqrt{\sum_{i=1}^{n} v_{i^2}}}
\\ \ \\ 
d(\mathbf{u}, \mathbf{v}) = \sqrt{\sum_{i=1}^{n} (u_i - v_i)^2}
\end{gather}
$$
- note: semantic similarity is underspecified – entities can be similar along some dimensions and different in others
	- Similarity refers to the sameness or alikeness of the entities being compared
	- for the same two entities, some dimensions may be similar, others different
- fine-tuning embeddings helps for specialised domains
	- where token distribution deviates from general purpose data
# 3 Fine-tuning embedding models
- choosing a base model factors
	- performance, model size/speed, embedding dimensions/storage, licensing
- training datasets:
    - <span style="color:rgb(255, 0, 247)">triplets</span> (anchor, positive, negative) – hard negatives preferred over random negatives
	    - most common way to train embedding models 
		    - for given anchor sentence - positive = sentence we want closer, negative = we want further apart 
	    - can choose negatives as random sentences from the corpus 
		    - even better to use hard negatives - somewhat relevant but not as relevant as the positive 
		    - better distinguishes the decision boundary 
		- simple method to select FNs = se the anchor as a query + find the top-k matches in a document corpus 
			- using an embedding model that are not already determined as positive examples
    - <span style="color:rgb(255, 0, 247)">sentence pairs</span> (query-response, passage-summary, paraphrases) based on downstream use-case
	    - `sentence-transformers` shows different ways you can format the dataset
    - <span style="color:rgb(255, 0, 247)">dataset size</span>: from few thousand examples to billions of tokens for domain adaptation
- loss functions
	- use <mark style="background: #FFB8EBA6;">triplet loss</mark> to minimize anchor-positive distance & maximise anchor-negative distance

$$
\begin{gather}
\large
\textbf{Triplet Loss}
\\ \ \\
\large L(a, p, n) = \max\Big(0,\ \|f(a) - f(p)\|_2^2 - \|f(a) - f(n)\|_2^2 + \alpha\Big)
\end{gather}
$$
- where 
	- $a$ = anchor sample 
		- $p$ = positive sample - similar to anchor 
		- $n$ = negative sample - different to anchor
		- $f(\cdot)$ = embedding function (neural network) to map inputs to vector representations
	- $\|f(a) - f(p)\|_2^2$ = squared euclidean distance between anchor + positive embeddings
		- how similar anchor vs positive is 
	- $||f(a) - f(n)\|_2^2$ =  squared euclidean distance between anchor + negative embeddings
		- how dissimilar anchor vs negative is 
	- $\alpha$ = margin hyperparameter, represents distance by which negative sample should be further than positive
		- suggests using margin of 5 when using euclidean distance, but also try to tune it 

```python
from datasets import load_dataset
from sentence_transformers import SentenceTransformer, SentenceTransformerTrainer
from sentence_transformers.losses import TripletLoss

model = SentenceTransformer( "'all-mpnet-base-v2'")

dataset = load_dataset("csv", data_files="negatives_dataset.csv")

loss = TripletLoss(model)

trainer = SentenceTransformerTrainer(
    model=model,
    train_dataset=dataset
    loss=loss
   )
trainer.train()
model.save_pretrained("mpnet_finetuned_negatives")
```
# 4 Instruction embeddings
- <mark style="background: #FFB8EBA6;">instructor embeddings</mark> = allow specifying domain, text type, & task via instruction template
    - template: "represent the {`domain`} {`text_type`} for {`task_objective`}:"
	    - `domain` = domain of text e.g. law, finance etc 
	    - `text_type` = optional to represent unit of text encoded e.g. question, sentence, paragraph
	    - `task_objective` = task for which we use embeddings e.g. semantic search, paraphrase detection etc 
- for semantic search use instructions like: 
	- *"represent the question for retrieving supporting documents"* for queries 
	- *"represent the sentence for retrieval"* for documents
- can also use description-based retrieval
	- query can be the description of the text that needs to be retrieved, rather than an instantiation (example) of the text that needs to be retrieved
# 5 Optimising embedding size
- challenge: high-dim embeddings (eg 768 dims in float32) can use huge memory for large corpora
- idea: reduce dimensions or bit-precision without significant performance loss
## 5.1 Matryoshka embeddings
- train embeddings so that early dimensions carry more important info
- use multiple truncation dimensions (eg 128, 256, 512, 768 for a 1024-d vector) with weighted losses over each
- benefit: can truncate vectors based on cost/latency while preserving most performance
## 5.2 Binary & integer embeddings
- quantisation: represent each dimension with fewer bits (eg 1-bit instead of float32)
	- method: assign 1 if positive, 0 if negative (with potential scaling)
- pros: drastic storage reduction & faster similarity via bitwise ops
- cons: loss in precision may hurt performance
## 5.3 Product quantisation
- split vector into equal-sized chunks
- cluster each chunk into a fixed number of clusters (eg 256 for int8)
- represent each chunk by its cluster id
# 6 Chunking
- purpose: ensure retrieval captures full context even if relevant info spans multiple text segments
## 6.1 Sliding window chunking
- allow text to appear in overlapping chunks to include neighboring context
## 6.2 Metadata-aware chunking
- use document metadata (paragraphs, sections, subsections) to set chunk boundaries
- may require document parsing (tools like unstructured)
## 6.3 Layout-aware chunking
- use computer vision techniques to extract layout info (titles, font sizes, positions) for chunking
- tools: aws textractor, unstructured, layoutlmv3
## 6.4 Semantic chunking
- group text by topic via clustering; chunks can be non-contiguous if semantically linked
# 7 Multi-level embeddings
- strategy: use embeddings at multiple granularities (sentence, paragraph/dialog turn, section, document)
- higher-level embeddings capture summaries rather than verbatim text
- can use different models at each level with coarser levels often using higher quality (more expensive) models
- retrieval can be top-down or targeted at specific levels based on use-case
