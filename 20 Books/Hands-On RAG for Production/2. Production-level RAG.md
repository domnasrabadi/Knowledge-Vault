- as RAG app scales, complexity grows quickly 
	- complexity & scale factors:
		- <span style="color:rgb(62, 143, 249)">volume of documents</span> 
		- <span style="color:rgb(62, 143, 249)">size of documents</span>
		- <span style="color:rgb(62, 143, 249)">complexity of documents</span> (formats, data types etc)
		- <span style="color:rgb(62, 143, 249)">data freshness & maintenance</span> (docs constantly changing, adding, deleting)
		- <span style="color:rgb(62, 143, 249)">volume of user queries</span>
		- <span style="color:rgb(62, 143, 249)">response quality</span> (hallucinations, relevance etc)
		- <span style="color:rgb(62, 143, 249)">cost</span> (storage & compute for indexing, embedding, search, model responses)
	- problems these cause:
		- as number of documents grows, performance may degrade
		- dynamic + changing data sources → indexing & embedding can become painful
- advanced data ingestion 
	- as complexity & scale increases → need robust pipelines that can be iteratively developed
		- including having monitoring, error handling + version control 
		- and being able to detect and fix "gotchas" & nuanced bugs 
- the need for an efficient incremental update pipeline 
	- involves strategies for: 
		- detecting changes
		- selectively re-embedding & re-indexing affected docs/chunks
		- handling deletions gracefully 
- scaling challenges above + specific strategies 
	- multiple document formats 
		- RAG needs to work w diverse file formats - PDF, DOCX, MD, HTML etc 
			- each has its own nuances + challenges
				- PDFs → need OCR, no explicit structure, varying scan quality, font styles etc 
				- DOCX + PPT → embedded objects, formatting, tracked changes, comments 
		- approach is to use modular ingestion pipeline
			- utilising best-in-class libraries tailored to each file type 
			- `pymupdf`, `python-docx`, `python-pptx`, `bs4`, `whisper` 
	- handling large volume of docs 
		- can scale to thousands/millions of docs + need to manage extraction, chunking, embedding
			- these last 3 steps can take considerable time each 
		- solutions/approaches
			- parallelisation helps distribute the work → handling batches of docs across compute (esp. for embedding)
			- stage-specific optimisation → refine chunking, metadata extraction etc 
	- handling large documents 
		- use incremental/streamed + parallel processing 
			- instead of load/process entire file into memory at once → e.g. process page or section at a time 
			- also parallelise chunks/parts
	- handing tables & images 
		- use VLMs + store images as separate object type in vector DB
